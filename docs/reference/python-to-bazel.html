The big difference is not syntax. In Python, anything on sys.path is importable, so a missing dependency can work by accident. In Bazel, a program sees only what its targets declare, so every dependency is written down, and that is what makes caching and "test only what changed" safe (M02).

Dependencies: pip and pyproject.toml

requests
pip-compile requirements.in -o requirements_lock.txt
pip install -r requirements_lock.txt
load("@rules_python//python:pip.bzl", "compile_pip_requirements")

compile_pip_requirements(
    name = "requirements",
    src = "requirements.in",
    requirements_txt = "requirements_lock.txt",
)
pip = use_extension("@rules_python//python/extensions:pip.bzl", "pip")
pip.parse(
    hub_name = "pypi",
    python_version = "3.13",
    requirements_lock = "//:requirements_lock.txt",
)
use_repo(pip, "pypi")
pixi run bazel run //:requirements.update   # re-lock
pixi run bazel test //:requirements_test    # fails if the lock is stale
  • compile_pip_requirements(name = "requirements") creates //:requirements.update (writes the lock file) and //:requirements_test (checks it is up to date).
  • A PyPI package is a target in the hub: deps = ["@pypi//requests"]. Names are normalized (PyYAML is @pypi//pyyaml). A package that is not pinned in the lock file is no such package '@@rules_python++pip+pypi//...'.
  • pyproject.toml's [project.dependencies] is not read by Bazel. Keep a requirements.in (or generate one) as the source of truth for the hub.
  • Rule sets themselves (rules_python, rules_go, bazel_skylib) come from the Bazel Central Registry with bazel_dep. MODULE.bazel.lock records the resolution; commit it.

Running code: python -m and scripts

python -m app.main --name Ada
pixi run bazel run //app:main -- --name Ada
  • Program arguments go after --. Without it, Bazel reads --name as one of its own options and fails: ERROR: --name :: Unrecognized option: --name.
  • py_binary(name = "main") uses main.py from srcs as its entry point, matched by the end of the path (so srcs = ["cli/main.py"] also works). Otherwise set main = "...".
  • bazel run starts the program in its runfiles tree, not your shell's directory. BUILD_WORKSPACE_DIRECTORY holds the workspace path when a tool must write into your checkout.
  • The built program is bazel-bin/app/main; you can run it directly, too.

Testing: pytest selection and fixtures

pytestbazel test
pytestbazel test //...
pytest tests/test_api.pybazel test //tests:test_api
pytest tests/bazel test //tests/... or //tests:all
pytest -k parsebazel test //tests:test_api --test_filter=parse (the test runner receives it as TESTBRIDGE_TEST_ONLY)
pytest -x -vv--test_arg=-x --test_arg=-vv (arguments for the test program)
pytest -m "not slow"--test_tag_filters=-slow
pytest -s (show output)--test_output=all (or errors for failures only)
pytest --lf (last failed)Not needed: passing, unchanged tests are cached, so only affected tests rerun
pytest -p xdist -n 8Tests run in parallel by default, one action per target; shard_count splits one target
pytest --count=20--runs_per_test=20 to hunt flaky tests

Fixtures and test data

  • A conftest.py fixture that builds objects in code still works: put conftest.py in the test's srcs (or a py_library in deps).
  • A fixture that reads files (tests/data/*.json) needs those files declared: data = glob(["data/*.json"]), located through the runfiles library. An undeclared file is not in the sandbox.
  • Shared test helpers go in a py_library with testonly = True, so production code cannot depend on them (analysis fails with "depends on testonly target").
  • A py_test runs your file as a script. Without a runner (unittest.main(), or pytest invoked from a small main), a failing test can still exit 0 and "pass".

pytest decides what to run by scanning files. Bazel decides by the graph: a change to billing/utils.py reruns exactly the tests that depend on it, whichever directory they live in.
