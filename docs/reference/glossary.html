Glossary

The terms this course uses, in plain language, each linked to the section that teaches it. Definitions describe Bazel 9.3 with Bzlmod.

⏱ Look things up as you goAlphabetical, grouped for the table of contents

A–C

Action
One command Bazel runs during execution, with exactly declared inputs and outputs, such as a compile step, a genrule's command, or a test run. M02
Action key (action cache key)
A hash of an action's command line, environment, and input contents. Same key means Bazel can reuse the stored result instead of running the action. M02
Analysis phase
The second phase of a build: each target's rule runs in a configuration, checks its dependencies (existence, visibility, providers), and declares actions. Nothing executes yet. M02
Apparent repository name
The name your module uses for a dependency, such as @rules_python (or a repo_name you chose). Compare canonical repository name. M04
aquery
The action query: lists the actions behind targets, with mnemonics, command lines, inputs, and outputs. M09
Bazel Central Registry (BCR)
The default registry of Bazel modules at registry.bazel.build, where bazel_dep versions come from. M04
.bazelrc
A file of default options per command (build, test, common, ...) and named configs such as build:ci used with --config=ci. M06
.bazelversion
A file holding the Bazel release a workspace uses. Bazelisk reads it and runs that version. M00
Bazelisk
A launcher that downloads and runs the Bazel version in .bazelversion. Pixi installs it; this repository wraps it as bazel. M00
bazel-bin, bazel-out, bazel-testlogs
Convenience symlinks Bazel creates in the workspace, pointing into its output tree: built files, all outputs by configuration, and test logs. Never commit them. M00, M05
bazel_dep
The MODULE.bazel call that declares a dependency on another module at a minimum version. M04
BUILD file (BUILD.bazel or BUILD)
The Starlark file that declares a package's targets. Its directory becomes a package. M01
Build setting
A user-defined flag, such as bazel_skylib's string_flag or bool_flag, set on the command line as --//config:env=prod and read by select(). M06
Bzlmod
Bazel's module system for external dependencies, driven by MODULE.bazel. It replaced WORKSPACE, which Bazel 9 removed. M04
Cached test result
A test whose inputs did not change is not run again; Bazel reports (cached) PASSED. M05
Canonical repository name
The unique name Bazel uses internally, such as @@rules_python+. It appears in error messages; do not write it in BUILD files. M04
Configuration
The set of build options that affect outputs (compilation mode, platform, build settings). The same target built in two configurations produces two outputs. M06
config_setting
A target that matches a configuration (by option values, build settings, or constraints) and serves as a key in select(). M06
Constraint (constraint_setting, constraint_value)
A dimension of a platform, such as OS or CPU, and one value of it, such as @platforms//os:linux. M06
cquery
The configured query: like query, but with select() resolved for the flags you pass. M06, M09
Cycle (dependency cycle)
Targets that depend on each other in a loop; analysis fails. Break it by extracting the shared part into its own target. M02

D–G

data
The attribute for files a program or test reads at run time; they are placed in its runfiles. M02, M03
deps
The attribute for code dependencies (libraries). The dependency must provide what the rule expects, such as PyInfo. M02
dev_dependency
A bazel_dep or extension use that only applies when your module is the root, such as test tooling. M04
diff_test
bazel_skylib's test that passes when two files are identical; the basis of the golden-file pattern. M08
Disk cache
A local directory, set with --disk_cache=PATH, that stores action results across clean builds and workspaces. M02
embed
The rules_go attribute that compiles a go_test together with a library's sources, so internal tests can see unexported names. M07
Execution phase
The third phase: Bazel runs the actions whose outputs are needed and not already cached. M02
exports_files
Makes source files in a package usable (visible) from other packages. In Bazel 9, files are private to their package otherwise. M02
Flaky test
A test that sometimes passes and sometimes fails with the same inputs. flaky = True retries it; --runs_per_test helps find it. M05
Gazelle
A BUILD-file generator for Go (and, with extensions, Python), covered in Level 2. M07
Generated file
A file target produced by a rule (for example a genrule's outs); it lives under bazel-bin and is used by label like any file. M01, M08
genrule
A native rule that runs a shell command with declared srcs, tools, and outs. M08
glob()
A BUILD-file function that lists files matching patterns in the current package; it never crosses into a subpackage. M01
Golden file
A checked-in expected output that a diff_test compares against a generated file. M08
GoInfo
The provider rules_go targets return; go_* rules require it in deps and embed. M07

H–M

Hermeticity
Builds that depend only on declared inputs and pinned tools, so they produce the same result anywhere. M02
Hub (pip hub)
The repository that pip.parse creates, exposing one target per pinned distribution, used as @pypi//requests. M04
imports
The rules_python attribute that adds directories to the import path, for example ["src"] for a src layout. M03
Incompatible target
A target whose target_compatible_with constraints the target platform does not satisfy; wildcard builds skip it. M06
Label
A target's name: @repo//package/path:name. //pkg means //pkg:pkg; :name is relative to the current package. M01
Loading phase
The first phase: Bazel evaluates MODULE.bazel, BUILD files, and loaded .bzl files to build the target graph. M02
load()
Imports symbols from a .bzl file into a BUILD or .bzl file. Bazel 9 requires it for every rule-set rule. M00
Lock file (requirements)
A fully pinned, hashed requirements file that pip.parse reads; generate it with compile_pip_requirements. M04
Macro
A Starlark function in a .bzl file that declares targets. Legacy macros are plain functions; symbolic macros use macro(). M08
Make variables
Placeholders such as $(location ...), $(rlocationpath ...), and $@ that Bazel expands in cmd, args, and env. M08
manual tag
Excludes a target from wildcard patterns like //...; it still runs when named, or through a test_suite that lists it. M05
Minimal Version Selection (MVS)
Bzlmod's resolution rule: each module gets the highest of the minimum versions anyone asked for. M04
Module
A versioned unit of Bazel code with a MODULE.bazel file: your workspace, or a dependency such as rules_python. M04
Module extension
Code in a dependency that creates repositories from tags in your MODULE.bazel, such as rules_python's pip; bring its repositories into scope with use_repo. M04
MODULE.bazel
The file at the workspace root that names the module and declares its dependencies. M01
MODULE.bazel.lock
A generated file recording resolved module versions and extension results; commit it in real projects. M04

O–R

Override
single_version_override, local_path_override, git_override, and archive_override change where or which version of a module comes from; only the root module's overrides apply. M04
Package
A directory with a BUILD file, plus everything below it that is not another package. M01
package_group
A named set of packages used in visibility. M02
Platform
A set of constraint values describing a machine. --platforms selects the target platform. M06
Provider
Structured information a target passes to its dependents, such as PyInfo or GoInfo. Rules require certain providers in certain attributes. M02
PyInfo
The provider Python rules return and require in deps. A filegroup in deps fails because it lacks it. M02
query
Answers questions about the loading-phase graph with functions such as deps, rdeps, somepath, and kind. It shows both branches of every select(). M09
rdeps
The query function for reverse dependencies: what in a universe depends on a target. The basis of affected-test selection. M09
Remote cache
A shared server storing action results, so CI and teammates reuse each other's work. Level 2 covers it. Roadmap
Repository (repo)
A tree of Bazel packages: the main repository (your workspace) or an external one created for a module or extension. M04
Rule
A kind of target, such as py_library or go_test. Rules come from rule sets that you load(), or are native (genrule, filegroup, ...). M00
run_binary
bazel_skylib's rule that runs a binary target as a build action without a shell; preferred over a genrule for that job. M08
Runfiles
The tree of files a binary or test needs at run time (its code and data), found with the runfiles library. M03

S–Z

Sandbox (sandboxing)
Running each action in a directory that contains only its declared inputs, so undeclared dependencies fail. M02
select()
Chooses an attribute value by configuration, keyed by config_settings or constraints, with //conditions:default as the fallback. M06
Sharding
Splitting one test target across several processes with shard_count; the test runner must support it. M05
Size (test size)
small, medium (default), large, or enormous: sets a test's default timeout and resource estimate. M05
somepath, allpaths
Query functions that show one or all dependency paths between targets: the answer to "why does X depend on Y?" M09
Source file
A file in the workspace used as a target, such as //hello:hello.py. M01
Starlark
The Python-like language of BUILD, .bzl, and MODULE.bazel files: deterministic, with no f-strings, while, try, or import. BUILD files also forbid def and top-level for/if. M00, M08
Subpackage
A directory with its own BUILD file inside another package; labels and globs cannot reach into it. M01
Target
Something in a package Bazel can build or use: a rule, a source file, or a generated file. M01
Target pattern
A way to name many targets: //..., //pkg/..., //pkg:all, //pkg:*, and exclusions after --. M01
test_suite
A native rule that groups tests by list or by tag. M05
testonly
Marks a target as usable only by tests and other testonly targets. M02, M05
TEST_TMPDIR
The writable scratch directory Bazel gives each test; write there, never next to your sources. M05
Toolchain
A pinned tool (a Python interpreter, the Go SDK) that Bazel selects for a platform, so builds do not use whatever is installed. M03, M07
tools
The genrule attribute for programs the command runs; they are built for the execution platform, unlike srcs. M08
use_repo
Brings repositories created by a module extension into your module's scope, such as use_repo(pip, pypi = "weather_pypi"). M04
Visibility
Who may depend on a target: private by default, or //visibility:public, //pkg:__pkg__, //pkg:__subpackages__, or a package_group. M02
WORKSPACE
The pre-Bzlmod file for external dependencies. Disabled by default in Bazel 8 and removed in Bazel 9; seeing it marks an old tutorial. M00
Workspace
The directory tree Bazel builds, rooted where MODULE.bazel lives. M01
