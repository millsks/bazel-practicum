Roadmap: Levels 2-3

Level 1 teaches you to build a polyglot monorepo with Bazel 9. Level 2 makes that monorepo fast and reproducible for a whole team: toolchains, remote caching and execution, CI, containers, and generated BUILD files. Level 3 teaches you to extend Bazel itself with Starlark rules, providers, and aspects. This page describes both and shows where Level 1 prepares you for each.

Gate 1: are you ready for Level 2?

You are ready when you can do these without looking anything up:

  • Write BUILD files for a new Python package and a new Go package from a blank page
  • Add a PyPI dependency (lock file, hub, @pypi//name) and a BCR module
  • Explain the three phases and say which one a given error comes from
  • Fix a visibility error without making the target public
  • Write a config_setting and a select(), and check it with cquery
  • Generate a file with a genrule or run_binary and test it with diff_test
  • Answer "which tests does this change affect?" with bazel query
  • Pass Capstone 1 with pixi run grade c1

Level 2: Bazel for a team

Level 1 makes a monorepo correct. Level 2 makes it fast for everyone and identical everywhere. Each stage ends with labs against real Bazel, as in Level 1.

Stage 3: Toolchains and hermeticity

A toolchain is how a rule finds its compiler or interpreter for a given platform, without hard-coding a path. You have already used two: the Python interpreter from python.toolchain and the Go SDK from go_sdk.download. Stage 3 opens the box.

  • toolchain_type, toolchain(), and register_toolchains: how Bazel picks one toolchain per type for the target and execution platforms, and how to read --toolchain_resolution_debug when it says "No matching toolchains found".
  • Execution versus target platforms, and cross-compiling a Go binary for linux_arm64 from a Mac.
  • Hermeticity audits: finding actions that read the host (/usr/bin, $HOME, the network) with sandboxing, --incompatible_strict_action_env, and aquery.
  • Hermetic C/C++ (for Python extensions and cgo) and why it is the hardest toolchain to pin.

Level 1 prepares you with: the Python and Go toolchains (M03, M07), platforms and constraint_values in select() (M06), and the sandbox and hermeticity ideas of M02.

Stage 4: Remote caching, remote execution, and CI

Because every action's key is a hash of its command and inputs, its result can come from any machine that ran the same action. That is the payoff of everything in Level 1.

  • --disk_cache first, then a remote cache (--remote_cache=grpcs://...) shared by CI and developers: who may write to it, and why CI usually writes and laptops only read.
  • Remote execution (--remote_executor): running actions on a build farm, and the hermeticity it demands.
  • Diagnosing cache misses: comparing execution logs between two machines to find the input that differs.
  • CI with Bazel: a build:ci config in .bazelrc, caching the repository cache and Bazelisk downloads, and running only affected targets with bazel query.
  • Build event protocol (--build_event_json_file) and result UIs.

Level 1 prepares you with: action keys and (cached) PASSED (M02), .bazelrc and --config (M06), and rdeps for affected tests (M09).

Stage 5: Containers with rules_oci, and Gazelle

  • rules_oci: building OCI container images from your Python service and Go CLI without a Docker daemon (oci_image, layers from tar rules, base images pulled by digest), and pushing them from CI. Images become ordinary, cacheable build outputs.
  • Running container structure tests as bazel test targets.
  • Gazelle: generating and updating BUILD files from your sources. For Go it reads imports; with the rules_python Gazelle plugin it does the same for Python. You will learn what it writes, the # gazelle: directives that steer it, and how to keep hand-written and generated BUILD files side by side.

Level 1 prepares you with: writing BUILD files by hand, so you can review what Gazelle generates (M01, M07), and generated files and run_binary (M08).

Level 3: Extending Bazel

Macros (M08) can only arrange existing rules. When no rule does what you need, you write one. Level 3 is about the Starlark that rule sets such as rules_python and rules_go are made of.

Stage 6: Starlark rules and providers

  • rule() and its implementation function: ctx.attr, ctx.files, ctx.actions.run/run_shell/write, and declaring outputs.
  • Providers: the typed data a target hands to the targets that depend on it. You met PyInfo and GoInfo as "does not have mandatory providers" errors; here you define your own with provider() and collect them across the graph with depsets.
  • Executable and test rules, runfiles, and DefaultInfo.
  • Custom build settings: writing the rule behind a string_flag, and transitions that change configuration for part of the graph.
  • Module extensions: how pip.parse and go_sdk.download create repositories.

Level 1 prepares you with: Starlark in BUILD and .bzl files and macros (M08), providers as an analysis-time contract (M02), the three phases (M02), and module extensions from the user side (M04).

Stage 7: Aspects and testing rules

  • Aspects: running extra analysis along the dependency graph without editing any BUILD file, the way type checkers and linters (mypy, ruff, nogo) are wired into Bazel builds.
  • Testing rules with bazel_skylib's unittest.bzl and analysistest: asserting on the actions and providers a rule creates, and that it fails with the right message.
  • Documenting rules with Stardoc and publishing a module to a registry.

Level 1 prepares you with: aquery and cquery (M09) and diff_test/build_test (M08).
