Capstone 1: Polyglot Monorepo

Harbor Supply is a small company with one repository: a Python pricing library, a quote service that uses it, a Go tool that formats money, and a product catalog that becomes Python code at build time. Somebody started moving it to Bazel and stopped halfway. You finish the job, and real Bazel grades every part of Level 1 along the way.

⏱ ~6–8 hoursPrerequisites: M01 to M09
  • Lay out a monorepo as Bazel packages with deliberate, narrow visibility, and prove the boundaries hold
  • Declare every rule set in MODULE.bazel, and pull a PyPI package through pip.parse with a hashed lock
  • Ship data and a Go binary to Python code through runfiles, data, and $(rlocationpath)
  • Keep tests sized, cached, and grouped, with a slow test that //... skips
  • Choose data at build time with a string_flag, select(), and .bazelrc configs
  • Generate Python code with run_binary and guard it with a diff_test golden file
  • Use bazel query to prove the dependency graph has the shape the design says it has

The scenario

Today Harbor's repository works the way many Python repositories do. The service imports the library through an editable install. A Makefile runs go build before the Python tests that call the Go tool. A script turns catalog.csv into catalog.py, and somebody remembers to run it (usually). A REGION environment variable picks US or EU prices at run time. Nothing stops the reporting script from importing the pricing internals, and nobody knows which tests a catalog change can break.

After the move to Bazel, all of that is in one graph. You will be able to say, with a command and not a guess:

  • which packages may use the pricing library (only services), and get a build error if anything else tries;
  • that the catalog module is always regenerated when the CSV or the generator changes, and never checked in;
  • that the Python quote test gets the Go binary it needs, built for this machine, with no Makefile;
  • that a US build and an EU build differ in exactly one data file, chosen at build time;
  • which tests a change to catalog.csv affects (four Python tests, no Go test).

The application code is small and already written. Your work is almost all Bazel: MODULE.bazel, .bazelrc, and BUILD files. When you need to change a .py or .go file, something is wrong in a BUILD file instead.

Requirements

  1. Modules. MODULE.bazel has a bazel_dep for every rule set a BUILD file loads from: rules_python 2.4.6, rules_go 0.65.0, bazel_skylib 1.9.2. Python 3.13 and Go 1.25.3 are hermetic toolchains.
  2. Packages. Every target in the table exists with the kind shown. bazel build //... succeeds.
  3. Visibility. Each target is visible exactly as the table says. The grader adds a package outside //services that must fail to use //libs/pricing, //data:catalog, and //tools/fmtcli/money, and a second package under //services that must succeed in using //libs/pricing.
  4. PyPI. requirements_lock.txt is generated by bazel run //:requirements.update, with sha256 hashes. The hub is named harbor_pypi and visible as @pypi. //libs/pricing depends on @pypi//tabulate; the pytest test depends on @pypi//pytest and actually collects its 5 tests.
  5. Runfiles. The quote binary and both quote tests find region.json and the Go tool in their runfiles, never through a relative path. They read the Go tool's location from the FMTCLI environment variable, set with $(rlocationpath //tools/fmtcli).
  6. Tests. Every test has a size that does not trigger Bazel's "too big" hint. bazel test //... passes, and a second run is all (cached) PASSED. The exhaustive test is the only manual test; //:fast lists the four fast tests; //:slow runs the exhaustive test and is itself skipped by //....
  7. Configuration. --//config:region=eu and --config=eu build an EU quote; unknown regions are rejected; --config=ci builds with -c opt, prints logs only for failing tests, and is accepted by bazel query as well.
  8. Go. bazel run //tools/fmtcli -- EUR 123456 -75 prints EUR 1.234,56 and -EUR 0,75. The Go test is internal and uses embed.
  9. Generated code. data/catalog.py is never checked in. It is generated by a run_binary whose tool is //tools/catalog_gen, and a diff_test compares it with the reviewed data/catalog.golden.py.
  10. Graph shape. Only services, the pricing tests, and the two suites depend on //libs/pricing. The pricing library does not depend on the region flag. The Go tool has no Python in its graph. A change to catalog.csv affects the Python tests and the golden test, and no Go test.

Sketch it first

Before you edit files locally, try the visibility part of the design in the simulator. The pricing library below is public, so the reporting tool in //tools/report can use it. Narrow the visibility so that both services still build and the reporting tool does not. Then ask the graph who depends on pricing.

Reveal: the narrowest visibility that works

visibility = ["//services:__subpackages__"]. It covers //services/quote, //services/invoice, and any service added later, and nothing in //tools. ["//services/quote:__pkg__"] is narrower but breaks the invoice service (and the grader's extra service package). The pricing test needs nothing: a package can always use its own targets.

Milestones

Work in this order: each milestone needs the ones before it. The grader names every check after its milestone (M1:, M2:, …), so you can grade at any time and look only at the lines for the milestone you are on. Try each step for a while before you open the hints.

Milestone 1: modules, packages, and visibility

Requirements 1 to 3. Skills from M01, M02, and M04. Add the missing modules, then fix visibility from the bottom of the graph up.

  • MODULE.bazel has bazel_dep for rules_go and bazel_skylib, and go_sdk.download(version = "1.25.3")
  • //tools/catalog_gen is visible to //data only
  • //services/quote is a py_binary with main = "main.py", built on //services/quote:quote_lib
  • //libs/pricing is visible to //services:__subpackages__; //data:catalog to //libs/pricing:__pkg__

Hint: why is the generator not visible?

A py_binary with no visibility is private to its own package. Something in //data runs it, so //data needs to see it: visibility = ["//data:__pkg__"]. Do not make it public: nothing else has a reason to run the generator.

Hint: the quote binary and main.py

Without main, a py_binary named quote looks for quote.py in its srcs. Here the entry point is main.py, so say so with main = "main.py". The logic stays in :quote_lib, which both tests also use.

Milestone 2: PyPI and runfiles

Hint: generating the lock

Add pip.parse and use_repo first, with the placeholder lock in place. Hint: a test that passes but runs nothing

If pricing_test passes in a fraction of a second with no pytest summary in --test_output=all, Bazel ran pricing_test.py as a script: it defined five functions and exited 0. Make pytest_main.py the main, put it in srcs, pass the test file with args = ["$(rootpath pricing_test.py)"], and depend on @pypi//pytest. This is the pattern from M04.

Hint: label '//tools/fmtcli:fmtcli' is not a declared prerequisite

The quote code reads the Go tool's runfiles path from FMTCLI. If you set env = {"FMTCLI": "$(rlocationpath //tools/fmtcli)"} but put the tool in the library's data, analysis fails:

Since this rule was created by the macro 'py_test', the error might have been caused by the macro implementation

$(rlocationpath) only expands labels in the same rule's attributes. Put data = ["//tools/fmtcli"] on each executable that sets FMTCLI. The region file is different: quote.py finds it at the fixed path _main/data/regions/region.json, so it can live in quote_lib's data and every user of the library gets it. Milestone 3: tests at scale

Requirement 6. Skills from M05.

  • Every test is size = "small", and bazel test //... shows no "too big" hint
  • //services/quote:exhaustive_test is tagged manual; no other test is
  • The root BUILD.bazel has test_suites fast (four tests) and slow (manual)
  • A second pixi run bazel test //... is all (cached) PASSED
Hint: the suite that runs a manual test

A test_suite runs every test it names, manual or not. That is why //:slow can run the exhaustive test, and also why //... runs it if the suite itself is not tagged manual: the wildcard matches the suite, and the suite brings its test along.

Hint: the tests are not cached

A test result is cached when nothing it depends on changed: sources, data, flags, and environment. If the second run re-runs a test, look for something that changes between runs: a --nocache_test_results in a .bazelrc, or a different --config. Changing flags between the two runs changes the configuration, which is a different cache key.

Milestone 4: a region flag and named configs

Requirement 7. Skills from M06 and M08 (copy_file).

  • //config:region is a string_flag with values us and eu; //config:eu is a public config_setting
  • //data/regions:region is a copy_file whose src is a select() and whose out is region.json
  • .bazelrc has common:eu and a ci config that bazel query accepts
  • pixi run bazel run //services/quote --config=eu -- WIDGET=2 GADGET prints a quote in EUR
Hint: why copy_file and not select() in data?

In M06 the select() went straight into a binary's data, and the program looked for each possible file. Here the program reads one fixed name, region.json. copy_file (from @bazel_skylib//rules:copy_file.bzl) produces that name, and the select() decides what goes into it. Python code never needs to know which regions exist.

Hint: Config value 'ci' is not defined

build:ci ... lines apply to build and the commands that inherit from it (test, run, cquery), but not to query. Write common:ci -c opt so every command accepts --config=ci, and keep test:ci --test_output=errors for the test-only part.

Design notes

The spec makes several choices for you. Each one is a trade-off you will meet again in real repositories.

Package boundaries

A Bazel package is a directory with a BUILD file, and it is the unit of visibility. The layout follows who owns what and who may use it: libs/ for code shared by services, services/ for things that run, tools/ for developer and build tools, data/ for data and the code generated from it, config/ for build settings. A finer split (one package per directory, as here) costs a few more BUILD files and buys precise visibility and smaller rebuilds. A coarser split (one BUILD file at libs/) is less work today and makes every target in it visible to every other.

//tools/fmtcli/money is its own package even though only one binary uses it. That separation is what lets the grader prove that nothing else imports it, and it is where a second Go tool would come from if the library ever went public.

Visibility: narrow by default, widen on purpose

  • Use package patterns for groups, labels for single users. //services:__subpackages__ means "any service, now or later". //libs/pricing:__pkg__ on the catalog means "exactly one user". A new service needs no BUILD change; a new user of the catalog needs a reviewed one.
  • Make the API public, not its parts. //tools/fmtcli is public because anyone may run the tool. Its money package is private, so the binary's command line is the only contract.
  • Tests live next to their code. A test in the same package needs no visibility at all. The grader's //services/grading package is a test of the visibility rule itself.
  • In a larger repository you would name groups with package_group and refer to them in visibility, so "who counts as a service" is written down once.

Where generated code lives

catalog.py exists only in bazel-bin/data/. It is never checked in, so it cannot drift from the CSV, and nobody reviews generated diffs by accident. Python still imports it as data.catalog, because in the runfiles tree Bazel merges source files and generated files under the same package path. The cost is that an editor without Bazel integration cannot find the module.

The golden file is the deliberate exception. It is a reviewed snapshot: when the generator or the CSV changes, the diff_test fails, and a person looks at the new output before updating the golden. That turns a silent behavior change into a visible code review. The price is one extra step on every intended change.

Choosing the region at build time

The old repository read a REGION environment variable at run time. A build flag is better for Harbor: the US and EU builds are different artifacts with different cache keys, cquery shows what each one contains, and nobody can ship a US build that silently reads EU prices. A run-time setting is better when one artifact must serve both regions; that is a product decision, not a Bazel one.

The select() sits as close to the data as possible, in //data/regions. The pricing library takes a tax rate as an argument and never sees the flag, which keeps it cached once for both regions, and is exactly what somepath(//libs/pricing, //config:region) verifies. Try it in the simulator:

Configs in .bazelrc

--config=ci is the one flag the CI pipeline passes, so what "a CI build" means lives in the repository and is reviewed like code. It uses common: so that every command accepts it, including bazel query in a CI script. Region and CI are separate configs on purpose: CI can run --config=ci --config=eu, and a developer can try --config=eu without an optimized build.

Smaller choices

  • The hub is harbor_pypi, aliased to @pypi. rules_python 2.4.6 reserves the hub name pypi; naming hubs after the module also keeps them unique when modules are combined.
  • The Go tool is data, not deps. Python cannot import a Go binary; it runs one. Run-time files are data.
  • FMTCLI is set on each executable. $(rlocationpath) only expands labels in the same rule, so the binary and each test repeat two lines. A macro would remove the repetition (see the stretch goals).
  • The exhaustive test is manual, not size = "large". Size describes how much a test needs; manual decides when it runs. Wildcards skip it, and the //:slow suite names it.

Self-review

Passing the grader means the build is right. Before you call the capstone done, review your BUILD files as a teammate would review a pull request.

  • No target is //visibility:public except //tools/fmtcli and //config:eu, and you can say why each of those is
  • No TODO markers are left in BUILD files, MODULE.bazel, or .bazelrc
  • Every load() is used, and every rule set loaded from has a bazel_dep
  • You never edited requirements_lock.txt or bazel-bin output by hand
  • You can explain why region.json is in quote_lib's data but the Go tool is in each executable's data
  • You can predict which tests re-run after editing money.go, catalog.csv, and pricing.py, and you checked with rdeps
  • BUILD files are formatted consistently (attributes sorted, one item per line in long lists), as buildifier would

Stretch goals

None of these are graded. Several add targets or tests, so try them on a copy of work/c1 or after you have passed.

  • A pytest macro. Write tools/bazel/pytest.bzl with a py_pytest_test macro that adds pytest_main.py, main, args, and @pypi//pytest for you (M08).
  • A quote test macro. Remove the repeated data and env for FMTCLI with a macro for "executables that run the Go formatter".
  • Bless the golden in one command. Add //data:update_golden, a py_binary that copies the generated file over the golden with BUILD_WORKSPACE_DIRECTORY.
  • A second service. Add //services/invoice that uses the pricing library without any BUILD change outside its own package. Then check how rdeps changes.
  • Name the group. Replace //services:__subpackages__ with a package_group named //libs:services and use it everywhere.
  • Test both regions. Make bazel test //... --config=eu assert EUR in quote_test, and run both regions in CI. How does the cache behave when you alternate?
  • Inspect an action. Use bazel aquery 'mnemonic("RunBinary", //data:catalog_gen)' to see the exact command line run_binary produces.
  • Share a cache. Add --disk_cache in user.bazelrc, delete bazel-* output with bazel clean, and watch the next build come back from the cache.

Recap

  • Packages and visibility turn an architecture diagram into rules the build enforces.
  • MODULE.bazel names every rule set and toolchain; pip.parse and a hashed lock make PyPI dependencies reproducible.
  • Programs find data and other programs through runfiles, with data and $(rlocationpath).
  • Sizes, manual, and test_suite decide how tests run; unchanged tests come from the cache.
  • A string_flag and one select() near the data choose build variants; .bazelrc configs name them.
  • Generated code lives in bazel-bin; a diff_test against a golden file makes changes to it reviewable.
  • rdeps, somepath, and kind answer "what depends on this?" and "what does this change affect?" with facts.

That is Level 1. The roadmap shows what comes next: toolchains, remote caching and execution, and writing your own rules.
