Go: A Second Language

A second language is where Bazel stops being "a slower way to run pytest" and starts paying for itself. In this module you add Go to a Python workspace: one graph, one cache, one bazel test //... for both. You learn just enough Go to read and write a small tool, then test that tool from Python.

⏱ ~2.5 hoursPrerequisites: M06
  • Read and write a small Go package: package, func main, imports, exported names, and testing.T tests
  • Add rules_go to MODULE.bazel and pin a hermetic Go SDK with go_sdk.download
  • Write go_library (with importpath), go_binary, and go_test, and choose between embed and deps for a test
  • Read the errors Go targets produce: missing strict dependencies, undefined, and GoInfo provider errors
  • Run a Go binary from a Python test through data, $(rlocationpath), and the runfiles library
  • Explain what Gazelle and go_deps are for, and when you will need them

Why a second language changes the picture

Picture a Python service with a small Go command-line tool next to it. Without Bazel you have two worlds: pixi run pytest for one, go test ./... for the other, two CI jobs, two caches, and a shell script that builds the Go tool before the Python tests that call it. Nothing knows that a change to the Go code should re-run those Python tests.

Bazel has no special notion of "the Python part" and "the Go part". A go_binary is a target like a py_binary: it has inputs, actions, and outputs, and other targets can depend on it. So the workspace gets:

One graph

bazel query 'rdeps(//..., //textutil)' finds Go and Python dependents alike.

One cache

Go compile actions and Python test results are keyed the same way, by input hashes, and shared the same way.

One test command

bazel test //... runs go_test and py_test targets together and reports them in one list.

Precise reruns

Edit the Go tool, and only the tests that depend on it run again, in either language.

This module builds that workspace: a Go package //textutil that counts lines and words, a Go command //tools/wc that uses it, and a Python test that runs the command and checks what it prints. Click the files below to see what each edit re-runs.

Click main.go. The Go unit test stays cached, but the Python test re-runs. Which shell script or Makefile you have seen would get that right?

Remember: to Bazel, languages are just rule sets. Once Go is in the graph, every Bazel guarantee you learned for Python (sandboxing, caching, precise reruns, query) covers it too.

Just enough Go for a Python developer

You do not need to become a Go programmer to follow this module, but you need to read four things: packages, main, imports, and tests. Go is compiled, statically typed, and has a small standard library that covers everything here. Here is the library we will build, next to its Python twin.

// Package textutil counts lines and words in text.
package textutil

import "strings"

// Words returns the number of whitespace-separated words in s.
func Words(s string) int {
	return len(strings.Fields(s))
}

// Lines returns the number of newline characters in s, like wc -l.
func Lines(s string) int {
	return strings.Count(s, "\n")
}
"""Count lines and words in text."""


def words(s: str) -> int:
    """Return the number of whitespace-separated words in s."""
    return len(s.split())


def lines(s: str) -> int:
    """Return the number of newline characters in s, like wc -l."""
    return s.count("\n")
Package
Every Go file starts with package <name>. All .go files in one directory belong to one package and see each other's names without importing, as if a Python package were a single module.
Exported names
Go has no __all__ and no leading underscore. A name starting with a capital letter (Words) is exported: other packages can use it. A lowercase name (words) is private to its package, and the compiler enforces it.
Types
func Words(s string) int is Python's def words(s: str) -> int, except the types are checked at compile time. Types come after names.
Formatting
Go code is indented with tabs and formatted by gofmt; nobody argues about style.

Programs: package main and func main

A Go program is a package named main with a function main(). It is Go's if __name__ == "__main__":, except it is the only way in. Imports name a package by its import path, a string like a URL:

// Command wc counts lines and words.
//
// With arguments, each argument is one line of text:
//
//	wc "to be or" "not to be"   prints   2 lines, 6 words
//
// Without arguments, it reads standard input.
package main

import (
	"fmt"
	"io"
	"os"
	"strings"

	"example.com/polyglot/textutil"
)

func main() {
	var text string
	if len(os.Args) > 1 {
		text = strings.Join(os.Args[1:], "\n") + "\n"
	} else {
		data, err := io.ReadAll(os.Stdin)
		if err != nil {
			fmt.Fprintln(os.Stderr, "wc:", err)
			os.Exit(1)
		}
		text = string(data)
	}
	fmt.Printf("%d lines, %d words\n", textutil.Lines(text), textutil.Words(text))
}
  • "fmt", "io", "os", "strings" are standard library packages. "example.com/polyglot/textutil" is ours; you use it by its last element, textutil.Words(...), like import textutil in Python.
  • os.Args is sys.argv. := declares and assigns a new variable.
  • Functions return errors as values: data, err := io.ReadAll(...), then if err != nil. Go has no exceptions for ordinary failures.

Tests: _test.go files and testing.T

Go's test convention is close to pytest's: test files end in _test.go, and each test is a function named TestXxx that receives a *testing.T. There is no assert; you compare and call t.Errorf, which marks the test failed and keeps going.

package textutil

import "testing"

func TestWords(t *testing.T) {
	cases := map[string]int{
		"":                0,
		"one":             1,
		"  two  words \n": 2,
	}
	for in, want := range cases {
		if got := Words(in); got != want {
			t.Errorf("Words(%q) = %d, want %d", in, got, want)
		}
	}
}
import pytest

from textutil.count import words


@pytest.mark.parametrize("text, want", [("", 0), ("one", 1), ("  two  words \n", 2)])
def test_words(text: str, want: int) -> None:
    assert words(text) == want

Notice the first line: package textutil. This test lives inside the package it tests, so it can call Words without a prefix (and could call lowercase helpers too). Go calls this an internal test. A test file that says package textutil_test instead is an external test: it imports textutil like any other user and sees only exported names. This difference matters to Bazel, as you will see.

Unlike unittest in M03, you never write a main for tests. Go's tooling generates the test runner, and rules_go does the same. A failing t.Errorf makes the test binary exit non-zero, which is what Bazel reads.

Remember: one directory, one package; capitalized names are public; programs are package main; tests are TestXxx(t *testing.T) in _test.go files.

MODULE.bazel for Go and the hermetic SDK

In M03, two lines in MODULE.bazel gave every Python target the same interpreter, whatever python3 your laptop has. Go works the same way, with a Go SDK (the compiler, linker, and standard library) instead of an interpreter.

Add the rule set with bazel_dep, then pin the SDK with rules_go's go_sdk module extension:

module(name = "polyglot")

bazel_dep(name = "rules_go", version = "0.65.0")
bazel_dep(name = "rules_python", version = "2.4.6")

go_sdk = use_extension("@rules_go//go:extensions.bzl", "go_sdk")
go_sdk.download(version = "1.25.3")

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(python_version = "3.13", is_default = True)

A module extension (M04) is code in a rule set that creates repositories from tags you write in MODULE.bazel. go_sdk.download(version = ...) is such a tag: it tells rules_go to download that Go release from go.dev and register it as the Go toolchain.

Unlike pip.parse in M04, go_sdk.download needs no use_repo(...) line. Go rules find the SDK through toolchain resolution, not by repository name. The SDK repositories even get mangled names (rules_go++go_sdk+main___download_0_linux_amd64) so nothing depends on them directly. Adding use_repo(go_sdk, "go_sdk"), a natural guess, fails before anything builds:

INFO: Elapsed time: 1.524s

Proof that it is hermetic

The machine these examples ran on has a system Go installed, an older one:

$ go version
go version go1.24.7 linux/amd64

A tiny program that prints runtime.Version(), the Go release it was compiled with, tells a different story under Bazel:

INFO: Running command line: bazel-bin/version/version_/version
built with go1.25.3 for linux/amd64

Bazel never looked at the system go. You do not need Go installed at all: Pixi installs Bazelisk, Bazelisk installs Bazel, and rules_go installs Go. Teammates on macOS and CI on Linux all compile with 1.25.3.

What if you leave go_sdk.download out? rules_go then registers its own default SDK. With rules_go 0.65.0 that is the version in rules_go's own go.mod, and the same program prints:

INFO: Running command line: bazel-bin/version/version_/version
built with go1.26.7 for linux/amd64

Still hermetic, but your Go version would silently change whenever you upgrade rules_go. Pin it.

rules_go registers SDKs for several platforms (Linux, macOS, and Windows, on amd64 and arm64) but downloads only the ones a build needs. Your first Go build also compiles the Go standard library once (a GoStdlib action, about a minute) and caches it like any other action.

If your Go code already has a go.mod, go_sdk.from_file(go_mod = "//:go.mod") reads the version from it, so go build and Bazel cannot drift apart. go_sdk.host() uses the system Go instead; the rules_go docs discourage it because it is not reproducible.

Try the simulator. It reads the same MODULE.bazel and loads the Go rules; break the bazel_dep line to see what a BUILD file says when @rules_go is unknown.

The simulator accepts any go_sdk tag and any use_repo of it, and it never downloads anything. The use_repo and go_version errors above come from real Bazel only.

Remember: bazel_dep(name = "rules_go", ...) plus go_sdk.download(version = "1.25.3"), no use_repo. The system Go is never used.

go_library and go_binary

rules_go's rules come from @rules_go//go:def.bzl. As with Python in Bazel 9, you must load() them; without it the error is the familiar name 'go_binary' is not defined (did you mean 'cc_binary'?).

load("@rules_go//go:def.bzl", "go_library")

go_library(
    name = "textutil",
    srcs = ["count.go"],
    importpath = "example.com/polyglot/textutil",
    visibility = ["//visibility:public"],
)
load("@rules_go//go:def.bzl", "go_binary")

go_binary(
    name = "wc",
    srcs = ["main.go"],
    visibility = ["//visibility:public"],
    deps = ["//textutil"],
)

Most attributes look like the Python ones. One is new:

depsallOther Go targets this code imports.

Why importpath exists

In Python under Bazel, a module's import name comes from its file path: textutil/count.py is textutil.count. Go imports are strings, and by convention they look like where the code would live on the internet: example.com/polyglot/textutil, github.com/acme/tools/textutil. Bazel cannot derive that from the directory, so you state it. Most teams use one prefix for the whole repository plus the package path.

When the Go compiler sees import "example.com/polyglot/textutil", rules_go looks for a target in deps whose importpath is exactly that string. Forget the deps entry, or misspell the importpath, and compilation fails with Bazel's strict dependencies check (absolute paths shortened to <output_base>):

Note the path: bazel-bin/tools/wc/wc_/wc, not bazel-bin/tools/wc/wc. rules_go puts each binary in a directory named <name>_. Remember that; it matters when Python goes looking for it. There is no launcher script either: a Go binary is one self-contained executable.

Predict the output of the first command, then run them. deps includes source files, and Go has no runfiles library in its deps.

Real bazel query 'deps(//tools/wc)' also lists rules_go's own implicit targets (its compiler configuration and test helpers). Add --noimplicit_deps to hide them; real Bazel then prints exactly the four labels of your own code, as the simulator does.

srcs of a Go target only accepts Go-toolchain files. Listing a Python file there is rejected at analysis: source file '//tools/wc:helper.py' is misplaced here (expected .go, .s, .S, .h, .c, .cc, .cpp, .cxx, .h, .hh, .hpp, .hxx, .inc, .m, .mm, or .syso).

Remember: go_library needs an importpath; every Go import of your own code needs a deps entry whose importpath matches, or the compile fails with "missing strict dependencies".

go_test: embed or deps?

A go_test compiles your _test.go files with a generated runner into a test binary. How it gets the code under test depends on which kind of test file you wrote.

Internal test: embed

go_test(
    name = "textutil_test",
    srcs = ["count_test.go"],
    embed = [":textutil"],
)

count_test.go says package textutil. It must be compiled together with count.go as one package. embed means exactly that: "add this library's sources to mine".

External test: deps

go_test(
    name = "ext_test",
    srcs = ["words_test.go"],
    deps = ["//textutil"],
)

words_test.go says package ext_test and imports example.com/polyglot/textutil. It is a separate package that uses the library, so the library is a normal dependency.

The common mistake is using deps for an internal test. The library is then compiled as a separate package, and the test file, which is also named package textutil, has no Words of its own:

Mixing languages in deps: the GoInfo error

M02 introduced providers: the typed information a target hands to the targets that depend on it. py_library provides PyInfo (import paths, sources). go_library provides GoInfo (an import path and a compiled package). Each rule says which providers its deps must have, and Bazel checks it during analysis.

So a Go target cannot list a Python library in deps, however natural it looks in a polyglot repo:

go_binary(
    name = "wc",
    srcs = ["main.go"],
    deps = [
        "//textutil",
        "//pylib:helpers",   # a py_library
    ],
)
ERROR: /home/claude/bazel-practicum/build/scratch-m07/ws/tools/wc/BUILD.bazel:3:10: in deps attribute of go_binary rule //tools/wc:wc: '//pylib:helpers' does not have mandatory providers: 'GoInfo'. Since this rule was created by the macro 'go_binary_macro', the error might have been caused by the macro implementation
ERROR: /home/claude/bazel-practicum/build/scratch-m07/ws/tools/wc/BUILD.bazel:3:10: Analysis of target '//tools/wc:wc' (config: a7a71fd) failed
ERROR: Analysis of target '//tools/wc:wc' failed; build aborted

The same check runs the other way. A Python target that lists the Go binary in deps:

ERROR: /home/claude/bazel-practicum/build/scratch-m07/ws/pylib/BUILD.bazel:3:11: in deps attribute of py_library rule //pylib:helpers: '//tools/wc:wc' does not have mandatory providers: 'PyInfo' or 'CcInfo'. Since this rule was created by the macro 'py_library', the error might have been caused by the macro implementation

Read these errors as: "deps means link or import this code, and this target is not code in my language". The "Since this rule was created by the macro" sentence is noise: go_binary and py_library are macros wrapping the real rules, and Bazel mentions it on every error.

Two different fixes, depending on what you meant:

  • You wanted to call the code. Code is not shared across languages through deps. Depend on a library in your own language (perhaps a Go port next to the Python one), or share data, a CLI, or generated code (M08) instead.
  • You wanted to run the program. Then it is a run-time file: put it in data. data accepts any target, in any language, because it requires no provider. That is the next section.

Try it: build, read the error, then fix the BUILD file so the Go binary depends only on Go code and the Python test gets the binary through data.

Remember: deps carries a language's provider (GoInfo, PyInfo) and stays within one language. data carries files and crosses any boundary.

A Python test that runs a Go tool

Testing a CLI from Python usually means subprocess.run(["wc", ...]) and hoping the right wc is on PATH, built from the current source. In CI that means a "build the tool first" step someone must remember to keep in sync.

Under Bazel the Go binary is just a run-time file of the test. Three pieces wire it up:

load("@rules_python//python:defs.bzl", "py_test")

py_test(
    name = "wc_test",
    srcs = ["wc_test.py"],
    data = ["//tools/wc"],                                   # 1. ship the binary
    env = {"WC_BIN": "$(rlocationpath //tools/wc)"},         # 2. tell the test its runfiles path
    deps = ["@rules_python//python/runfiles"],               # 3. the library that resolves it
)
import os
import subprocess
import unittest

from python.runfiles import runfiles


def wc_path() -> str:
    path = runfiles.Create().Rlocation(os.environ["WC_BIN"])
    assert path is not None, "WC_BIN is not a runfile; is //tools/wc in data?"
    return path


class WcTest(unittest.TestCase):
    def test_counts_stdin(self) -> None:
        out = subprocess.run([wc_path()], input="a b\nc\n", capture_output=True, text=True, check=True)
        self.assertEqual(out.stdout, "2 lines, 3 words\n")

    def test_counts_arguments(self) -> None:
        out = subprocess.run([wc_path(), "to be or", "not to be"], capture_output=True, text=True, check=True)
        self.assertEqual(out.stdout, "2 lines, 6 words\n")


if __name__ == "__main__":
    unittest.main()
  1. data = ["//tools/wc"] builds the Go binary and puts it in the test's runfiles tree. The binary must be visible to //tests, as for any dependency.
  2. $(rlocationpath //tools/wc) is a make variable: Bazel replaces it, while analyzing the test, with the binary's runfiles path. Here it expands to _main/tools/wc/wc_/wc. env hands that string to the test as an environment variable.
  3. Rlocation() from the rules_python runfiles library (M03) turns the runfiles path into a real path on disk, from any working directory.
//tests:wc_test                                                          PASSED in 0.8s
Executed 1 out of 1 test: 1 test passes.

Why not hard-code the path?

You could write Rlocation("_main/tools/wc/wc_/wc"). It works, but it bakes rules_go's private output layout (that wc_/ directory) into your Python. The obvious guess, _main/tools/wc/wc, is wrong, and it fails in a confusing way. The rules_python library, given a well-formed path under _main/, returned a path to a file that does not exist, and subprocess failed (paths shortened):

ERROR: test_counts (__main__.WcTest.test_counts)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "<output_base>/sandbox/linux-sandbox/29/execroot/_main/bazel-out/k8-fastbuild/bin/tests/wc_test.runfiles/_main/tests/wc_test.py", line 11, in test_counts
    out = subprocess.run([wc], input="a b\nc\n", capture_output=True, text=True, check=True)
  ...
FileNotFoundError: [Errno 2] No such file or directory: '<output_base>/sandbox/linux-sandbox/29/execroot/_main/bazel-out/k8-fastbuild/bin/tests/wc_test.runfiles/_main/tools/wc/wc'

$(rlocationpath) asks the Go rules where they put the file, so your test never needs to know. It is the documented, current pattern for "a test runs a tool". The variable also has a safety check: it only accepts a label the target already depends on. Drop the data line and analysis fails:

ERROR: /home/claude/bazel-practicum/build/scratch-m07/ws/tests/BUILD.bazel:3:8: in env[WC_BIN] attribute of py_test rule //tests:wc_test: label '//tools/wc:wc' in $(location) expression is not a declared prerequisite of this rule. Since this rule was created by the macro 'py_test', the error might have been caused by the macro implementation

args = ["$(rlocationpath //tools/wc)"] passes the same string as sys.argv[1] instead. Real run: argv[1] = _main/tools/wc/wc_/wc. Use env when the test framework owns argv (unittest and pytest both parse it), args for a plain script.

One graph, one cache

Here is the payoff. This workspace has four tests: the Go unit test, an external Go test, and two Python tests that run wc (the second uses args). After editing only tools/wc/main.go, a change to an error message:

//ext:ext_test                                                  (cached) PASSED in 0.0s
//textutil:textutil_test                                        (cached) PASSED in 0.1s
//tests:wc_args_test                                                     PASSED in 0.4s
//tests:wc_test                                                          PASSED in 0.5s
Executed 2 out of 4 tests: 4 tests pass.

Bazel re-ran exactly the Python tests downstream of the Go binary. The Go tests did not depend on main.go, so their results came from the cache. It can go further still: appending a comment to the end of count.go left all four tests (cached). Actions are keyed on input content, so when a recompiled package comes out the same, nothing downstream runs again.

The simulator checks that //tools/wc is visible and is a valid data dependency, but it does not expand $(rlocationpath) in env or args, so it misses the "not a declared prerequisite" error. It also prints bazel-bin/tools/wc/wc for bazel run, where real rules_go uses wc_/wc. Trust the real output above.

Predict, then run: which targets does the Python test reach, and which of them are Go?

A data edge is a real dependency edge: deps(...) follows it, and so does rdeps. That is how Bazel knew to re-run the Python test.

The other direction

Go code can consume what Python produces, too, but not through deps. The usual pattern is a Python program that generates a file (a table, a config, Go source) and a Go target that compiles or embeds it. That needs generated files, which arrive in M08.

Remember: to run a tool from a test: data = ["//tool"], pass $(rlocationpath //tool) in env or args, resolve it with Rlocation(). Never guess a rule set's output path.

Gazelle and third-party Go modules (a preview)

By now you may be thinking: every Go import maps to exactly one deps label, and the package line decides embed versus deps. A program could write these BUILD files. One does.

Gazelle is a BUILD file generator from the rules_go authors. It reads your Go sources and writes or updates go_library, go_binary, and go_test targets, including importpath, deps, and embed. It has a Python extension too (mentioned in M03), which writes py_library deps from your import statements. In large Go repositories almost nobody writes Go BUILD files by hand; they run Gazelle and review the diff.

Third-party Go modules (anything in a go.mod require block) come in through Gazelle's go_deps module extension, which reads go.mod and go.sum and creates one repository per module, much like pip.parse does for PyPI in M04. You already have Gazelle in your dependency graph: rules_go 0.65.0 depends on gazelle 0.51.3, which is why bazel mod lists it.

This module writes Go BUILD files by hand on purpose: you cannot review what a generator writes until you can write it yourself. Level 2 covers Gazelle and go_deps in depth. Everything here is standard library only.

Teams that adopt Gazelle usually add a CI check that runs it and fails if the BUILD files change, the same way they check formatting with buildifier. Hand edits and generated edits then never drift apart.

Remember: Gazelle generates Go (and Python) BUILD files from source; go_deps brings in go.mod dependencies. Both are Level 2 topics.

Exercises run in the simulator: it checks rules, labels, providers, and visibility. It cannot compile Go, so the lab afterwards proves the code really builds, passes its tests, and runs from Python.

The greet directory has greet.go (package greet, with an exported Hello function) and greet_test.go (also package greet). The cmd/hello directory has main.go, which does import "example.com/practicum/greet". Neither BUILD file declares anything yet.

  • //greet:greet: a go_library with importpath = "example.com/practicum/greet", usable from //cmd/hello.
  • //greet:greet_test: a go_test for the internal test file.
  • //cmd/hello:hello: a go_binary that uses the library.
Hint

Load go_library and go_test in greet/BUILD.bazel, and go_binary in cmd/hello/BUILD.bazel. The library needs importpath and a visibility that admits //cmd/hello. The test file starts with package greet, so it embeds the library.

Show solution 
load("@rules_go//go:def.bzl", "go_library", "go_test")

go_library(
    name = "greet",
    srcs = ["greet.go"],
    importpath = "example.com/practicum/greet",
    visibility = ["//cmd/hello:__pkg__"],
)

go_test(
    name = "greet_test",
    srcs = ["greet_test.go"],
    embed = [":greet"],
)
load("@rules_go//go:def.bzl", "go_binary")

go_binary(
    name = "hello",
    srcs = ["main.go"],
    deps = ["//greet"],
)

With real Bazel, bazel run //cmd/hello prints Hello, Bazel!. Without the importpath, the simulator is satisfied but the real compile fails with "missing strict dependencies".

With real Bazel, bazel test //... fails to compile //money:money_test with undefined: Cents, a function defined in money.go.

The test file starts with package money. Meanwhile //money:report_test, an external test in package money_test, compiles fine. Fix the broken target without touching the working one or any Go file.

Hint

undefined: Cents inside a package money test means the test was compiled as a separate package from money.go. Which attribute compiles another library's sources into this target?

Show solution

tests/slug_test.py (read-only) runs the Go tool //tools/slug and checks its output. It finds the binary with runfiles.Create().Rlocation(os.environ["SLUG_BIN"]). Wire it up:

  • The test ships the Go binary as a run-time file.
  • The test's environment sets SLUG_BIN to the binary's runfiles path, computed by Bazel (do not hard-code it).
  • The test depends on the rules_python runfiles library.
  • bazel build //... succeeds.
Hint

Three attributes on the py_test: data, env, and deps. Then build: //tools/slug is private to its package, so it also needs a visibility that admits //tests.

Show solution 
load("@rules_python//python:defs.bzl", "py_test")

py_test(
    name = "slug_test",
    srcs = ["slug_test.py"],
    data = ["//tools/slug"],
    env = {"SLUG_BIN": "$(rlocationpath //tools/slug)"},
    deps = ["@rules_python//python/runfiles"],
)
load("@rules_go//go:def.bzl", "go_binary")

go_binary(
    name = "slug",
    srcs = ["main.go"],
    visibility = ["//tests:__pkg__"],
)

Real Bazel expands SLUG_BIN to _main/tools/slug/slug_/slug. Forget data and real Bazel stops at analysis: "label '//tools/slug:slug' in $(location) expression is not a declared prerequisite of this rule".

The rates package has a Python library and a Go library side by side. Someone wired the consumers by guessing, and bazel build //... now fails with two provider errors (run it under "Try commands").

Quiz

Recap

  • A second language is where Bazel shines: one graph, one cache, and one bazel test //... across Go and Python, with precise reruns.
  • Go basics: one directory is one package; capitalized names are exported; programs are package main with func main(); tests are TestXxx(t *testing.T) in _test.go files.
  • bazel_dep(name = "rules_go", version = "0.65.0") plus go_sdk.download(version = "1.25.3") gives a hermetic Go; no use_repo, no system Go.
  • go_library needs an importpath; every import of your own code needs a matching deps entry, or the compile fails with "missing strict dependencies".
  • Internal tests (package X) embed the library; external tests (package X_test) list it in deps.
  • deps is per language (GoInfo, PyInfo); data crosses languages.
  • To run a Go tool from Python: data = ["//tool"], env = {"BIN": "$(rlocationpath //tool)"}, and Rlocation() from the runfiles library.
  • Gazelle generates Go and Python BUILD files; go_deps brings in third-party Go modules. Both come in Level 2.
