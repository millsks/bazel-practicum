Configuration, Flags & select()

The same BUILD files have to produce a debug build on your laptop, an optimized build in CI, and a production build with production settings. Bazel does this with configurations: sets of build options that are decided before anything runs. This module shows how to set them in .bazelrc, define your own flags, branch on them with select(), and describe the machines you build for with platforms.

⏱ ~2.5 hoursPrerequisites: M05

  • Organize a .bazelrc with common, build, and test lines, named --configs, and a try-imported personal file
  • Write config_settings on values, define_values, and flag_values, and choose attribute values with select()
  • Diagnose "doesn't match this configuration" and "Illegal ambiguous match" errors, and know which attributes cannot be configured

  • Describe target machines with constraints and platform(), and skip targets with target_compatible_with
  • Use cquery to see what a select() resolves to, and keep environment variables out of your build

What a configuration is

A Python project switches behavior at run time. Django reads DJANGO_SETTINGS_MODULE, a Flask app reads os.environ["APP_ENV"], and pytest reads pytest.ini and its command line. The same installed code behaves differently depending on what is set when it starts.

Bazel switches behavior at build time. A configuration is the full set of build options that can change what a build produces: the compilation mode, the target platform, every custom flag, and many more. Bazel fixes the configuration before analysis, then builds every target in it.

The most common option is --compilation_mode, usually written -c. It has three values:

ModeMeaningTypical use
fastbuildThe default: build quickly, little optimizationDay-to-day development
dbgKeep debug informationRunning native code under a debugger
optOptimize, strip asserts in C/C++Release builds and benchmarks

For pure Python code the mode changes little by itself. It matters for compiled extensions (C, Go), and above all it is something your BUILD files can branch on. Anything else is rejected before Bazel starts:

ERROR: While parsing option -c fast: Not a valid compilation mode: 'fast' (should be fastbuild, dbg or opt)

Configurations are directories

Because different options can produce different files, Bazel keeps each configuration's outputs apart. Build the same target twice, once with -c opt and once without, and look in bazel-out:

pixi run bazel build //app:banner
pixi run bazel build //app:banner -c opt
pixi run bazel build //app:banner -c dbg
ls bazel-out
_tmp
k8-dbg
k8-fastbuild
k8-opt
stable-status.txt
volatile-status.txt

The directory name is <cpu>-<mode>. k8 is Bazel's historical name for x86-64 Linux; other machines show another prefix. Switching modes does not delete the other directory, so switching back is fast. bazel-bin points into whichever configuration you built last.

Configurations have IDs

Every configuration also has a hash. You saw one already in M03's analysis error, Analysis of target '//app:server' (config: a7a71fd) failed. bazel cquery (configured query, see below) prints it after each target:

$ bazel cquery //app:banner
//app:banner (a7a71fd)
$ bazel cquery //app:banner -c opt
//app:banner (bf3a44e)

Same target, two configurations, two hashes. bazel config lists the configurations the server currently holds, and bazel config <hash> dumps every option in one (hundreds of lines; search it for the option you care about):

Available configurations:
04bf134dfa57115b01daa56bd3a30421a6e74b1819e002496a26c94ed0087067 k8-opt-exec (exec)
3030ed4c810cf3435d066294fa495e650fe75173e4b4ef410ea56cb683458569 fastbuild-noconfig (test-trimmed)

Note k8-opt-exec (exec): tools that run during the build (compilers, code generators) are built in a separate exec configuration, optimized by default, even when your own code is fastbuild.

Changing an option also costs something. Bazel keeps one analyzed graph in memory, and a new configuration throws it away:

WARNING: Build option --compilation_mode has changed, discarding analysis cache (this can be expensive, see https://bazel.build/advanced/performance/iteration-speed).

That warning is why teams put their usual options in a file instead of typing them differently each time. Next section.

Remember: a configuration is the set of options that can change outputs. Each one gets its own bazel-out/<cpu>-<mode> tree and a hash that cquery prints.

.bazelrc: options you do not want to type

You keep pytest options in [tool.pytest.ini_options] so nobody has to remember -ra --strict-markers. Pixi tasks do the same for whole commands.

A .bazelrc file holds default options for Bazel commands. Each line starts with the command it applies to, followed by options exactly as you would type them:

# Every command that accepts the option
common --//config:verbose=false

# build, and every command that inherits from it
build --compilation_mode=fastbuild

# Only when you pass --config=prod
build:prod --//config:env=prod
build:prod -c opt

# Only for bazel test
test --test_output=errors

# Personal settings, if the file exists
try-import %workspace%/user.bazelrc

Which lines apply to which command

Commands inherit options from each other. test, run, and cquery all build, so they read build lines too. common lines apply to every command (Bazel skips options a command does not support). query does not build, so it does not read build lines.

CommandReads lines for
buildcommon, build
runcommon, build, run
testcommon, build, test
cquerycommon, build, test, cquery
querycommon, query

That cquery row is easy to miss: a line test --//config:env=prod changed what bazel cquery resolved in our test workspace, because cquery inherits from test.

Named configs: --config=name

A line like build:prod ... is a named config. It does nothing until you pass --config=prod; then Bazel splices those options in at that point on the command line. One short flag stands for a bundle of options, and CI and laptops can share the same bundles.

Pass --announce_rc to see what Bazel read. Trimmed to the workspace file's lines (this machine's personal rc lines are left out):

INFO: Reading rc options for 'build' from /…/ws/.bazelrc:
  Inherited 'common' options: --//config:verbose=false
INFO: Reading rc options for 'build' from /…/ws/.bazelrc:
  'build' options: --compilation_mode=fastbuild
INFO: Found applicable config definition build:prod in file /…/ws/.bazelrc: --//config:env=prod -c opt

Asking for a config nobody defined is an error:

ERROR: Config value 'qa' is not defined in any .rc file

You get the same error from bazel query //... --config=prod when only build:prod exists, because query never reads build lines. Write common:prod if a config must work with query too.

Which value wins

When the same option is set several times, the last one wins. Bazel lays the options out in this order:

  1. common lines, then lines for the inherited commands (build, then test...), then the command's own lines. A build line beats a common line for the same option, even if the common line comes later in the file.
  2. Within one section, later lines beat earlier lines.
  3. The command line comes last, so it beats every rc file. A --config=prod expands where you wrote it: --config=prod --//config:env=staging ends with staging, while --//config:env=staging --config=prod ends with prod. Both verified in Bazel 9.3.2.

Which files

Bazel reads up to three rc files, in this order: the system file (/etc/bazel.bazelrc on Linux), the workspace file (.bazelrc next to MODULE.bazel), and the home file (~/.bazelrc). Bazel 9.3.2's own startup log lists them:

Looking for the following rc files: /etc/bazel.bazelrc,/…/ws/.bazelrc,/root/.bazelrc

So your personal ~/.bazelrc is read after the workspace file and can override it. Commit the workspace file; it is part of the build.

For settings that belong to one person but one repository (a disk cache path, --config=mine), teams add try-import %workspace%/user.bazelrc to the workspace file and list user.bazelrc in .gitignore. %workspace% expands to the workspace root. try-import skips a missing file silently; plain import stops Bazel cold:

[FATAL 02:56:10.534 src/main/cpp/blaze.cc:1275] Nonexistent path in import declaration in config file '/…/ws/.bazelrc': 'import %workspace%/missing.bazelrc' (are you in your source checkout/WORKSPACE?)

Predict what the first command prints, then try the others. The .bazelrc tab is editable.

Common team habits: a build:ci config used only by CI (--config=ci in the pipeline), test --test_output=errors for everyone, common --enable_platform_specific_config so build:linux and build:macos lines apply automatically per OS, and try-import %workspace%/user.bazelrc as the last line. Keep secrets out of every rc file.

Remember: .bazelrc lines are command[:name] options. Commands inherit (test and cquery read build; query does not), named configs expand where --config appears, and the last value wins.

config_setting and select()

In Python you would write if settings.DEBUG: ... and decide while the program runs. In a BUILD file there is no running program and no if statement at the top level. The branching has to be a value Bazel can resolve itself, once the configuration is known.

That value is select(). It maps conditions to attribute values, and Bazel picks the branch whose condition matches the current configuration. A condition is a label, usually of a config_setting: a native rule (no load() needed) that matches when a set of options has particular values.

config_setting(
    name = "opt",
    values = {"compilation_mode": "opt"},
    visibility = ["//visibility:public"],
)
py_binary(
    name = "server",
    srcs = ["server.py"],
    data = select({
        "//config:opt": ["logging_quiet.ini"],
        "//conditions:default": ["logging_debug.ini"],
    }),
)

//conditions:default is the built-in "nothing else matched" branch. A config_setting matches when all of its entries match. It has three main ways to say what to match:

values

Built-in options, named without dashes: {"compilation_mode": "opt"}.

define_values

Old-style --define key=value pairs: {"env": "prod"}. See why to avoid it.

flag_values

Custom flags by label: {"//config:env": "prod"}. The modern choice.

A fourth, constraint_values, matches the target platform and comes up with platforms.

Predict what the first command returns, then run them all. Notice that query and cquery disagree.

When nothing matches

Leave out //conditions:default and build in a configuration that matches no condition. Analysis fails, and the message lists every condition it checked:

ERROR: /…/ws/sel/BUILD.bazel:1:10: configurable attribute "srcs" in //sel:nodefault doesn't match this configuration. Would a default condition help?

Conditions checked:
 //config:prod
 //config:staging

To see a condition's definition, run: bazel query --output=build <condition label>.

This instance of //sel:nodefault has configuration identifier a7a71fd. To inspect its configuration, run: bazel config a7a71fd.

For more help, see https://bazel.build/docs/configurable-attributes#faq-select-choose-condition.
ERROR: Analysis of target '//sel:nodefault' failed; build aborted

Sometimes failing is right: a target that only makes sense in production. Then say why, with no_match_error:

filegroup(
    name = "custommsg",
    srcs = select(
        {"//config:prod": ["prod.txt"]},
        no_match_error = "Set --//config:env=prod; this target only exists for production.",
    ),
)
ERROR: /…/ws/sel/BUILD.bazel:9:10: configurable attribute "srcs" in //sel:custommsg doesn't match this configuration: Set --//config:env=prod; this target only exists for production.

When two conditions match

Conditions are not checked in order. If two match, Bazel does not take the first; it fails, unless one condition is more specialized (it checks everything the other checks, and more) or both branches have the same value. With --config=prod meaning "env=prod and -c opt", this select has two matches:

filegroup(
    name = "ambiguous",
    srcs = select({
        "//config:prod": ["prod.txt"],   # flag_values = {":env": "prod"}
        "//config:opt": ["opt.txt"],     # values = {"compilation_mode": "opt"}
        "//conditions:default": ["dev.txt"],
    }),
)
ERROR: /…/ws/sel/BUILD.bazel:17:10: Illegal ambiguous match on configurable attribute "srcs" in //sel:ambiguous:
//config:prod
//config:opt
Multiple matches are not allowed unless one is unambiguously more specialized or they resolve to the same value. See https://bazel.build/reference/be/functions#select.
ERROR: Analysis of target '//sel:ambiguous' failed; build aborted

The fix is a condition for the overlap. A config_setting that sets both entries is more specialized than either one alone, so Bazel picks it:

config_setting(
    name = "prod_opt",
    values = {"compilation_mode": "opt"},
    flag_values = {":env": "prod"},
)

With :prod_opt added to the select, --config=prod resolves to its branch, --//config:env=prod alone to :prod's, and -c opt alone to :opt's (all three verified with cquery).

Combining selects

A select() can be added to a list, or to another select, with +. Each select is resolved on its own and the results are concatenated. This keeps the shared part out of every branch:

filegroup(
    name = "concat",
    srcs = ["common.txt"] + select({
        "//config:prod": ["prod.txt"],
        "//conditions:default": [],
    }),
)
$ bazel cquery 'labels(srcs, //sel:concat)' --//config:env=prod
//sel:common.txt (null)
//sel:prod.txt (null)
$ bazel cquery 'labels(srcs, //sel:concat)'
//sel:common.txt (null)

((null) is the configuration of a source file: files on disk are the same in every configuration.) You cannot put a select() inside another select()'s branch, and you cannot index into one: it is an opaque value until analysis.

Attributes that cannot be configured

Bazel must know some attributes while loading, before any configuration exists: the target's name, its visibility, its tags (which bazel test filters on), a genrule's outs, and a few more. A select there is a loading error:

ERROR: /…/ws/nc/BUILD.bazel:1:10: //nc:files: attribute "visibility" is not configurable
ERROR: /…/ws/nc/BUILD.bazel:2:8: //nc:t: attribute "tags" is not configurable

Why must tags be known before configuration? Think about bazel test //... --test_tag_filters=-slow from M05: which phase decides which tests exist?

Remember: select() picks one branch per configuration; give it a //conditions:default or a no_match_error. Two matching conditions are an error unless one is more specialized. name, visibility, tags, and outs cannot be selected.

Your own flags: build settings

Bazel's built-in options cover compilers and platforms, not "which environment am I deploying to?". For that you define a build setting: a target whose value comes from the command line. bazel_skylib's common_settings.bzl provides the usual ones:

load("@bazel_skylib//rules:common_settings.bzl", "bool_flag", "string_flag")

string_flag(
    name = "env",
    build_setting_default = "dev",
    values = ["dev", "staging", "prod"],
)

bool_flag(
    name = "verbose",
    build_setting_default = False,
)

config_setting(
    name = "prod",
    flag_values = {":env": "prod"},
    visibility = ["//visibility:public"],
)

config_setting(
    name = "verbose_on",
    flag_values = {":verbose": "true"},
)

The flag's name on the command line is its label, with -- in front:

pixi run bazel run //app:banner --//config:env=prod
pixi run bazel build //... --//config:verbose          # bool: same as =true
pixi run bazel build //... --no//config:verbose        # bool: false

In flag_values, a bool_flag's value is written as a string. Bazel 9.3.2 accepted both "true" and "True" in our test; use lowercase "true". The command line also accepts =1 and =0, but nothing else:

ERROR: While parsing option //config:verbose=maybe: 'maybe' is not a boolean

Why not --define?

Older repositories use --define env=prod with config_setting(define_values = {"env": "prod"}). It works, but every --define key is just a string. Compare what happens with a typo:

--define=enviroment=prod (misspelled): silently ignored. The build succeeds with the default branch:

//app:dev.txt (null)

--//config:enviroment=prod (misspelled): the label does not exist, and Bazel stops:

ERROR: //config:enviroment :: Error loading option //config:enviroment: no such target '//config:enviroment': target 'enviroment' not declared in package 'config' defined by /…/ws/config/BUILD.bazel

A string_flag with values also rejects values nobody planned for. This is a Starlark fail() inside bazel_skylib, so it arrives with a short traceback:

ERROR: /…/ws/config/BUILD.bazel:3:12: in string_flag rule //config:env:
Traceback (most recent call last):
	File "/…/external/bazel_skylib+/rules/common_settings.bzl", line 157, column 13, in _string_impl
		fail("Error setting " + _no_at_str(ctx.label) + ": invalid value '" + value + "'. Allowed values are " + str(allowed_values))
Error in fail: Error setting //config:env: invalid value 'qa'. Allowed values are ["dev", "staging", "prod"]
ERROR: /…/ws/config/BUILD.bazel:3:12: Analysis of target '//config:env' (config: ffb1666) failed
ERROR: /…/ws/app/BUILD.bazel:3:10: errors encountered resolving select() keys for //app:banner
ERROR: Analysis of target '//app:banner' failed; build aborted

Build settings are also ordinary targets. They have visibility, show up in bazel query, and can be read by your own rules (later in the course). --define has none of that.

The simulator accepts any flag label and any value: a misspelled --//config:... or an unlisted value quietly selects the default branch instead of failing. Real Bazel reports both errors above; Lab 1 checks the invalid value one.

Try it. Run the commands, then change prod to staging in the second one.

Unlike -c opt, changing a flag like --//config:env on the command line did not create a new bazel-out directory in Bazel 9.3.2: cquery --output=files still printed bazel-out/k8-fastbuild/bin/app/banner. Outputs for dev and prod replace each other there; the action cache still makes switching back cheap.

Remember: declare flags with string_flag/bool_flag, set them with --//pkg:name=value, and match them with flag_values. Typos and unknown values fail loudly, which --define never does.

Platforms and constraints

A wheel's file name says where it runs: cp313-cp313-manylinux_2_28_x86_64 or macosx_11_0_arm64. pip compares those tags with your machine and picks a match. Python code checks sys.platform at run time.

Bazel describes machines the same way, with three building blocks:

constraint_setting

A dimension a machine can vary in: operating system, CPU, "has a GPU".

constraint_value

One choice in a dimension: linux for the OS setting, arm64 for CPU.

platform

A named machine: a list of constraint values, at most one per setting.

The common settings already exist in the platforms module (version 1.1.0 here): @platforms//os:linux, @platforms//os:macos, @platforms//os:windows, @platforms//cpu:x86_64, @platforms//cpu:arm64, and more. @platforms//host is the machine you are on. You add your own settings for anything else:

constraint_setting(
    name = "accelerator",
    default_constraint_value = ":cpu_only",
)

constraint_value(name = "cpu_only", constraint_setting = ":accelerator")
constraint_value(name = "gpu", constraint_setting = ":accelerator")

platform(
    name = "gpu_host",
    parents = ["@platforms//host"],   # everything the host has...
    constraint_values = [":gpu"],      # ...plus a GPU
)

platform(
    name = "macos_arm",
    constraint_values = [
        "@platforms//os:macos",
        "@platforms//cpu:arm64",
    ],
)

--platforms=//platforms:macos_arm sets the target platform: the machine the outputs are for. It defaults to the host. Like any option, it is part of the configuration.

The sandbox's host is Linux, so the second command picks launch.sh. On a Mac, the same command would pick launch_mac.sh: the default target platform follows the machine.

target_compatible_with: "this only builds there"

Some targets make no sense on some platforms: a Windows-only test, a CUDA kernel. Mark them with target_compatible_with, a list of constraint values the target platform must have:

py_test(
    name = "train_test",
    srcs = ["train_test.py"],
    target_compatible_with = ["//platforms:gpu"],
)

On an incompatible platform, a wildcard like //... skips the target instead of failing. Tests show up as SKIPPED:

//gpu:cpu_math_test                                             (cached) PASSED in 0.5s
//gpu:train_test                                                        SKIPPED
Executed 0 out of 2 tests: 1 test passes and 1 was skipped.

Naming the target explicitly is an error, and so is depending on it. The dependency chain points at the constraint that was not met:

ERROR: Analysis of target '//platforms_demo:uses_cuda' failed; build aborted: Target //platforms_demo:uses_cuda is incompatible and cannot be built, but was explicitly requested.
Dependency chain:
    //platforms_demo:uses_cuda (a7a71f)
    //platforms_demo:cuda_only (a7a71f)   <-- target platform (@@platforms//host:host) didn't satisfy constraint //platforms_demo:has_gpu
ERROR: Build did NOT complete successfully

Here uses_cuda had no target_compatible_with of its own; it became incompatible because it depends on a target that is. Incompatibility flows up the graph. With --platforms=//platforms_demo:linux_gpu, the same build succeeds.

The simulator does not model target_compatible_with: it accepts the attribute but never skips a target or reports one as incompatible. Every output above is from real Bazel, and Lab 2 grades it.

Remember: constraint settings are dimensions, constraint values are choices, platforms are named combinations. --platforms picks the target platform; select() can branch on it, and target_compatible_with makes wildcards skip targets that cannot work there.

query vs cquery

You have seen the difference in every sandbox so far. bazel query works on the graph as loaded, before any configuration exists. It cannot know which branch of a select() applies, so it reports all of them:

$ bazel query 'labels(data, //app:banner)'
//app:dev.txt
//app:prod.txt
//app:staging.txt

bazel cquery runs after analysis, in the configuration your flags (and .bazelrc) describe, and reports only the branch that applies, with each target's configuration hash:

$ bazel cquery 'labels(data, //app:banner)' --config=prod
//app:prod.txt (null)
$ bazel cquery 'deps(//app:banner, 1)' --output=label_kind --config=prod
py_binary rule //app:banner (eaa8dce)
source file //app:prod.txt (null)
source file //app:banner.py (null)

(The second command's output is trimmed to the //app lines. A configured graph also contains toolchains and rules_python's internal settings.)

Which one to use:

  • query for "what could this depend on?": impact analysis, finding every user of a library across all configurations. It is fast and needs no flags.
  • cquery for "what does this depend on in this build?": debugging a select(), checking what --config=prod really ships.

Two cquery --output formats are worth knowing now. --output=files prints the output files a target produces in that configuration, which shows the configuration directory:

$ bazel cquery //app:banner --output=files
bazel-out/k8-fastbuild/bin/app/banner
app/banner.py

--output=build prints the target as a BUILD rule with every select() already resolved. Compare query --output=build, which keeps the select (trimmed):

py_binary(
  name = "banner",
  ...
  data = ["//app:prod.txt"],
  deps = ["@rules_python//python/runfiles:runfiles"],
  srcs = ["//app:banner.py"],
)
  data = select({"//config:prod": ["//app:prod.txt"], "//config:staging": ["//app:staging.txt"], "//conditions:default": ["//app:dev.txt"]}),

The simulator's cquery resolves select() like Bazel, but prints labels without the configuration hash, and supports --output=label, label_kind, and package only.

Predict the first two outputs before you run them. Notice that the select's condition, //config:s3, is a dependency too, in both answers. (Real Bazel's lists are longer: they include the Python toolchain and other implicit dependencies, which the simulator leaves out.)

Selecting deps like this is how one binary gets a different implementation per configuration. The Python code imports both names behind a try/except ImportError, or the two libraries provide the same module path.

Remember: query shows every branch of every select; cquery shows the one your flags choose. Reach for cquery whenever the question includes "with these flags".

Environment variables are not configuration

Twelve-factor apps read configuration from the environment: DATABASE_URL, API_URL, DEBUG=1. Build scripts often do too: a setup.py that checks os.environ to decide whether to compile an extension.

That is fine for running a program. It is a problem for building one. Bazel caches an action by its declared inputs (M02). If a build step read $API_URL from your shell, its output would depend on something Bazel does not track: two machines would produce different files under the same cache key. That is exactly the non-hermetic build Bazel exists to prevent.

So, by default, actions and tests do not see your shell's variables. In this experiment we exported API_URL=https://example.test, then ran a test that prints it and a genrule that writes it to a file:

genrule(
    name = "stamp",
    outs = ["stamp.txt"],
    cmd = "echo \"API_URL=$${API_URL:-unset}\" > $@",
)
CommandThe test printedstamp.txt held
no flagAPI_URL = <not set>API_URL=unset
--test_env=API_URLAPI_URL = https://example.test(not a test)
--action_env=API_URLAPI_URL = https://example.testAPI_URL=https://example.test
  • --test_env=NAME passes a variable into tests only. Use it for things like a test database URL. Tests that read it will rerun when its value changes.
  • --action_env=NAME passes a variable into build actions (and, as the table shows, tests). Its value becomes part of every affected action's key, so changing it reruns them. Use it rarely, for things like PATH for a legacy tool.
  • Either form also takes a fixed value: --test_env=API_URL=http://localhost:8000, which is reproducible and fine in .bazelrc.

If what you want is "a production build" rather than "a build that read my shell", that is a build setting: --//config:env=prod, visible in the graph, selectable, and part of the configuration.

Do not try to read a .bazelrc value or a flag from Python with os.environ. Flags exist at build time; your program runs later. To hand a build-time choice to run-time code, select a data file (as in Lab 1), select a deps library, or set env on the target with a select.

Remember: build-time choices are flags and configurations, never ambient environment variables. --test_env is for tests; --action_env leaks the environment into the cache key, so use it sparingly.

Quiz

Recap

  • A configuration is the set of options that can change outputs. Each gets a bazel-out/<cpu>-<mode> tree (for -c) and a hash that cquery prints.
  • -c is fastbuild (default), dbg, or opt.
  • .bazelrc lines are command[:name] options. test, run, and cquery read build lines; query does not. --config=name expands in place; the last value wins.
  • Workspace .bazelrc is committed; try-import %workspace%/user.bazelrc holds personal settings. ~/.bazelrc is read after the workspace file.
  • config_setting matches on values, define_values, flag_values, or constraint_values; select() picks a branch per configuration.
  • Give every select a //conditions:default or a no_match_error. Overlapping conditions need a more specialized one.
  • name, visibility, tags, and outs are not configurable.
  • string_flag/bool_flag from bazel_skylib make typed, checked flags: --//config:env=prod. Prefer them to --define.
  • Platforms are named sets of constraint values; --platforms sets the target platform. target_compatible_with makes wildcards skip a target, and explicit requests fail.
  • query shows every select branch; cquery shows the one your flags choose.
  • Shell variables do not reach actions or tests unless you pass --action_env or --test_env.
