Testing at Scale

With pytest, "run the tests" means "run all of them, every time". In a monorepo with thousands of tests that stops working. Bazel treats every test as a cached action with a declared size, tags, and environment, so bazel test //... runs only what your change can affect. This module teaches you to control which tests run, read what they did, and keep them fast and trustworthy.

⏱ ~2 hoursPrerequisites: M04
  • Explain why an unchanged test reports (cached) PASSED, and when to bypass the cache
  • Give tests a size and timeout, and act on Bazel's "size is too big" hint
  • Select tests with tags, manual, --test_tag_filters, --test_size_filters, and test_suite
  • Find and read test.log and test.xml, and choose a --test_output mode
  • Write tests that respect the test environment: runfiles, TEST_TMPDIR, arguments, and filters
  • Detect flaky tests with --runs_per_test, and know what flaky = True and sharding really do
  • Keep test helpers out of production code with testonly

Tests are cached actions

pytest keeps no memory between runs. pytest --lf reruns last failures, but nothing tells pytest "you changed billing.py, so only these 40 tests can be affected". You choose a subset by hand, or you wait for all of them.

In Bazel, running a test is an action, just like compiling a file (M02). Its inputs are the test program, its runfiles (sources, dependencies, data files, the interpreter), the environment, and the test flags. Its outputs are the exit code and the log. If none of the inputs changed, Bazel already knows the result.

Run the tests of a workspace twice. The first line comes from a test that already passed earlier; the second ran now, because its inputs were new:

//calc:env_test                                                 (cached) PASSED in 0.3s
//calc:calc_test                                                         PASSED in 0.7s

Executed 1 out of 2 tests: 2 tests pass.

Executed 1 out of 2 is the headline. (cached) means the result was reused: the time shown is from the run that produced it. Now edit one library, calc/calc.py, and test four packages:

//app:app_test                                                  (cached) PASSED in 0.3s
//calc:env_test                                                 (cached) PASSED in 0.7s
//rd:read_test                                                  (cached) PASSED in 0.5s
//calc:calc_test                                                         PASSED in 0.3s
Executed 1 out of 4 tests: 4 tests pass.

Only //calc:calc_test depends on calc.py, so only it ran. Its neighbor //calc:env_test lives in the same package but does not depend on the library, so it stayed cached. This is the payoff of declaring deps precisely.

Bypassing the cache

Sometimes you want a real run anyway: you suspect the machine, or you are timing a test. Two spellings of the same flag force it:

pixi run bazel test //... --nocache_test_results
pixi run bazel test //... --cache_test_results=no    # same thing

The default, --cache_test_results=auto, caches passing results. It reruns a test that failed last time, and a test tagged external (see Tags), which is never cached.

Changing how you look at results does not invalidate them. --test_output=errors and --test_output=all both print (cached) PASSED for an unchanged test, and with all you see the cached log. A test whose behavior depends on something Bazel does not track (the clock, the network, a file outside the workspace) can be cached with a stale verdict. That is a bug in the test, and later sections show how to fix it.

The simulator never runs tests. Its bazel test prints which tests would run, after the loading and analysis phases, and says (would run) instead of PASSED. Selection (tags, sizes, suites, manual) is modeled exactly; results and caching need real Bazel and the labs.

Try it: which tests does bazel test //... select here, and which does //calc:all?

Remember: a test is an action keyed by its inputs. Unchanged inputs mean (cached) PASSED; --nocache_test_results forces a fresh run.

Size and timeout

pytest has no built-in timeout. A test that hangs on a socket hangs your CI job until something outside kills it. The pytest-timeout plugin exists because of that.

Every Bazel test has a size: small, medium (the default), large, or enormous. The size describes how heavy the test is, and it sets the default timeout. When the timeout passes, Bazel kills the test and reports TIMEOUT.

sizeDefault timeoutSeconds (TEST_TIMEOUT)Typical test
smallshort60Pure functions, no I/O beyond a temp file
mediummoderate300A local database, a subprocess, a few seconds of work
largelong900Several services, end-to-end flows
enormouseternal3600Rare: hour-long system tests

The seconds column is what a test actually received in its TEST_TIMEOUT environment variable under Bazel 9.3.2. You can set timeout on its own when a test is light but slow, for example size = "small", timeout = "long" gives 900 seconds.

py_test(
    name = "distance_test",
    size = "small",
    srcs = ["distance_test.py"],
    deps = [":geo"],
)

Only those four words are allowed. A typo is a loading error that stops the whole package:

ERROR: /work/practicum/bad/BUILD.bazel:4:8: In rule 'tiny_test', size 'tiny' is not a valid size.
ERROR: /work/practicum/bad/BUILD.bazel:4:8: In rule 'tiny_test', timeout 'illegal' is not a valid timeout.

What a timeout looks like

--test_timeout=N overrides every test's timeout for one run, which is handy to reproduce a hang quickly. A test that sleeps five seconds, run with a two-second limit:

INFO: Build completed, 1 test FAILED, 2 total actions
//sel:slow_test                                                         TIMEOUT in 2.0s
  /root/.cache/bazel/_bazel_root/…/execroot/_main/bazel-out/k8-fastbuild/testlogs/sel/slow_test/test.log

Executed 1 out of 1 test: 1 fails locally.

The last line of that test.log is -- Test timed out at 2026-11-09 08:48:36 UTC --.

The "size is too big" hint

You saw this line in M03, after every test run where a test had no size:

There were tests whose specified size is too big. Use the --test_verbose_timeout_warnings command line option to see which ones these are.

Bazel noticed a test finished far inside its timeout. Add the flag it suggests to find out which one:

//calc:calc_test                                                (cached) PASSED in 1.1s
//calc:env_test                                                 (cached) PASSED in 1.2s
  WARNING: //calc:env_test: Test execution time (1.2s excluding execution overhead) outside of range for MODERATE tests. Consider setting timeout="short" or size="small".

Why care, if it passes? Two reasons. A tight timeout catches a hang in one minute instead of five. And sizes let you choose tests by weight, as the next sandbox shows.

Predict which tests --test_size_filters=small selects. Remember the default size.

parse_test is still small even with a long timeout: the filter looks at size only (--test_timeout_filters filters by timeout). When a filter matches nothing, Bazel stops with ERROR: No test targets were found, yet testing was requested.

Remember: set size on every test; small is right for most unit tests. The size gives a default timeout (60, 300, 900, 3600 seconds) and a handle for --test_size_filters.

Tags and test filters

pytest has markers: @pytest.mark.slow on a function, then pytest -m "not slow". Markers live in the code and select individual test functions.

Bazel's equivalent is the tags attribute, a list of strings on the target. Any string works as a label for your own filters, like "slow" or "integration". A handful of tags also change what Bazel does:

TagEffect
manualWildcards (//..., :all) skip the target. It runs only when named explicitly or through a test_suite.
externalThe test talks to the outside world, so its result is never cached. It reran on every invocation in our checks.
exclusiveRun this test alone, with no other test in parallel. Still sandboxed in Bazel 9.
no-sandboxRun without the sandbox, directly in the execution root (local instead of linux-sandbox in the summary line). A last resort.
no-cache, no-remoteKeep the action out of the disk and remote caches. For tests, prefer external.

no-cache does not do what its name suggests for local test reruns. A test tagged no-cache still printed (cached) PASSED on its second run in our workspace, because the local test result cache is separate. Use external when a test's result must never be reused.

Choosing tests with --test_tag_filters

--test_tag_filters takes a comma-separated list. A plain tag means "has at least one of these"; a tag with - means "has none of these". Exclusions win.

pixi run bazel test //... --test_tag_filters=-slow,-external   # everyday run
pixi run bazel test //... --test_tag_filters=integration        # only integration tests

Filters only narrow what the target pattern already selected. Two consequences surprise people:

  • manual is not a filter. --test_tag_filters=manual does not select manual tests; real Bazel ignores a positive manual and runs the usual non-manual tests. Name a manual test explicitly, or put it in a suite.
  • A size counts as a tag here. --test_tag_filters=small selected the small tests in our workspace, exactly like --test_size_filters=small.

Tests only: --build_tests_only

bazel test //... also builds every non-test target the pattern matches. If an unrelated binary is broken, the build fails and the tests are skipped with NO STATUS:

ERROR: /work/practicum/bt/BUILD.bazel:3:10: //bt:tool: missing input file '//bt:tool.py'
ERROR: Build did NOT complete successfully
//bt:ok_test                                                          NO STATUS
Executed 0 out of 1 test: 1 was skipped.

--build_tests_only builds only what the selected tests need. The same command then passes:

INFO: Build completed successfully, 3 total actions
//bt:ok_test                                                             PASSED in 1.3s
Executed 1 out of 1 test: 1 test passes.

Many teams keep two habits: CI runs bazel test //... without --build_tests_only, so a broken binary fails the build; developers use it locally with tag and size filters for a fast loop. Lines like test --test_tag_filters=-external in .bazelrc (M06) make the everyday filter the default.

Predict which tests each command selects, then run them.

Remember: manual hides a target from wildcards; external disables result caching; --test_tag_filters narrows with any-of and none-of, but never adds manual tests back.

Grouping tests with test_suite

A test_suite is a native rule (no load needed) that names a group of tests. bazel test //billing:quick runs the group. It has two ways to choose members:

# 1. By tag: every non-manual test in this package that matches.
test_suite(
    name = "quick",
    tags = ["-slow"],
)

# 2. Explicitly: exactly these tests (or other suites), from any package.
test_suite(
    name = "nightly",
    tags = ["manual"],
    tests = [
        ":ledger_db_test",
        ":pdf_test",
        "//shipping:label_test",
    ],
)

With no tests attribute, a suite collects the package's tests, skipping manual ones, and tags filters them like --test_tag_filters. That form keeps itself up to date: a new non-slow test joins :quick automatically. With tests, it holds exactly what you list (and tags still filters that list, except the manual tag, which is about the suite itself).

Suites and manual tests

A suite that names a manual test runs it. That is the standard way to give manual tests a single entry point: bazel test //billing:nightly. The trap is the other direction: //... matches the suite itself, so a non-manual suite drags its manual members into every wildcard run. In our workspace a suite naming //sel:manual_test made bazel test //sel/... run it. Tag the suite manual too, as :nightly does above.

Only tests and suites may be members. Listing a library is an error:

ERROR: /work/practicum/bad/BUILD.bazel:5:11: in test_suite rule '//bad:suite': expecting a test or a test_suite rule but '//bad:lib' is not one.

bazel query 'tests(//billing:quick)' expands a suite into its tests without running anything. Try it, and predict the answer for :nightly first.

Remove tags = ["manual"] from :nightly and run bazel test //... again. Which test appears, and why would that hurt on a laptop without the ledger database?

Remember: a suite selects by tag (package tests, minus manual) or by explicit list. Explicit members run even if manual, so tag suites that hold manual tests manual as well.

Test output and logs

pytest prints everything to your terminal and, with --junitxml, writes a report CI can read.

Bazel runs tests in parallel, so it keeps their output out of your terminal by default. You choose how much to see with --test_output:

ValueWhat you see
summary (default)One status line per test and the path of each failing log.
errorsAlso the full log of every failing test. The everyday choice.
allThe log of every test, passing or failing (cached ones too).
streamedOutput live as the test runs. Bazel runs the tests locally, one at a time, so their output does not interleave, so use it to watch one test, not a whole suite.

With streamed, the unittest output of two tests appears in sequence, before the summary:

bazel-testlogs

Whatever you print, Bazel saves. The bazel-testlogs symlink holds one directory per test, at the test's package path and name:

test.cache_status
test.log                 # stdout and stderr of the test
test.outputs/            # files the test wrote to TEST_UNDECLARED_OUTPUTS_DIR
test.outputs_manifest/
test.raw_splitlogs/
test.xml                 # a JUnit-style report for CI

test.log is the place to look first. test.xml is meant for CI dashboards. If the test runner does not write one (plain unittest does not), Bazel writes a minimal report with one test case per target and the log embedded:

<?xml version="1.0" encoding="UTF-8"?>
<testsuites>
  <testsuite name="calc/calc_test" tests="1" failures="0" errors="0">
    <testcase name="calc/calc_test" classname="" status="run" duration="1" time="1"></testcase>
      <system-out>
Generated test.log (if the file is not UTF-8, then this may be unreadable):
…

A runner that knows the protocol writes its own, richer file to the path in XML_OUTPUT_FILE; the pytest runner in Arguments and filters does. Repeated runs get one directory each: --runs_per_test=4 produced run_1_of_4/ to run_4_of_4/, and retries of a flaky test land in test_attempts/.

bazel-testlogs points at the latest configuration you tested. The absolute path in the summary line (…/execroot/_main/bazel-out/k8-fastbuild/testlogs/…) is the same directory; on this page we shorten Bazel's output base to … and workspaces to /work/practicum.

Remember: --test_output=errors for daily work; bazel-testlogs/<pkg>/<name>/test.log for the details; test.xml for CI.

The test environment

pytest runs in your shell's directory, with your environment variables, and your tests can write anywhere, often next to the test file. tmp_path exists, but nothing forces you to use it.

Bazel starts each test in a controlled place. It sets these variables, among others (values from a real run, paths shortened):

VariableValue in our runMeaning
TEST_SRCDIR, RUNFILES_DIR…/bin/calc/env_test.runfilesThe test's runfiles tree (M03)
TEST_TMPDIR…/execroot/_main/_tmp/531d74…A private, writable scratch directory. HOME points here too.
TEST_UNDECLARED_OUTPUTS_DIR…/testlogs/calc/env_test/test.outputsFiles written here are kept after the test
XML_OUTPUT_FILE…/testlogs/calc/env_test/test.xmlWhere a runner should write its JUnit XML
TEST_SIZE, TEST_TIMEOUTmedium, 300The test's size and timeout in seconds
TEST_TARGET, TEST_WORKSPACE//calc:env_test, _mainWhich test this is
PATH, TZ.:/bin:/usr/bin:/usr/local/bin, UTCA fixed, minimal environment

The working directory is the workspace inside the runfiles tree, …/env_test.runfiles/_main, the same place bazel run uses. Your own variables do not leak in: pass them with --test_env=NAME=value (or --test_env=NAME to copy one from your shell), or set env on the target.

Mistake: reading files relative to the working directory

A test that opens "rd/testdata/cases.json" fails if the file is not in data, even though it is right there in your checkout:

FileNotFoundError: [Errno 2] No such file or directory: 'rd/testdata/cases.json'

Adding data = ["testdata/cases.json"] makes it pass, because the file is now in the runfiles and the working directory happens to be the runfiles root. "Happens to" is the problem: wrappers, debuggers, and --run_under start tests elsewhere. Use the runfiles library from M03, which works from any directory:

from python.runfiles import runfiles

path = runfiles.Create().Rlocation("_main/rd/testdata/cases.json")

Mistake: writing next to the test

Python tests often write fixtures with Path(__file__).parent / "report.txt". Under the sandbox, __file__ resolves into your source tree, which is mounted read-only:

OSError: [Errno 30] Read-only file system: '/work/practicum/io/report.txt'

The sandbox just saved you from a test that edits your checkout. Writing to the current directory, by contrast, silently succeeds: it lands in the runfiles tree, which is shared with other runs of the same test. Neither is safe. Write to TEST_TMPDIR:

import os
from pathlib import Path

out = Path(os.environ["TEST_TMPDIR"]) / "report.txt"
out.write_text("ok")

Under the Linux sandbox even /tmp is private to the test: a test that created /tmp/cards_export.txt with open(..., "x") passed four runs in a row, and the file never appeared in the real /tmp. Still, use TEST_TMPDIR: it is the documented contract on every platform and strategy. To keep a file for later inspection (a screenshot, a diff), write it to TEST_UNDECLARED_OUTPUTS_DIR; it shows up in bazel-testlogs/<pkg>/<name>/test.outputs/.

Tag the same test no-sandbox and the write to the source tree succeeds: the test passes and leaves io/report.txt in your checkout. If a test only passes without the sandbox, it depends on something undeclared. Fix the test, not the tag.

Remember: the working directory is the runfiles root, but find files with Rlocation; write only to TEST_TMPDIR (or TEST_UNDECLARED_OUTPUTS_DIR to keep files); pass environment variables with --test_env.

Arguments, filters, and pytest

Bazel offers two ways to talk to a test runner. Both depend on the runner listening.

--test_arg

--test_arg=X appends X to the test's command line, after the target's own args. Repeat the flag for each word. Plain unittest parses its command line, so this selects one test method by substring:

pixi run bazel test //shard:filter_test --test_arg=-k --test_arg=beta --test_output=all
test_beta (__main__.FilterTest.test_beta) ... ok
----------------------------------------------------------------------
Ran 1 test in 0.000s

The flip side: unittest.main() rejects arguments it does not know. A test with args = ["--from-build"] meant for the code under test fails before running anything:

usage: env_test.py [-h] [-v] [-q] [--locals] [--durations N] [-f] [-c] [-b]
                   [-k TESTNAMEPATTERNS]
                   [tests ...]
env_test.py: error: unrecognized arguments: --from-build

If your test needs its own arguments, read them from sys.argv first, then call unittest.main(argv=sys.argv[:1]) so unittest sees none.

Changing --test_arg changes the test action, so the result is not reused from a run with different arguments.

--test_filter

--test_filter=EXPR is Bazel's portable "run only these test cases" flag. Bazel does not filter anything itself: it puts the value in the TESTBRIDGE_TEST_ONLY environment variable and leaves it to the runner. Runners for Java and Go read it. rules_python 2.4.6 does not, and neither does plain unittest. We checked: with --test_filter=FilterTest.test_alpha, the variable was set and both test methods still ran.

pytest under Bazel

M04 ran pytest through a tiny entry point, a py_test whose main calls pytest.main() on the files in args, with @pypi//pytest in deps. That works, and --test_arg=-k --test_arg=beta selects tests as you would expect. --test_filter is ignored there too:

collected 4 items
t/math_test.py ....                                                      [100%]
============================== 4 passed in 0.01s ===============================

Three more lines in the entry point make pytest follow Bazel's conventions: honor the filter and write the XML report where Bazel expects it.

"""Run pytest the way Bazel expects: honor --test_filter and write test.xml."""

import os
import sys

import pytest

if __name__ == "__main__":
    args = sys.argv[1:]
    if os.environ.get("TESTBRIDGE_TEST_ONLY"):  # set by --test_filter
        args += ["-k", os.environ["TESTBRIDGE_TEST_ONLY"]]
    if os.environ.get("XML_OUTPUT_FILE"):  # Bazel's test.xml
        args += ["--junitxml", os.environ["XML_OUTPUT_FILE"]]
    sys.exit(pytest.main(args))
collected 4 items / 3 deselected / 1 selected
- generated xml file: …/testlogs/t/math_test/test.xml -
======================= 1 passed, 3 deselected in 0.01s ========================

unittest

No dependency, works from day one. Needs unittest.main() at the bottom, or the test silently passes (M03). Parses sys.argv.

pytest

Fixtures, plain assert, plugins. Needs @pypi//pytest (M04) and an entry point. Write the entry point once, as above, and reuse it.

The labs in this module use unittest so they run without a PyPI hub. Everything else on this page applies to both.

Remember: --test_arg reaches the runner's command line; --test_filter becomes TESTBRIDGE_TEST_ONLY, which a Python runner must read itself.

Flaky tests

A flaky test passes and fails on the same code. In a cached world flakiness is worse than in pytest: a lucky pass is cached and nobody sees the failure until an unrelated change reruns the test.

Here is a classic Python flake: a test that uses random without a seed.

import random
import unittest


class CoinTest(unittest.TestCase):
    def test_heads(self) -> None:
        self.assertLess(random.random(), 0.5)


if __name__ == "__main__":
    unittest.main()

Detect: --runs_per_test

--runs_per_test=N runs each selected test N times, in parallel, and reports how many runs failed. It is the fastest way to prove a test is (or is no longer) flaky:

//flaky:coin_test                                                        FAILED in 4 out of 10 in 3.0s
  Stats over 10 runs: max = 3.0s, min = 0.7s, avg = 1.4s, dev = 0.8s
  …/testlogs/flaky/coin_test/run_2_of_10/test.log
  …/testlogs/flaky/coin_test/run_3_of_10/test.log
  …/testlogs/flaky/coin_test/run_5_of_10/test.log
  …/testlogs/flaky/coin_test/run_7_of_10/test.log

Executed 1 out of 1 test: 1 fails locally.

One failure out of N means FAILED. Runs with --runs_per_test are not served from the cache: two identical commands with --runs_per_test=3 both executed every run.

Tolerate: flaky = True and --flaky_test_attempts

flaky = True on the target tells Bazel to retry a failing test, up to three attempts in total. If any attempt passes, the test counts as passing, but is labeled:

//flaky:coin_flaky_test                                                   FLAKY, failed in 2 out of 3 in 0.4s
  Stats over 3 runs: max = 0.4s, min = 0.3s, avg = 0.4s, dev = 0.0s
  …/testlogs/flaky/coin_flaky_test/test_attempts/attempt_1.log
  …/testlogs/flaky/coin_flaky_test/test_attempts/attempt_2.log
Executed 1 out of 1 test: 1 test passes.

When all three fail, it is FAILED in 3 out of 3. --flaky_test_attempts=N does the same from the command line, for every test, without editing BUILD files.

A coin-flip test with flaky = True still failed outright in one of our six runs. Retries make a flake rarer and slower, and they hide real bugs that happen to be intermittent: race conditions, ordering assumptions, leaked state. Use flaky = True to unblock a team for a few days, with an issue to fix the test. bazel query 'attr(flaky, 1, //...)' lists every test currently excused.

Fix: make the test deterministic

The usual Python causes and fixes:

  • Randomness: pass a seeded random.Random(1234) into the code under test instead of using the global random module.
  • Time: inject a clock, or compare with a tolerance; never assert on time.time() differences tighter than the machine can guarantee.
  • Order: iteration order of a set of strings can change between interpreter runs (hash randomization); sort before comparing.
  • Shared state: files in the runfiles tree or a fixed /tmp path; use TEST_TMPDIR.
  • The network: tag it external and manual, and test the logic against a fake.

Remember: --runs_per_test=10 detects; flaky = True and --flaky_test_attempts tolerate; only a deterministic test fixes. Lab 1 walks through it.

Sharding

One big test target can be split into shards: N copies of the same test program run in parallel, each running a different slice of the test cases. Set shard_count on the target:

py_test(
    name = "many_test",
    size = "small",
    srcs = ["many_test.py"],
    shard_count = 2,
)

Bazel starts the program twice and tells each copy which slice is its job through environment variables: TEST_TOTAL_SHARDS (2) and TEST_SHARD_INDEX (0 or 1). Choosing the slice is the runner's job. To prove the runner understood, it must create the file named in TEST_SHARD_STATUS_FILE.

What happens with Python today

Neither plain unittest nor pytest touches that file, and rules_python 2.4.6 does not do it for them. So under Bazel 9.3.2, shard_count = 2 on an ordinary unittest or pytest target fails:

ERROR: /work/practicum/shard/BUILD.bazel:3:8: Testing //shard:many_test (shard 1 of 2) failed: Sharding requested, but the test runner did not advertise support for it by touching TEST_SHARD_STATUS_FILE. Either remove the 'shard_count' attribute, use a test runner that supports sharding or temporarily disable this check via --noincompatible_check_sharding_support.
…
//shard:many_test                                                     NO STATUS

Executed 0 out of 1 test: 1 was skipped.

The check exists because the old behavior was worse: every shard ran every test, so sharding only multiplied the work. (--noincompatible_check_sharding_support brings that back. Don't.) A runner that implements the protocol is short. This one keeps every Nth unittest case:

def sharded_suite() -> unittest.TestSuite:
    """Keep every Nth test, as Bazel's sharding protocol asks."""
    status = os.environ.get("TEST_SHARD_STATUS_FILE")
    if status:
        pathlib.Path(status).touch()  # tell Bazel this runner understands sharding
    index = int(os.environ.get("TEST_SHARD_INDEX", "0"))
    total = int(os.environ.get("TEST_TOTAL_SHARDS", "1"))
    tests = list(unittest.defaultTestLoader.loadTestsFromName("__main__"))
    flat = [t for suite in tests for t in suite]
    mine = [t for i, t in enumerate(flat) if i % total == index]
    print(f"shard {index} of {total}: {[t.id().split('.')[-1] for t in mine]}")
    return unittest.TestSuite(mine)


if __name__ == "__main__":
    result = unittest.TextTestRunner().run(sharded_suite())
    raise SystemExit(0 if result.wasSuccessful() else 1)
==================== Test output for //shard:many_test (shard 2 of 2):
shard 1 of 2: ['test_b', 'test_d']
==================== Test output for //shard:many_test (shard 1 of 2):
shard 0 of 2: ['test_a', 'test_c']
//shard:many_test                                                        PASSED in 1.1s
Executed 1 out of 1 test: 1 test passes.

Each shard gets its own log directory, bazel-testlogs/shard/many_test/shard_1_of_2/ and shard_2_of_2/. For pytest, community plugins implement the same protocol; check one against these variables before you rely on it.

--test_sharding_strategy

explicit (the default) shards targets that set shard_count. disabled ignores shard_count and runs one copy, which is useful when debugging:

shard 0 of 1: ['test_a', 'test_b', 'test_c', 'test_d']
//shard:many_test                                                        PASSED in 0.5s

forced=K shards every selected test K ways, which only works when every runner supports it.

Before sharding a Python test, try splitting it into several targets along natural lines (one per module under test). Separate targets cache separately, so a change reruns only the affected part. Sharding helps when one target is slow and must stay one target.

Remember: shard_count splits one test across processes, but only a runner that reads TEST_SHARD_INDEX/TEST_TOTAL_SHARDS and touches TEST_SHARD_STATUS_FILE can be sharded. Python runners need that code added.

testonly: helpers that never ship

In a pytest project, shared helpers go in conftest.py or a tests/helpers.py. Nothing stops production code from importing them, except reviewers.

In Bazel, put shared test helpers (fakes, fixtures, builders) in their own py_library with testonly = True. Tests are testonly automatically, so they may depend on it. Anything else may not:

py_library(
    name = "fakes",
    srcs = ["fakes.py"],
    testonly = True,
    visibility = ["//visibility:public"],
)
ERROR: /work/practicum/app/BUILD.bazel:3:11: in py_library rule //app:app: non-test target '//app:app' depends on testonly target '//helpers:fakes' and doesn't have testonly attribute set
ERROR: /work/practicum/app/BUILD.bazel:3:11: Analysis of target '//app:app' (config: a7a71fd) failed
ERROR: Analysis of target '//app:app' failed; build aborted

This is an analysis error, so it is caught before anything runs, for every target in the graph. Two correct fixes, depending on intent:

  • Production code should not use the fake: remove the dependency and depend on the real library.
  • The depending target is itself test infrastructure (a demo server with fake data, a test-data generator): mark it testonly = True as well. testonly spreads upward, never into production.

Do not "fix" it by removing testonly from the helper. That is how fakes end up in a release. package(default_testonly = True) marks a whole package of helpers at once.

Run the build, read the error, then mark //app:demo testonly and build again.

The Python developer's checklist

Every mistake below produced the exact output shown on this page or in M03:

  • No unittest.main() at the bottom: the file exits 0 and Bazel reports PASSED for broken code.
  • open("testdata/x.json"): works only from the runfiles root, and only if the file is in data. Use Rlocation.
  • Writing next to __file__: Read-only file system. Use TEST_TMPDIR.
  • Arguments in args that unittest.main() does not know: unrecognized arguments.
  • Unseeded randomness or wall-clock assertions: flaky, and a lucky pass gets cached.
  • Expecting --test_filter or shard_count to work with a plain Python runner: they need runner support.

Remember: test helpers live in testonly = True libraries; only tests and other testonly targets may depend on them.

Hint

With a fixed seed, the count is the same on every run, so any bound that passes once passes forever. Pick a bound that still means something: with 4000 shuffles of four cards, the ace of spades lands on top about 1000 times. range(900, 1101) is a reasonable window.

def shuffle(cards: list[str], rng: random.Random | None = None) -> list[str]:
    """Return a shuffled copy of cards, using rng if one is given."""
    out = list(cards)
    (rng or random.Random()).shuffle(out)
    return out
    def test_shuffle_is_fair(self) -> None:
        # A seeded generator makes the result the same on every run, while
        # 4000 shuffles still say something about fairness (about 1000 on top).
        rng = random.Random(1234)
        cards = new_deck()
        on_top = sum(shuffle(cards, rng)[0] == "ace of spades" for _ in range(4000))
        self.assertIn(on_top, range(900, 1101))

Quiz

Recap

  • Tests are actions keyed by their inputs. Unchanged tests report (cached) PASSED; --nocache_test_results forces a run, and external tests are never cached.
  • size (small, medium, large, enormous) sets the default timeout (60, 300, 900, 3600 s) and feeds --test_size_filters. --test_verbose_timeout_warnings names oversized tests.
  • manual hides a target from wildcards. --test_tag_filters narrows by any-of and none-of, never re-adding manual tests.
  • --build_tests_only builds only what the selected tests need.
  • test_suite selects by tag or by explicit list; explicit members run even if manual, so tag such suites manual.
  • Logs live in bazel-testlogs/<pkg>/<name>/test.log and test.xml; --test_output=errors prints failing logs.
  • Tests start in the runfiles root with a fixed environment. Find files with Rlocation, write to TEST_TMPDIR, pass variables with --test_env.
  • --test_arg reaches the runner's command line; --test_filter becomes TESTBRIDGE_TEST_ONLY, which Python runners must read themselves.
  • --runs_per_test detects flakes; flaky = True only retries. Fix the nondeterminism.
  • shard_count needs a runner that implements the sharding protocol; plain unittest and pytest fail.
  • Test helpers belong in testonly = True libraries.
