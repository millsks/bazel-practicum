The Build Graph & Caching

Every BUILD file you write adds nodes and edges to one graph of your whole repository. This module shows how Bazel checks that graph (who may depend on whom, and what kind of thing each edge needs), how it turns the graph into actions, and why an honest graph is what makes rebuilds fast and test results cacheable.

⏱ ~2.5 hoursPrerequisites: M01
  • Read srcs, deps, and data as edges of a graph, and query them
  • Control who may depend on a target with visibility, choosing the least permissive setting that works
  • Diagnose cycles, testonly violations, and "does not have mandatory providers" errors
  • Say which of the three phases (loading, analysis, execution) produced an error
  • Explain actions, action keys, and sandboxing, and why an undeclared file read fails
  • Predict what re-runs after a change, keep tests (cached), and use --disk_cache

Edges: srcs, deps, and data

In Python, dependencies are implicit. import lib.greet works if lib/ is somewhere on sys.path, and open("prices.csv") works if the file happens to be in the current directory. Nothing writes down that app needs lib, or that a test needs a CSV file.

Bazel makes you write those facts down, and each one becomes an edge: an arrow from a target to something it needs. The targets are the nodes. Together they form the build graph (strictly, a directed acyclic graph: arrows have a direction, and no path may loop back to where it started).

For Python rules, three attributes carry almost every edge:

srcs

The target's own source files, usually in its own package. For py_* rules, the .py files.

deps

Other code this target imports: libraries that must provide Python information. Their own deps come along transitively.

data

Files the program reads at run time: CSVs, templates, config. Bazel places them next to the program when it runs.

Here is a small workspace. //app:hello imports a library and reads a config file that lives in another package. Before you run anything, predict what the first command prints.

labels(data, X) lists only the direct data edges of X: here //app:cfg. deps(X) follows every edge, transitively, and includes source files, because files are targets too. The real Bazel output for the last command matches the simulator's:

//app:hello.py
//config:settings.yaml
//lib:greet.py

Real bazel query 'deps(...)' also lists implicit dependencies that rules add for you, such as the Python toolchain. --noimplicit_deps hides most of them. The simulator shows only the edges you wrote.

Remember: srcs is your own code, deps is code you import, data is files you open. Each is an edge, and Bazel only knows about edges you declare.

Visibility: who may depend on you

Python's privacy is a convention: a leading underscore says "please don't import this". Anyone can ignore it, and in a big repository someone always does. Then you cannot change your "private" module without breaking a team you have never heard of.

Bazel enforces privacy. Every rule target has a visibility: the list of packages allowed to depend on it. The default is //visibility:private, meaning only targets in the same package. Put greet in //lib and use it from //app without saying anything, and the build stops:

ERROR: app/BUILD.bazel:3:10: in py_binary rule //app:hello: Visibility error:
target '//lib:greet' is not visible from
target '//app:hello'
Recommendation: modify the visibility declaration if you think the dependency is legitimate. For more info see https://bazel.build/concepts/visibility
ERROR: app/BUILD.bazel:3:10: Analysis of target '//app:hello' (config: a7a71fd) failed
ERROR: Analysis of target '//app:hello' failed; build aborted
INFO: Elapsed time: 0.331s, Critical Path: 0.00s
INFO: 1 process: 1 internal.
ERROR: Build did NOT complete successfully

The error points at the user (app/BUILD.bazel), but the fix goes on the dependency: the owner of greet decides who may use it. These are the values you can list:

ValueWho may depend on the target
//visibility:privateOnly its own package (the default).
//app:__pkg__Exactly the package //app, not its subpackages.
//app:__subpackages__//app and every package below it (//app/cli, //app/cli/v2, …).
//tools:friendsThe packages named by a package_group target called friends.
//visibility:publicEveryone, in every repository.

__pkg__ and __subpackages__ are not targets. They are special names that only mean something inside a visibility list. The list is a union: if any entry admits the user, it is allowed.

Package groups and package defaults

A package_group names a set of packages once, so many targets can share it. Patterns ending in /... include subpackages:

package_group(
    name = "friends",
    packages = [
        "//app/...",
        "//tools/release",
    ],
)

Writing visibility on every target gets repetitive. package(default_visibility = [...]), called at the top of a BUILD file before any rule, sets the default for every rule in that package. A target's own visibility still overrides it.

load("@rules_python//python:defs.bzl", "py_library")

package(default_visibility = ["//internal:friends"])

py_library(
    name = "core",          # visible to //internal:friends
    srcs = ["core.py"],
)

py_library(
    name = "scratch",
    srcs = ["scratch.py"],
    visibility = ["//visibility:private"],   # overrides the default
)

The mistake everybody makes once

A label without a colon names the target with the same name as the package: //app means //app:app. So visibility = ["//app"] does not mean "the app package". Bazel tries to load a target called app as a package group:

ERROR: app/BUILD.bazel: no such target '//app:app': target 'app' not declared in package 'app' defined by app/BUILD.bazel
ERROR: lib/BUILD.bazel:3:11: no such target '//app:app': target 'app' not declared in package 'app' defined by app/BUILD.bazel and referenced by '//lib:greet'
ERROR: Analysis of target '//app:hello' failed; build aborted: Analysis failed

Write "//app:__pkg__". (If //app:app does exist and is not a package group, you get a different, equally confusing error.)

Edit lib/BUILD.bazel below until //app:hello and //app/cli:main both build but //web:page does not. Try __pkg__ first and see which one still fails. Then try __subpackages__.

Reach for //visibility:public last. Public targets are an API: anyone can depend on them, and removing that later is a migration. Start private, then widen to the exact packages that need access. In code review, a new public deserves a question.

Remember: targets are private by default; the dependency's owner grants access; prefer :__pkg__ or a package_group over public; and //app is not the same as //app:__pkg__.

Source files in other packages

Visibility covers files too. A source file is a target in the package that contains it, so config/settings.yaml is //config:settings.yaml. In Bazel 9, source files are private unless their package says otherwise. How you say it is exports_files:

exports_files(
    ["settings.yaml"],
    visibility = ["//app:__pkg__"],
)

Without the visibility argument, exports_files makes the files public. Bazel reports a missing export in two ways, depending on whether anything in the file's own package mentions the file.

If nothing in //config refers to settings.yaml, Bazel does not even create a target for it, and it tells you exactly what to add:

ERROR: config/BUILD.bazel: no such target '//config:settings.yaml': target 'settings.yaml' not declared in package 'config' defined by config/BUILD.bazel; however, a source file of this name exists.  (Perhaps add 'exports_files(["settings.yaml"])' to config/BUILD.bazel?)
ERROR: app/BUILD.bazel:3:10: no such target '//config:settings.yaml': target 'settings.yaml' not declared in package 'config' defined by config/BUILD.bazel; however, a source file of this name exists.  (Perhaps add 'exports_files(["settings.yaml"])' to config/BUILD.bazel?) and referenced by '//app:hello'
ERROR: Analysis of target '//app:hello' failed; build aborted: Analysis failed

If a rule in //config does use the file (say, a filegroup), the target exists but is private, and you get a visibility error with a pointed last sentence:

ERROR: app/BUILD.bazel:3:10: in py_binary rule //app:hello: Visibility error:
target '//config:settings.yaml' is not visible from
target '//app:hello'
Recommendation: modify the visibility declaration if you think the dependency is legitimate. For more info see https://bazel.build/concepts/visibility. To set the visibility of that source file target, use the exports_files() function

Older Bazel versions let other packages use any source file that a rule in its package mentioned. Bazel 9 does not: a file in another package needs exports_files() (or a visible filegroup that wraps it). Old BUILD files that relied on the leak fail with the error above after an upgrade.

There are two good ways to share files across packages. Export the file when another package needs that one file by name. Wrap it in a visible filegroup when you want to hand out a set of files under one stable name, so the owner can add or rename files without breaking users.

Remember: files are targets with visibility too; in Bazel 9 another package can use a source file only if its package exports it.

testonly: keeping test helpers out of production

In a Python project, tests/fakes.py sits next to production code, and nothing stops app/main.py from importing a fake clock. It works, so it ships.

Set testonly = True on a target that only tests should use: fakes, fixtures, test data. Bazel then refuses any edge from a non-test target to it. Test rules (py_test) are testonly automatically, and another testonly library may depend on it too.

py_library(
    name = "fake_clock",
    srcs = ["fake_clock.py"],
    testonly = True,
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":fake_clock"],    # a production binary using a fake
)
ERROR: app/BUILD.bazel:9:10: in py_binary rule //app:hello: non-test target '//app:hello' depends on testonly target '//app:fake_clock' and doesn't have testonly attribute set
ERROR: app/BUILD.bazel:9:10: Analysis of target '//app:hello' (config: a7a71fd) failed
ERROR: Analysis of target '//app:hello' failed; build aborted

The fix is almost never to mark hello testonly. Move the fake into the test's deps, or have the binary depend on a real implementation. package(default_testonly = True) marks a whole package of test helpers at once.

Remember: testonly is visibility for "only tests"; it fails at analysis, before any code runs.

Dependency cycles, and how to break them

Python tolerates circular imports, sometimes: orders.py imports users.py, which imports orders.py, and it works until someone moves an import to module level and gets ImportError: cannot import name ... (most likely due to a circular import).

Bazel does not tolerate them at all. A build graph must be acyclic, because Bazel builds a target only after everything it depends on. If //orders depends on //users and //users on //orders, neither can go first:

ERROR: orders/BUILD.bazel:3:11: in py_library rule //orders:orders: cycle in dependency graph:
    //orders:orders (e722a217ced723dfeb49874b2007895ae0dc9a9d49d004d95320b88c609c409a)
.-> //orders:orders (a7a71fd16b14112464272f754633480c74c664f2488224c592ebf2dfc7a06b18)
|   //users:users (a7a71fd16b14112464272f754633480c74c664f2488224c592ebf2dfc7a06b18)
`-- //orders:orders (a7a71fd16b14112464272f754633480c74c664f2488224c592ebf2dfc7a06b18)
ERROR: Analysis of target '//orders:orders' failed; build aborted

Read the ASCII loop from .-> down to `--: orders → users → orders. The hex strings are configuration hashes (which flags each target was built with); ignore them for now.

bazel query runs before analysis, so it still works on a cyclic graph. somepath(A, B) prints one path from A to B, which is how you find the edge to cut in a big graph:

$ bazel query 'somepath(//orders, //users)'
//orders:orders
//users:users

The fix: extract what both sides share

A cycle usually means two packages share an idea that belongs to neither. Typically orders needs users only for a UserId type, and users needs orders only for an OrderId. Move the shared code into a third library that both depend on, and the loop becomes a V:

flowchart LR
  subgraph Before
    O1["//orders"] --> U1["//users"]
    U1 --> O1
  end
  subgraph After
    O2["//orders"] --> S["//shared:ids"]
    U2["//users"] --> S
  end

Other ways out: merge the two targets into one (if they really are one unit), or invert one edge by passing a function or interface in at run time instead of importing it. Extraction is the most common and the easiest to review.

In the sandbox, run the build to see the cycle, then run somepath both ways. Then break it: create shared/BUILD.bazel with a py_library named ids (its source shared/ids.py already exists), point both packages at it, and remove their deps on each other.

Remember: the graph must be acyclic; Bazel reports a cycle at analysis; find it with somepath, and break it by extracting the shared code into its own library.

Providers: what kind of thing is on the other end

An edge is not just "depends on". Each attribute expects a certain kind of target. Bazel checks that through providers: small, typed bundles of information a target hands to the targets that depend on it. You never write providers in BUILD files; rules create them.

For Python, the important one is PyInfo. A py_library returns a PyInfo listing its Python sources and import paths (plus those of its own deps). A py_binary collects the PyInfo of everything in its deps to know which files to put on its Python path. So deps of a Python rule requires PyInfo (or CcInfo, for C extensions).

A filegroup is just a named bag of files. It returns no PyInfo. Put one in deps and analysis fails:

filegroup(
    name = "templates",
    srcs = ["page.html"],
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":templates"],     # files are not Python code
)
ERROR: app/BUILD.bazel:8:10: in deps attribute of py_binary rule //app:hello: '//app:templates' does not have mandatory providers: 'PyInfo' or 'CcInfo'. Since this rule was created by the macro 'py_binary', the error might have been caused by the macro implementation
ERROR: app/BUILD.bazel:8:10: Analysis of target '//app:hello' (config: a7a71fd) failed
ERROR: Analysis of target '//app:hello' failed; build aborted

Read it as: "the deps attribute needs something that provides PyInfo; this does not". The sentence about the macro is boilerplate: py_binary is a macro wrapping the real rule, and Bazel cannot tell whose mistake it was. It was yours.

The fix depends on what the files are:

  • Files the program reads (templates, CSV, YAML): move the filegroup to data. Any target that produces files is fine there.
  • Python code: make it a py_library with those files in srcs, and keep it in deps.

The reverse mistake is quieter. A .yaml file in a Python rule's srcs builds without complaint with rules_python 2.4.6 (we checked), so nothing tells you it is in the wrong place. Keep srcs for .py files and put files the program reads in data, where readers and tools expect them.

Remember: attributes check providers, not names. deps of a Python rule needs PyInfo; files go in data.

The three phases

Every bazel build or bazel test goes through three phases, in order. Knowing which phase an error came from tells you where to look.

Loading
Bazel evaluates the BUILD files (and the .bzl files they load) of the packages your command needs. Errors here are Starlark errors: an undefined name, a syntax error, an empty glob. A loading error breaks the whole package, so every target in it is unusable.
Analysis
For each target, the rule's implementation runs. It looks up every dependency, checks visibility, testonly, cycles, and providers, and declares the actions needed to build the outputs. Nothing has run yet.
Execution
Bazel runs the actions whose outputs are needed and not already cached. Errors here come from real commands: a missing input file, a failing compiler, a failing test.

Each package in this sandbox fails in a different phase. Predict which phase before you run each command.

The execution one surprises people. config.yaml is in the same package, so Bazel creates a target for it from the label alone and analysis passes. Only when an action needs the file does Bazel notice it does not exist. Real Bazel, with the same mistake in a genrule's srcs:

INFO: Analyzed target //gen:count (1 packages loaded, 2 targets configured).
ERROR: gen/BUILD.bazel:1:8: Executing genrule //gen:count failed: missing input file '//gen:wordz.txt'
ERROR: gen/BUILD.bazel:1:8: Executing genrule //gen:count failed: 1 input file(s) do not exist
Target //gen:count failed to build
Use --verbose_failures to see the command lines of failed build steps.
ERROR: gen/BUILD.bazel:1:8 Executing genrule //gen:count failed: 1 input file(s) do not exist
INFO: Elapsed time: 0.168s, Critical Path: 0.00s
INFO: 1 process: 1 internal.
ERROR: Build did NOT complete successfully
PhaseErrors you meet there
Loadingname 'py_binary' is not defined, syntax errors, glob pattern ... didn't match anything, no such package
Analysisno such target, Visibility error, does not have mandatory providers, depends on testonly target, cycle in dependency graph
Executionmissing input file, a command exiting non-zero, FAILED tests, undeclared files not found in the sandbox

Two tells in the output. "Analysis of target ... failed; build aborted" means analysis. A line starting "Executing ..." or a test marked FAILED means execution. Loading errors usually print a Starlark traceback or "error loading package".

Remember: loading reads BUILD files, analysis checks the graph and plans actions, execution runs them. Everything in the earlier sections of this module is an analysis error.

Actions and action keys

Analysis turns targets into actions. An action is one command with an exact list of input files, an exact list of output files, and an environment. "Run this genrule's shell command", "write a launcher script", and "run this test" are each an action.

You can see the actions Bazel plans with bazel aquery ("action query"). For a genrule that counts lines in words.txt:

genrule(
    name = "count",
    srcs = ["words.txt"],
    outs = ["count.txt"],
    cmd = "wc -l < $(location words.txt) > $@",
)
$ bazel aquery //gen:count
INFO: Analyzed target //gen:count (1 packages loaded, 2 targets configured).
INFO: Found 1 target...
action 'Executing genrule //gen:count'
  Mnemonic: Genrule
  Target: //gen:count
  Configuration: k8-fastbuild
  Execution platform: @@platforms//host:host
  ActionKey: 1c74c343d28db6786290499ca59ef411b61fe731182471b2b4e790d46cda0d18
  Inputs: [external/bazel_tools/tools/genrule/genrule-setup.sh, gen/words.txt]
  Outputs: [bazel-out/k8-fastbuild/bin/gen/count.txt]
  Environment: [PATH=/bin:/usr/bin:/usr/local/bin]
  Command Line: (exec /bin/bash \
    -c \
    'source external/bazel_tools/tools/genrule/genrule-setup.sh; wc -l < gen/words.txt > bazel-out/k8-fastbuild/bin/gen/count.txt')

Everything Bazel needs to decide "can I skip this?" is on that screen. The action key is a hash of the command line, the environment, and the action's settings. Before running an action, Bazel combines that key with the hashes of the contents of every input file. If an earlier run produced outputs for exactly that combination, Bazel reuses them instead of running the command.

Three consequences follow, and they explain most of Bazel's behavior:

  1. Content, not timestamps. touch words.txt changes nothing: our next build reported 1 action cache hit. (Make uses timestamps; Bazel does not.)
  2. The environment is part of the key. Changing --action_env=NOTE=b to NOTE=c re-ran every affected action and test in our runs, even though no file changed.
  3. Undeclared inputs are invisible to the key. If a command reads a file not in its inputs, the key does not change when that file does, and Bazel would happily reuse a stale result. The next section is about how Bazel stops that from happening.

aquery, action keys, and running commands are execution-time concepts the simulator does not model. Everything from here to the end of the module is shown with real Bazel output and practiced in the labs.

Remember: an action is a command plus exact inputs and outputs; its cache key hashes the command, environment, and input contents.

Sandboxing and hermeticity

A pytest test can open any file on your disk. It passes on your laptop because prices.csv happens to be in the working directory, and fails on CI, or worse, passes on CI against a stale copy.

A build is hermetic when each action's result depends only on its declared inputs: not on what else is on the machine, not on what ran before. Hermeticity is what makes action keys trustworthy, and therefore what makes caching safe.

Bazel enforces it with a sandbox. On Linux, each action runs in a fresh directory tree (an execution root) that contains symlinks to only the action's declared inputs. Files you did not declare are simply not there. A genrule that reads a file it never listed:

genrule(
    name = "count",
    outs = ["count.txt"],
    cmd = "wc -l < gen/words.txt > $@",    # reads a file it never declared
)
INFO: Analyzed target //gen:count (2 packages loaded, 2 targets configured).
ERROR: gen/BUILD.bazel:1:8: Executing genrule //gen:count failed: (Exit 1): bash failed: error executing Genrule command (from genrule rule target //gen:count) /bin/bash -c 'source external/bazel_tools/tools/genrule/genrule-setup.sh; wc -l < gen/words.txt > bazel-out/k8-fastbuild/bin/gen/count.txt'
Use --sandbox_debug to see verbose messages from the sandbox and retain the sandbox build root for debugging
/bin/bash: line 1: gen/words.txt: No such file or directory
Target //gen:count failed to build
Use --verbose_failures to see the command lines of failed build steps.
INFO: Elapsed time: 0.223s, Critical Path: 0.03s
INFO: 2 processes: 2 internal.
ERROR: Build did NOT complete successfully

The file is right there in your workspace, but not in the sandbox. Run the same build with --spawn_strategy=standalone (no sandbox) and it "works": exactly the kind of accidental success the sandbox exists to catch. The fix is to declare the input and let Bazel tell the command where it is: srcs = ["words.txt"] and $(location words.txt).

Tests and runfiles

Tests and binaries see their files through runfiles: a directory tree, built next to the executable, holding its sources, its deps, and its data. A py_test starts with its working directory at the root of that tree. So a test that opens herm/words.txt without declaring it fails, even though the path is correct relative to your workspace:

FileNotFoundError: [Errno 2] No such file or directory: 'herm/words.txt'
----------------------------------------------------------------------
Ran 1 test in 0.001s
FAILED (errors=1)
cwd: /root/.cache/bazel/_bazel_root/cafad382fe0dddd68f47a0053524c931/sandbox/linux-sandbox/3/execroot/_main/bazel-out/k8-fastbuild/bin/herm/words_test.runfiles/_main

Add data = ["words.txt"] to the py_test and it passes. In real projects, declare the file on the library that reads it, not on each test: data is transitive, so every binary and test that depends on the library gets the file. Lab 1 practices exactly this. Module 03 covers runfiles in depth, including the runfiles library for reading them portably.

The Linux sandbox hides undeclared files from relative paths, but it is not a full jail. An absolute path into your source tree still works. So does Path(__file__).resolve().parent / "words.txt": resolve() follows the runfiles symlink back into your workspace, where the undeclared file sits. We tried it: the test passed with no data, and after we edited words.txt it still reported (cached) PASSED, because the file is not an input. Use Path(__file__).parent (no resolve()) and declare the file.

Remember: hermetic means "depends only on declared inputs"; the sandbox makes undeclared reads fail; and anything that escapes the sandbox also escapes the cache key.

Incremental rebuilds and cached tests

Put the pieces together. Every action is keyed by its command and its input contents. Change one file, and only the actions that (transitively) take that file as input get a new key. Everything else is a cache hit.

Click each source file in the graph below. Notice which tests re-run, and which stay (cached).

Edit report_test.py: one test re-runs. Edit prices.csv: everything does, because it is data of the library at the bottom of the graph. What would happen if prices.csv were read but not declared? (Answer: nothing would re-run, and the tests would report stale results.)

Here is the same thing for real. Two packages, each with a test; nothing changed since the last run:

$ bazel test //...
INFO: Analyzed 4 targets (0 packages loaded, 0 targets configured).
INFO: Found 2 targets and 2 test targets...
INFO: Elapsed time: 0.175s, Critical Path: 0.01s
INFO: 1 process: 2 action cache hit, 1 internal.
INFO: Build completed successfully, 1 total action
//app:hello_test                                                (cached) PASSED in 0.5s
//lib:greet_test                                                (cached) PASSED in 0.8s
Executed 0 out of 2 tests: 2 tests pass.

Then one line is appended to lib/greet.py. Only the test that depends on it runs:

$ bazel test //...
INFO: Analyzed 4 targets (0 packages loaded, 0 targets configured).
INFO: Found 2 targets and 2 test targets...
INFO: Elapsed time: 0.926s, Critical Path: 0.76s
INFO: 4 processes: 1 action cache hit, 3 internal, 2 linux-sandbox.
INFO: Build completed successfully, 4 total actions
//app:hello_test                                                (cached) PASSED in 0.5s
//lib:greet_test                                                         PASSED in 0.6s
Executed 1 out of 2 tests: 2 tests pass.

The PASSED in 0.5s on a cached line is the time the test took when it actually ran. The N processes: ... line counts what happened: action cache hit (skipped), internal (bookkeeping Bazel does in-process, such as writing symlinks), and linux-sandbox (commands that really ran, sandboxed).

The action cache, and why bazel clean is rarely needed

The action cache lives in Bazel's output base (a directory under ~/.cache/bazel, one per workspace). It maps action keys to the outputs they produced. Test results are outputs of the test action, so they are cached exactly like compiled files.

bazel clean deletes the outputs and that cache. Coming from Make or a stale __pycache__, it is tempting to run it whenever something looks odd. With Bazel it almost never helps: if inputs are declared, the cache cannot be stale, and cleaning only throws away work. When a clean does change the result, that is a hermeticity bug (an undeclared input) worth finding, not a ritual worth repeating.

Why a test is never cached

If bazel test re-runs a test every time even though nothing changed, look for one of these:

  • --nocache_test_results (or -t-) on the command line or in a .bazelrc. It forces every test to run.
  • tags = ["external"] on the test. It tells Bazel the test talks to the outside world (a network service, say), so its result can never be cached.
  • A volatile input: a generated file that embeds a timestamp or random value changes every build, so the test's key changes too.

Lab 2 has the first two hidden in a real workspace.

A cache that survives: --disk_cache

The action cache is per workspace and disappears with bazel clean. --disk_cache=PATH adds a second cache in a directory you choose, keyed the same way, shared by every workspace and every clean. It also remembers older results: the local action cache keeps only the latest result for each output, so switching back to a previous version of a file re-runs its actions, while with a disk cache our rebuild of a previously seen version reported 1 disk cache hit. Put it in your .bazelrc:

build --disk_cache=~/.cache/bazel-disk

After bazel clean, the next test run gets its results back from that directory:

$ bazel clean
INFO: Starting clean (this may take a while). Use --async if the clean takes more than several minutes.
$ bazel test //...
INFO: Analyzed 3 targets (96 packages loaded, 2895 targets configured).
INFO: Found 1 target and 2 test targets...
INFO: Elapsed time: 2.730s, Critical Path: 0.65s
INFO: 25 processes: 4 disk cache hit, 23 internal.
INFO: Build completed successfully, 25 total actions
//textstats:report_test                                         (cached) PASSED in 0.4s
//textstats:stats_test                                          (cached) PASSED in 0.3s
Executed 0 out of 2 tests: 2 tests pass.

Use an absolute path or ~/ for --disk_cache. We tried --disk_cache=%workspace%/.cache: Bazel 9.3.2 does not expand %workspace% in this flag and created a directory literally named %workspace%. A relative path is resolved from the workspace root, which also works, but then each workspace gets its own cache.

A remote cache is the same idea over the network: CI fills it, and every developer's build downloads results instead of recomputing them. It is only safe because of everything in this module: honest edges, sandboxed actions, and content-hashed keys. Setting one up is part of Level 2 of this course.

Teams usually commit a .bazelrc with build --disk_cache=~/.cache/bazel-disk for local work. The disk cache grows without bound by default; --experimental_disk_cache_gc_max_size=20G caps it.

Remember: only actions downstream of a change re-run; tests are actions, so unchanged tests report (cached) PASSED; bazel clean is a smell, not a fix; --disk_cache keeps results across cleans and workspaces.

//app:hello fails with a visibility error on //lib:greet. Fix it the least permissive way: //app:hello must build, but //tools:audit, which also tries to use the library, must still be refused. Do not touch app/ or tools/.

Hint

Add a visibility list to greet naming exactly one package. The special name for "this package and not its subpackages" ends in :__pkg__. "//app" alone is a label for //app:app, which does not exist.

Show solution 
load("@rules_python//python:defs.bzl", "py_library")

py_library(
    name = "greet",
    srcs = ["greet.py"],
    visibility = ["//app:__pkg__"],
)

If //app/cli later needs it too, widen to //app:__subpackages__, or define a package_group once several unrelated packages need it.

//orders and //users depend on each other, so nothing builds. Both only need the ID types now in shared/ids.py. Create a py_library named //shared:ids from that file, make both //orders and //users depend on it, and remove their dependencies on each other. Give ids a visibility that admits just those two packages.

Hint

A visibility list can hold several entries: ["//orders:__pkg__", "//users:__pkg__"]. Once neither package depends on the other, the visibility they granted each other is no longer needed either; you may delete it.

Show solution 
load("@rules_python//python:defs.bzl", "py_library")

py_library(
    name = "ids",
    srcs = ["ids.py"],
    visibility = [
        "//orders:__pkg__",
        "//users:__pkg__",
    ],
)
load("@rules_python//python:defs.bzl", "py_library")

py_library(
    name = "orders",
    srcs = ["orders.py"],
    deps = ["//shared:ids"],
)
load("@rules_python//python:defs.bzl", "py_library")

py_library(
    name = "users",
    srcs = ["users.py"],
    deps = ["//shared:ids"],
)

The Python side changes the same way: orders.py and users.py now from shared.ids import OrderId, UserId instead of importing each other.

//app:hello reads config/settings.yaml at run time, but the file is private to //config. Change only config/BUILD.bazel so that //app:hello builds while //ops:deploy, which also lists the file, is still refused. Keep the all_configs filegroup working for //config itself.

Hint

exports_files takes a list of file names and an optional visibility. Without visibility the files become public, which would let //ops in too.

Show solution 
exports_files(
    ["settings.yaml"],
    visibility = ["//app:__pkg__"],
)

filegroup(
    name = "all_configs",
    srcs = ["settings.yaml"],
)

The real error for the starter ends with "To set the visibility of that source file target, use the exports_files() function". Bazel told you the answer.

A teammate added the HTML templates to //web:server's deps, and the build fails with "does not have mandatory providers: 'PyInfo' or 'CcInfo'". The server reads the templates at run time. Fix the BUILD file so //web:server builds and the templates still reach it. Keep //web:render in deps: it is real Python code.

Hint

deps is for code you import (targets that provide PyInfo). Which attribute is for files a program opens?

Show solution 
load("@rules_python//python:defs.bzl", "py_binary", "py_library")

filegroup(
    name = "templates",
    srcs = [
        "templates/index.html",
        "templates/item.html",
    ],
)

py_library(
    name = "render",
    srcs = ["render.py"],
)

py_binary(
    name = "server",
    srcs = ["server.py"],
    data = [":templates"],
    deps = [":render"],
)

Even better, if only render.py opens the templates, put data = [":templates"] on :render: data is transitive, so the server (and any test of render) gets them automatically.

Labs: hermeticity and caching for real

The simulator stops at analysis, so it cannot show a sandbox hiding a file or a test result coming from a cache. These two labs do, with real Bazel. The first proves that undeclared inputs fail; the second proves your tests are cacheable and that results survive bazel clean.

The //inventory package has a library that reads prices.csv at run time, a test for it, and a genrule that counts the items in the CSV. Neither the library nor the genrule declares the file, so the test cannot find it and the genrule fails in the sandbox. Declare the file where it is used. Do not change any .py file.

  • Run pixi run start m02-lab1, then cd work/m02-lab1
  • Run pixi run bazel test //inventory:stock_test --test_output=errors and find the path in the FileNotFoundError: which directory was the test looking in?
  • Add prices.csv to the data of the library that opens it (not just the test) and re-run
  • Run pixi run bazel build //inventory:item_count, read the sandbox error, and declare the input in the genrule's srcs, using $(location prices.csv) in cmd
  • Check cat bazel-bin/inventory/item_count.txt prints 3
  • Back at the repository root, run pixi run grade m02-lab1
Hint

The test's traceback ends in .../stock_test.runfiles/_main/inventory/prices.csv: the runfiles tree. A file gets into runfiles through data. For the genrule, a file gets into the sandbox through srcs, and $(location prices.csv) expands to its path there.

Show solution 
load("@rules_python//python:defs.bzl", "py_library", "py_test")

# The library reads prices.csv at run time (see stock.py).
py_library(
    name = "stock",
    srcs = ["stock.py"],
    data = ["prices.csv"],
)

py_test(
    name = "stock_test",
    srcs = ["stock_test.py"],
    deps = [":stock"],
)

# Counts the items in the price list (every line but the header).
genrule(
    name = "item_count",
    srcs = ["prices.csv"],
    outs = ["item_count.txt"],
    cmd = "tail -n +2 $(location prices.csv) | wc -l > $@",
)

Because data sits on the library, every future binary or test that depends on :stock gets prices.csv without anyone remembering to add it. And because it is now an input, editing a price re-runs stock_test; before, a cached result could have hidden the change.

In //textstats, both tests pass, but they run every single time, and CI is slow. Nothing in them is volatile; something in the workspace's configuration keeps Bazel from reusing results. Find and remove it, then add a disk cache so results also survive bazel clean. The grader runs bazel test //... twice, then bazel clean, then bazel test //... again, and expects Executed 0 out of 2 tests both times after the first.

  • Run pixi run start m02-lab2, then cd work/m02-lab2
  • Run pixi run bazel test //... twice; note the second run says Executed 2 out of 2
  • Read .bazelrc and textstats/BUILD.bazel; remove what forces re-runs
  • Run the tests twice again and look for (cached) PASSED
  • Add build --disk_cache=~/.cache/bazel-disk to .bazelrc; run the tests, pixi run bazel clean, and run them again
  • Back at the repository root, run pixi run grade m02-lab2
Hint

There are two culprits: a test flag in .bazelrc whose name says what it does, and a tag on report_test that tells Bazel the test talks to the outside world. The comment says the test no longer does.

Show solution 
# Keep action outputs and test results in a cache that survives `bazel clean`
# (and is shared by every workspace on this machine).
build --disk_cache=~/.cache/bazel-disk

# Show the output of failing tests.
test --test_output=errors

Quiz

Recap

  • srcs, deps, and data are edges of the build graph; bazel query walks them, and files are nodes too.
  • Targets are private by default. The dependency's owner grants access with :__pkg__, :__subpackages__, a package_group, or (rarely) //visibility:public; package(default_visibility = ...) sets a package-wide default.
  • In Bazel 9, a source file in another package is usable only if that package exports_files() it (or wraps it in a visible filegroup).
  • testonly keeps fakes and fixtures out of production targets.
  • The graph must be acyclic; find cycles with somepath and break them by extracting a shared library.
  • Attributes check providers: Python deps need PyInfo, so files go in data.
  • Loading evaluates BUILD files, analysis checks the graph and declares actions, execution runs them; each has its own family of errors.
  • An action's key hashes its command, environment, and input contents. Sandboxing hides undeclared inputs so keys stay honest.
  • Only actions downstream of a change re-run; unchanged tests report (cached) PASSED. bazel clean is rarely the answer; --disk_cache keeps results across cleans.
