Query & Debugging

Every BUILD file you wrote in this course added edges to one graph. This module teaches you to ask that graph questions: what depends on this, why does that depend on this, which tests does my change affect, and why did Bazel just rebuild everything. It is the toolkit you will use most once a repository is too big to hold in your head.

⏱ ~2 hoursPrerequisites: M08
  • Choose between query, cquery, and aquery for a question, and say what each one cannot see
  • Write query expressions with target patterns, set operations, deps, rdeps, kind, attr, filter, labels, and tests
  • Answer "why does X depend on Y?" with somepath and allpaths, and fix the BUILD file that causes it
  • List the tests a set of changed files affects, the way CI systems do
  • Read actions with aquery: mnemonics, command lines, inputs, and outputs
  • Explain a rebuild with --explain, see commands with -s, and find Bazel's directories with bazel info

Three questions, three tools

In a Python project you answer "who uses money.py?" with grep -r "from core.money". It finds direct importers only, misses anything that reads a file at run time, and is fooled by comments and dynamic imports. pipdeptree shows which installed distributions require which, not which of your modules import each other. import-linter checks layering rules by parsing imports. Each is a partial, reconstructed picture.

Bazel does not need to reconstruct anything. The graph is declared: every deps, data, srcs, and generated file is an edge you wrote down, across every language. Bazel offers three commands to read it, one per phase you met in M02:

CommandReadsUse it forBlind spot
bazel queryThe target graph after loading"What depends on what?" Fast, works on broken builds.No configuration: both branches of every select().
bazel cqueryThe configured graph after analysis"What does this build, with these flags, really use?" Output file paths.Needs the build to analyze; slower.
bazel aqueryThe action graph after analysis"What command does Bazel run, with which inputs?"Verbose; nothing about whether an action will actually run.

All three take the same expression language. A query expression evaluates to a set of targets; the command prints that set. The simplest expression is a target pattern:

The workspace below is a small shop: a money library at the bottom, a catalog and a checkout built on it, a server, a report tool, and a genrule that writes a version file. Run the commands and get a feel for the graph. You will use this workspace for most of the module.

bazel query needs no build and no configuration, so it answers in well under a second even in large repositories, and it works when the build is broken at analysis (M02 used it on a dependency cycle). Reach for it first; move to cquery only when flags or select() matter.

Remember: query reads the declared graph, cquery the graph for one set of flags, aquery the commands. They share one expression language.

The query language

An expression is built from three things: target patterns (the same //..., //pkg:all, //pkg:* you pass to bazel build), functions that take sets and return sets, and set operators that combine them. Results are printed once each, sorted by package and then name.

Patterns in query are not quite build patterns

One difference matters: bazel build //... skips targets tagged manual, but bazel query //... lists them. Query describes the graph; it does not decide what to build. In our workspace a manual py_test and a manual test_suite both appeared in bazel query //catalog/.... Keep that in mind when you turn query results into a test list.

Functions you will use every day

FunctionReturns
deps(X), deps(X, N)X and everything it depends on, transitively, or only N edges deep. deps(X, 1) is X plus its direct dependencies.
rdeps(U, X), rdeps(U, X, N)Targets inside the universe U that depend on X (the next section).
kind(REGEX, X)Targets whose kind matches: py_test, genrule, "source file", "generated file".
attr(NAME, REGEX, X)Rules whose attribute, printed as text, matches: attr(tags, manual, //...), attr(size, small, //...).
filter(REGEX, X)Targets whose label matches: filter("_test$", //...).
labels(ATTR, X)The labels written in one attribute of X: labels(deps, //checkout).
tests(X)The tests in X, with test_suites expanded into their members.
set(A B C)A literal set, space-separated. Handy for a list of changed files.

Regexes are partial matches (like Python's re.search): kind(test, //...) matches py_test, go_test, and also test_suite. Anchor them when that matters: kind("py_test", ...) or filter("_test$", ...).

Set operations

A + B (or A union B) is everything in either; A ^ B (intersect) is what is in both; A - B (except) removes B from A. Put spaces around -. Without them the shell word //...-//core/... is read as one malformed pattern:

$ bazel query '//...-//core/...'
ERROR: invalid package name '...-//core': package names may not contain '//' path separators

Predict each result before you run it. The last one asks: which of the targets //checkout depends on are rules rather than files?

Implicit dependencies

Rules add edges you never wrote: a Python toolchain, a launcher, config settings. deps() follows them. In our workspace, bazel query 'deps(//app:server)' printed 173 lines, most of them C++ helper files under @bazel_tools. --noimplicit_deps hides most of that. For a py_library it leaves only your edges; a py_binary or py_test keeps a few settings that rules_python attaches through its own attributes:

$ bazel query 'deps(//checkout:checkout_test)' --noimplicit_deps
//catalog:catalog
//catalog:catalog.py
//checkout:checkout
//checkout:checkout.py
//checkout:checkout_test
//checkout:checkout_test.py
//core:money
//core:money.py
@@platforms//os:os
@@platforms//os:windows
@rules_python//command_line_option:enable_runfiles
@rules_python//python:none
@rules_python//python/private:sentinel

To keep only your own repository, intersect with it: deps(//app:server) ^ //... (rules only, since //... has no files), or ^ //...:* to keep files too.

The simulator shows only the edges you wrote, as if --noimplicit_deps were always on, and it never lists external targets such as @rules_python//python:none. It also lacks let expressions (below), the minrank/maxrank/graph/build output formats, and file paths like core/money.py as targets: write //core:money.py in sandboxes.

Naming a sub-result with let

Long expressions repeat themselves. let NAME = EXPR in BODY names a set, and $NAME uses it:

$ bazel query 'let t = kind(test, //...) in rdeps(//..., //catalog:catalog.py) ^ $t'
//catalog:catalog_test
//checkout:checkout_test

Remember: query lists manual targets; regexes match anywhere, so anchor them; spaces around -; --noimplicit_deps or ^ //... to cut the toolchain noise.

rdeps: what breaks if I change this?

deps walks edges forward, from a target to what it needs. Reverse dependencies walk them backwards: from a target to everything that needs it. That is the question you ask before renaming a function, deleting a library, or changing its behavior.

rdeps takes a universe first: the set of targets to search. Bazel only knows the packages it has loaded, so you tell it where to look. //... means "my whole repository". The optional third argument is a depth: 1 means direct users only.

Predict both results, then run them. Which targets reach //core:money only indirectly?

The result includes //core:money itself: a target is in its own reverse closure, just as it is in its own deps. Two mistakes produce errors worth recognizing. Forgetting the universe:

$ bazel query 'rdeps(//core:money)'
ERROR: Error while parsing 'rdeps(//core:money)': too few arguments to function 'rdeps' at ')'

And reaching for allrdeps (reverse deps over "everything loaded") without telling Bazel what "everything" is. It is not even in the list of functions until you pass --universe_scope=//...:

$ bazel query 'allrdeps(//core:money)'
ERROR: Error while parsing 'allrdeps(//core:money)': unknown function 'allrdeps' at 'allrdeps ( //core:money'; expected one of ['allpaths', 'attr', 'buildfiles', 'deps', 'executables', 'filter', 'kind', 'labels', 'loadfiles', 'rdeps', 'same_pkg_direct_rdeps', 'siblings', 'some', 'somepath', 'tests', 'visible']

Query does not check visibility

Query reads edges as written. It does not run analysis, so it does not care whether an edge is allowed. We added a //sec:dump binary that lists //checkout in its deps, although //checkout is visible only to //app:

$ bazel query 'rdeps(//..., //checkout, 1)'
//app:server
//checkout:checkout
//checkout:checkout_test
//sec:dump
$ bazel build //sec:dump
ERROR: sec/BUILD.bazel:3:10: in py_binary rule //sec:dump: Visibility error:
target '//checkout:checkout' is not visible from
target '//sec:dump'

That is a feature: rdeps finds every target that tries to use a library, including the ones that will fail. Use it to find illegal users before you tighten a visibility list, and remember that a clean rdeps is not proof that everything builds.

Before deleting or renaming a public target, paste the output of bazel query 'rdeps(//..., //lib:old, 1)' into the pull request. Reviewers see the blast radius, and you have a checklist of BUILD files to update.

Remember: rdeps(universe, target[, depth]); the universe is usually //...; query ignores visibility, so it shows would-be users too.

somepath and allpaths: why does X depend on Y?

"Why is numpy in my lambda bundle?" With pip you run pipdeptree -r -p numpy and read the tree upwards. Inside your own code, there is no such tool: you grep for imports, then grep for the importers.

somepath(A, B) returns one chain of edges from A to B: the shortest explanation. Real Bazel prints it in path order, from A to B. allpaths(A, B) returns every target on any path from A to B, sorted. When both are empty, A does not depend on B at all, and Bazel prints INFO: Empty results.

somepath picked the direct edge //checkout → //core:money; allpaths also found the route through //catalog. That difference matters when you are trying to remove a dependency: cut the edge somepath shows, run it again, and it may show you the next one. allpaths shows them all at once.

The simulator prints somepath results sorted, like every other query. Real Bazel prints the path in order. For somepath(//app:server, //catalog:catalog.py) real Bazel printed //app:server, //checkout:checkout, //catalog:catalog, //catalog:catalog.py: same set, path order.

Seeing the paths as a picture

--output=graph prints the result as Graphviz dot, with the edges between the targets in the set. Pipe it into dot -Tsvg (from the graphviz package, which pixi add graphviz installs) or paste it into an online viewer:

$ bazel query 'allpaths(//app:server, //core:money)' --output=graph
digraph mygraph {
  node [shape=box];
  "//app:server"
  "//app:server" -> "//checkout:checkout"
  "//checkout:checkout"
  "//checkout:checkout" -> "//core:money"
  "//checkout:checkout" -> "//catalog:catalog"
  "//catalog:catalog"
  "//catalog:catalog" -> "//core:money"
  "//core:money"
}

--output=graph on deps(//...) of a real repository is thousands of nodes and renders as a grey smear. Graph a somepath or allpaths, or a deps with a depth, and add --noimplicit_deps.

Remember: somepath explains one way A reaches B, in path order; allpaths lists everything on every way; empty means no dependency.

Which tests does this change affect?

CI systems for large repositories do not run bazel test //... blindly. They take the files changed in a pull request and ask the graph which tests can see them. You can do the same in one query.

Files are targets

Every source file is a target in its package: core/money.py is //core:money.py. Real bazel query also accepts the workspace-relative path and works out the label, which is exactly what git diff --name-only gives you:

$ bazel query 'tests(rdeps(//..., set(core/money.py catalog/catalog.py)))'
//catalog:catalog_test
//checkout:checkout_test
//core:money_test

kind(test, ...) or tests(...)?

The workspace below adds a manual live test and a manual suite to //catalog. Predict each result. The differences are the whole lesson.

  • kind(test, ...) matched //catalog:nightly too: test_suite contains "test". Harmless for bazel test, confusing in a report.
  • tests(...) expands suites into their members and drops everything else, so it is the right wrapper. It keeps manual tests, because query does.
  • except attr(tags, manual, //...) removes the tests bazel test //... would skip anyway.
  • A change to the server's own source affects no test at all: nothing tests the server. That empty answer is itself useful information.

Files that belong to no package

A real change list contains README.md or docs/ files that no BUILD file owns. Query fails on them, and --keep_going skips them instead, exiting with code 3 ("partial success"):

$ bazel query 'set(core/money.py README.md)'
ERROR: couldn't determine target from filename 'README.md'
$ bazel query --keep_going 'tests(rdeps(//..., set(core/money.py README.md)))'
ERROR: Skipping 'README.md': couldn't determine target from filename 'README.md'
WARNING: --keep_going specified, ignoring errors. Results may be inaccurate
//catalog:catalog_live_test
//catalog:catalog_test
//checkout:checkout_test
//core:money_test
$ echo $?
3

Exit code 7 was the plain failure. A script that treats any non-zero exit as fatal will fail on every pull request that touches the README. Lab 2 builds exactly this script.

This selection is only as good as the graph. A test that reads a file it never declared does not appear in rdeps of that file, and neither does it rerun when the file changes (M02's hermeticity section). An affected-tests query turns undeclared inputs from a caching bug into a CI bug: changes that break the test land without running it.

Remember: tests(rdeps(//..., set(FILES))) except attr(tags, manual, //...), with --keep_going for files outside packages.

--output=build: the rule after macros

In M03 you learned that py_binary is a macro. --output=build shows what it expanded into, with labels made absolute and select() left intact, because query never resolves configuration:

$ bazel query //app:server --output=build
# /path/to/ws/app/BUILD.bazel:8:10
py_binary(
  name = "server",
  generator_name = "server",
  generator_function = "py_binary",
  generator_location = "app/BUILD.bazel:8:10",
  data = ["//gen:version"],
  config_settings = select({"@@platforms//os:windows": {"@rules_python//command_line_option:enable_runfiles": "true"}, "//conditions:default": {}}) + {},
  deps = ["//checkout:checkout"] + select({"//app:fast": ["//core:speedups"], "//conditions:default": []}),
  srcs = ["//app:server.py"],
)
# Rule server instantiated at (most recent call last):
#   /path/to/ws/app/BUILD.bazel:8:10 in <toplevel>
#   .../external/rules_python+/python/py_binary.bzl:44:15 in py_binary
#   ...

That config_settings line is where the @@platforms//os:windows and enable_runfiles entries from the "implicit dependencies" listing come from: the macro added an attribute you never wrote. (This server has a select() on -c opt; the next section uses it.)

Remember: label_kind and package for reading, graph for pictures, build to see through macros, ranks for depth.

cquery: the graph for these flags

M06 introduced cquery for checking a select(). Here is the full picture. The shop's server pulls in a C-accelerated module only in optimized builds:

config_setting(
    name = "fast",
    values = {"compilation_mode": "opt"},
)

py_binary(
    name = "server",
    srcs = ["server.py"],
    data = ["//gen:version"],
    deps = ["//checkout"] + select({
        ":fast": ["//core:speedups"],
        "//conditions:default": [],
    }),
)

Ask query and cquery the same question:

$ bazel query 'somepath(//app:server, //core:speedups)'
//app:server
//core:speedups
$ bazel cquery 'somepath(//app:server, //core:speedups)'
INFO: Empty results
$ bazel cquery 'somepath(//app:server, //core:speedups)' -c opt
//app:server (bf3a44e)
//core:speedups (bf3a44e)

query says yes: it sees both branches. cquery says no for the default build and yes with -c opt. When the question is "is this in my production binary?", only cquery with your production flags answers it.

Reading cquery output

Each line carries a configuration id, the start of a hash of every build option. Targets built with the same flags share it. Source files print (null): a file is not configured.

$ bazel cquery 'deps(//app:server, 1)' --noimplicit_deps
//app:server (a7a71fd)
//app:server.py (null)
//app:fast (a7a71fd)
//gen:version (a7a71fd)
//checkout:checkout (a7a71fd)

The order is not sorted, and config_settings appear as dependencies. A tool that builds code for the machine running the build (an exec configuration, such as the Python precompiler) shows a different id. --output=label_kind works here too (py_binary rule //app:server (a7a71fd)).

Where is my output? --output=files

cquery --output=files prints the files a target produces, relative to the workspace. It is the reliable way for a script to find a genrule's output without guessing the bazel-out directory name:

$ bazel cquery //gen:version --output=files
bazel-out/k8-fastbuild/bin/gen/version.txt
$ bazel cquery //app:server --output=files
bazel-out/k8-fastbuild/bin/app/server
app/server.py

The simulator's cquery resolves select() exactly, but prints plain sorted labels with no configuration id, never lists implicit dependencies (real cquery without --noimplicit_deps printed 33 lines for deps(//app:server, 1)), and has no --output=files. Use it to check what is selected; read ids and paths from real Bazel.

Remember: query answers "could"; cquery answers "does, with these flags". Configuration ids group targets by flags; (null) means a source file; --output=files finds outputs.

The simulator stops before actions exist, so it has no aquery. Everything in this section is real output.

Remember: aquery prints actions with mnemonic, inputs, outputs, environment, and command; --output=summary first; filter with mnemonic(), inputs(), outputs().

Why did that rebuild? Why is it slow?

When pytest is slow you reach for pytest --durations=10, and when something reruns you shrug: it always reruns everything. With Bazel, "why did this run?" has an exact answer, and Bazel will write it down for you.

--explain: why each action ran

--explain=FILE writes one line per executed action with the reason Bazel could not reuse a cached result. --verbose_explanations adds detail where Bazel has it. We appended a comment to catalog/catalog.py and reran the tests:

$ bazel test //... --explain=explain.log --verbose_explanations
$ cat explain.log
Executing action 'BazelWorkspaceStatusAction stable-status.txt': unconditional execution is requested.
Executing runfiles for //catalog:catalog_test: action changed since cached execution.
Executing runfiles for //app:server: action changed since cached execution.
Executing runfiles for //checkout:checkout_test: action changed since cached execution.
Executing runfiles for //tools:report: action changed since cached execution.
Executing action 'Testing //catalog:catalog_test': action changed since cached execution.
Executing action 'Testing //checkout:checkout_test': action changed since cached execution.

Read it like rdeps in action: the runfiles trees of everything that contains catalog.py were refreshed, and the two tests that depend on it ran. //core:money_test is absent: it stayed (cached). The reasons you will see most:

ReasonMeaning, from our runs
no entry in the cache (action is new)Never built before: a new target, or a first build.
action changed since cached executionThe key differs: an input's content, the command, or the environment. Editing gen/VERSION and passing a new --action_env or --test_env value each produced it.
unconditional execution is requestedBazel was told to run it: the workspace status action (every build), or a test under --nocache_test_results.

An action that was a cache hit is not listed. If the log is nearly empty and the build was still slow, the time went somewhere else: loading, analysis, or fetching. That is a job for the profile.

-s: the exact command

--subcommands (-s) prints every command as it runs, ready to paste into a shell. It is the fastest way to see what a genrule really executed after $(location) expansion:

$ bazel build //gen:version -s
INFO: Analyzed target //gen:version (0 packages loaded, 0 targets configured).
SUBCOMMAND: # genrule rule target //gen:version [action 'Executing genrule //gen:version', configuration: a7a71fd16b14112464272f754633480c74c664f2488224c592ebf2dfc7a06b18, execution platform: @@platforms//host:host, mnemonic: Genrule]

  exec env - \
    PATH=/bin:/usr/bin:/usr/local/bin \
  /bin/bash -c 'source external/bazel_tools/tools/genrule/genrule-setup.sh; cp gen/VERSION bazel-out/k8-fastbuild/bin/gen/version.txt')

The output base is one directory per workspace holding everything Bazel keeps: the action cache, fetched repositories (external/), and the execution root, the tree where actions run and where bazel-out really lives. bazel info bazel-bin prints one key, which is handy in scripts. command_log holds the full output of the last command.

--profile: where did the time go?

Bazel writes a profile of every command, in Chrome trace format, to command.profile.gz in the output base. --profile=PATH puts it somewhere you choose. Open it in chrome://tracing or ui.perfetto.dev to see a timeline: phases, every action on every thread, and the critical path (the chain of actions that decided the wall time). In our profile of bazel test //... after editing money.py, the critical path ended in action 'Testing //checkout:checkout_test'.

Older guides say to run bazel analyze-profile. Bazel 9.3.2 no longer has it: Command 'analyze-profile' not found. Try 'bazel help'. Use a trace viewer.

The build event protocol

Everything Bazel reports (targets configured, actions, test results) is also a stream of structured build events. CI dashboards read it. --build_event_json_file=bep.json writes one JSON object per line; two of them from our test run:

{"id": {"testResult": {"label": "//catalog:catalog_test", "run": 1, "shard": 1, "attempt": 1, "configuration": {"id": "e722a217..."}}}, "testResult": {"testAttemptDurationMillis": "1467", "status": "PASSED"}}
{"id": {"testSummary": {"label": "//catalog:catalog_test", "configuration": {"id": "e722a217..."}}}, "testSummary": {"totalRunCount": 1, "overallStatus": "PASSED", "runCount": 1}}

If you are tempted to parse Bazel's terminal output in a script, parse this instead: it is stable and documented.

--keep_going: all the errors at once

By default Bazel stops at the first broken package. With two broken packages (an undefined py_library in one, a dependency on a missing target in the other), plain bazel build //... reported only the first. With --keep_going (-k) it reported both and built the eleven targets that did not depend on either:

ERROR: broken1/BUILD.bazel:1:1: name 'py_library' is not defined (did you mean 'cc_library'?)
...
ERROR: broken2/BUILD.bazel:3:11: no such target '//core:nope': target 'nope' not declared in package 'core' defined by core/BUILD.bazel and referenced by '//broken2:b'
INFO: Analyzed 12 targets (0 packages loaded, 1 target configured).
WARNING: errors encountered while analyzing target '//broken2:b', it will not be built.
Analysis failed
INFO: Build succeeded for only 11 of 12 top-level targets
...
ERROR: Build did NOT complete successfully

It works for query too: bazel query //... --keep_going printed every loadable target and warned Results may be inaccurate.

Remember: --explain for "why did this run", -s for "what ran", bazel info for "where", the profile for "how long", BEP for machines, -k for "show me everything".

Three diagnoses

Most "Bazel is being weird" reports are one of these. Each has a query that finds it and a BUILD change that fixes it.

1. A dependency you did not expect

Symptom: the server image includes test fakes, or a CLI pulls in a heavy library. Find it: somepath(//app:server, //testing:fakes), then allpaths if cutting one edge is not enough. Fix: move the dependency to the target that really needs it (often a test), split the library that carries it, and add testonly = True or a narrow visibility so it cannot creep back. Exercise 1.

2. A test that runs too often

Symptom: a template edit reruns every test in the repository. Find it: kind(test, rdeps(//..., //web:templates/receipt.html)) lists tests that have no business seeing a template; somepath from one of them to the template shows the edge. Usually it is a "utils" library that bundles unrelated code and data. Fix: split it so each test depends only on what it imports. Lab 1 is this diagnosis, for real: before the fix, one template edit reran all four tests; after, only one:

//billing:invoice_test                                          (cached) PASSED in 0.5s
//common:text_test                                              (cached) PASSED in 0.5s
//inventory:stock_test                                          (cached) PASSED in 0.6s
//web:render_test                                                        PASSED in 0.5s
Executed 1 out of 4 tests: 4 tests pass.

The reverse symptom, a test that should rerun and does not, is an undeclared input: rdeps cannot see it, so neither can the cache. Declare the file in data.

3. A cache miss you cannot explain

Symptom: nothing changed, but actions keep running. Find it: build twice with --explain=explain.log --verbose_explanations and read the second log. "unconditional execution" on a test points at --nocache_test_results or tags = ["external"] (M02). "action changed" on every run with no edits points at something volatile in the key: a genrule that embeds date, an --action_env that differs between your shell and CI, or a flag that toggles between commands (each flag change also prints Build option ... has changed, discarding analysis cache). Fix: remove the volatility, or pin the flag in .bazelrc.

A colleague says "CI is slow because Bazel reruns all 900 tests on every pull request." Which two commands would you run first, and what would each tell you? (One answer: an affected-tests query for a typical change, to see whether the graph is too connected; then --explain on a second, unchanged run, to see whether caching works at all.)

Hint

bazel run starts the program inside its runfiles tree, and Bazel refuses to start there: ERROR: bazel should not be called from a bazel output directory. BUILD_WORKSPACE_DIRECTORY (M03) is where the user ran bazel run. For README.md, --keep_going makes query skip it, and then Bazel exits with 3, which your script must not treat as failure under set -e.

Show solution 
#!/usr/bin/env bash
# Print the tests affected by the files given as arguments (paths relative to the
# workspace root), one label per line.
set -euo pipefail

if [ "$#" -eq 0 ]; then
  echo "usage: bazel run //tools:affected_tests -- FILE [FILE...]" >&2
  exit 2
fi

# `bazel run` starts us inside the runfiles tree, where Bazel refuses to run.
# BUILD_WORKSPACE_DIRECTORY is the workspace the user ran `bazel run` from.
cd "${BUILD_WORKSPACE_DIRECTORY:?run this with bazel run}"

# Every test that depends on a changed file, minus the manual ones that
# `bazel test //...` would skip anyway.
query="tests(rdeps(//..., set($*))) except attr(tags, manual, //...)"

# --keep_going skips files that belong to no package (README.md, docs/...);
# Bazel then exits with 3 ("partial success"), which is fine here.
status=0
bazel query --keep_going "$query" || status=$?
if [ "$status" -ne 0 ] && [ "$status" -ne 3 ]; then
  exit "$status"
fi

With the solution, bazel run //tools:affected_tests -- README.md common/text.py printed //billing:invoice_test, //common:text_test, and //inventory:stock_test on stdout, and the Skipping 'README.md' error on stderr. The nested bazel query talks to the same Bazel server that is running bazel run, which works because run releases the server before starting your program.

Quiz

Recap

  • query reads the declared target graph (no configuration, both select() branches, implicit deps, manual targets); cquery the configured graph for your flags; aquery the actions.
  • Expressions combine patterns, functions (deps, rdeps, kind, attr, filter, labels, tests, set, let), and set operators + ^ - (spaces around -).
  • rdeps(//..., X) answers "what breaks"; it ignores visibility, so it also finds would-be users.
  • somepath shows one path in order, allpaths every target on any path; --output=graph draws them.
  • Affected tests: tests(rdeps(//..., set(FILES))) except attr(tags, manual, //...), with --keep_going (exit 3) for files outside packages. It is only as good as your declared inputs.
  • cquery prints configuration ids, (null) for files, and finds outputs with --output=files.
  • aquery shows mnemonics (PyCompile, Genrule, TestRunner), inputs, outputs, environment, and commands; filter with mnemonic(), inputs(), outputs().
  • --explain says why actions ran, -s what ran, bazel info where things live, the profile how long it took, BEP for machines, --keep_going for every error at once.
