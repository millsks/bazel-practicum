Generated Files & Macros

Real repositories generate code: constants from a CSV, clients from a schema, a version file at release time. Bazel can run any generator you have, as long as you tell it every input and every output in advance. This module teaches genrule and its Make variables, the safer helpers in bazel_skylib, golden-file tests, and how to stop copy-pasting BUILD code by writing your own macros.

⏱ ~2.5 hoursPrerequisites: M07

  • Write a genrule with srcs, outs, cmd, and tools, and choose the right Make variable for each path
  • Read the exact errors for undeclared prerequisites, $@ with several outputs, and a binary in srcs
  • Prefer write_file, copy_file, and run_binary from bazel_skylib when they fit

  • Write a legacy macro in a .bzl file with native.*, naming suffixes, passed-through visibility, and private helpers
  • Say what symbolic macros (macro()) add, and when you need a custom rule instead

Why generated files, and why declare them

In a Python project, code generation hides in many places: a build.py that writes _version.py, a setup.py hook that compiles .proto files, a Makefile target that turns colors.csv into constants.py. You run it when you remember to. If you forget, you import a stale file, and nothing tells you.

A generated file is any file a build step produces instead of a person: a constants module, a protobuf-style client, a version stamp, a processed data file. Typical reasons to generate:

Code generation

Python constants or enums from a CSV, API clients from an OpenAPI schema, gRPC stubs from .proto files.

Version stamps

A version.txt or _build_info.py holding a release number.

Data processing

Cleaning a CSV, compressing assets, building a lookup table a test reads.

Documentation

A table of contents, a reference page generated from code, a rendered diagram.

In Bazel, a generator is just another action (M02): a command with exact inputs and exact outputs. Bazel must know the outputs before it runs anything. During analysis it plans the whole action graph, and a planned action needs a list of files to produce. Other targets refer to those files by label, so the files must exist as targets after loading.

That is the big difference from a Makefile habit. Make lets a recipe write any file it likes, and finds out later. Bazel asks you to declare the outputs. In exchange it knows exactly when to re-run the generator (an input's contents changed), can cache the result, and can share it with CI.

In this graph, constants.py is generated from colors.csv by a Python tool. Click colors.csv: the generator, the library, and both tests re-run. Then click gen_constants.py (the generator's own source). Why does editing the tool re-run the tests too?

The tool is an input of the generator action, so a change to the tool can change the output. Bazel tracks that for you; a Makefile rarely does.

Remember: a generator is an action; Bazel needs its outputs named in the BUILD file, so it can plan, cache, and re-run it exactly when an input changes.

genrule: a shell command with declared files

genrule is Bazel's general-purpose generator. It is native, so it needs no load(). It runs one Bash command, with four attributes doing most of the work:

srcs
Input files (labels). Only these are inside the sandbox.
outs
Output file names, relative to the package. Not labels: plain names.
cmd
The Bash command. It must create every file in outs.
tools
Programs the command runs (next sections).
genrule(
    name = "count",
    srcs = ["words.txt"],
    outs = ["count.txt"],
    cmd = "wc -l < $(location words.txt) > $@",
)
$ bazel build //gen:count
INFO: Analyzed target //gen:count (6 packages loaded, 9 targets configured).
INFO: Found 1 target...
Target //gen:count up-to-date:
  bazel-bin/gen/count.txt
INFO: Elapsed time: 6.302s, Critical Path: 0.06s
INFO: 2 processes: 1 internal, 1 linux-sandbox.
INFO: Build completed successfully, 2 total actions

The output lands in bazel-bin/gen/count.txt: the same package path, under bazel-bin. Never under your source tree. Bazel makes outputs read-only, so editing them by hand fails; change the inputs instead.

Outputs are targets too

Each name in outs becomes a generated file target in the package: //gen:count.txt. You use it exactly like a source file: in another rule's srcs or data, in another genrule, in a py_library's srcs if it is a .py file. So there are two labels here, and they mean different things:

LabelKindMeans
//gen:countgenrule ruleThe rule. As a dependency, it stands for all its outputs.
//gen:count.txtgenerated fileExactly one output file.

Prefer the file label when you want one specific output, so a later second output does not sneak into your inputs. Give the rule a different name from its outputs: naming a genrule version.txt with output version.txt builds, but Bazel warns:

WARNING: e/BUILD.bazel:1:8: target 'version.txt' is both a rule and a file; please choose another name for the rule

A common convention is a _gen suffix for the rule: version_gen producing version.txt.

Predict before you run: what does bazel query '//gen:*' --output=label_kind list for this package? How many targets, of which kinds? Then try deps(//gen:report), which uses the output of another genrule.

Six targets: the BUILD file, words.txt, two genrules, and two generated files. Generated files exist from the moment the package loads, before anything has run. That is what "declared in advance" means.

Remember: outs are names, each becomes a generated file target, the file lands in bazel-bin/<package>/, and you reference it by label like any other file.

Make variables: letting Bazel write the paths

You never know where Bazel will put a file. Inputs sit at gen/words.txt in the sandbox, outputs under bazel-out/k8-fastbuild/bin/gen/, tools under yet another directory. So cmd uses Make variables: placeholders like $(location words.txt) that Bazel replaces with the right path before running the command. (The name comes from Make's $(VAR) syntax.)

We ran one genrule that prints every variable, with a source file, a generated file (:count), and a tool in its inputs. These are the real expansions:

The difference between execpath and rootpath shows up for generated files: $(execpath :count.txt) was bazel-out/k8-fastbuild/bin/gen/count.txt, while $(rootpath :count.txt) was gen/count.txt. A genrule's command runs from the execution root, so it wants execpaths. A binary started by bazel run or a test runs from its runfiles tree, so its args want rootpaths.

The errors you will meet

Every one of these is an analysis error: Bazel expands the variables while planning the action, before running anything. (Paths shortened from absolute to workspace-relative in all outputs below.)

A label that is not an input. $(location) only works for labels listed in srcs, tools, or outs:

ERROR: gen/BUILD.bazel:8:8: in cmd attribute of genrule rule //gen:undeclared: label '//gen:words.txt' in $(location) expression is not a declared prerequisite of this rule
ERROR: gen/BUILD.bazel:8:8: Analysis of target '//gen:undeclared' (config: a7a71fd) failed
ERROR: Analysis of target '//gen:undeclared' failed; build aborted

The fix is never to hard-code the path. Add the file to srcs; then it is in the sandbox and in the cache key.

$@ with two outputs. $@ means "the output", so it is ambiguous with more than one:

ERROR: gen/BUILD.bazel:14:8: in cmd attribute of genrule rule //gen:two: variable '$@' : more than one output file
ERROR: gen/BUILD.bazel:14:8: Analysis of target '//gen:two' (config: a7a71fd) failed
ERROR: Analysis of target '//gen:two' failed; build aborted

Use $(location a.txt) and $(location b.txt) for each output instead (outputs are prerequisites too). $< has the twin error: variable '$<' : more than one input file.

A shell variable. In cmd, every $ belongs to Bazel first. To reach the shell, double it:

ERROR: e/BUILD.bazel:20:8: in cmd attribute of genrule rule //e:home: '$HOME' syntax is not supported; use '$(HOME)' instead for "Make" variables, or escape the '$' as '$$' if you intended this for the shell

So a shell loop is for f in $(SRCS); do wc -l < $$f; done > $@. And an unknown Make variable such as $(VERSION) fails with $(VERSION) not defined.

Even $$HOME fails on Linux: genrules run with set -u and a minimal environment (PATH=/bin:/usr/bin:/usr/local/bin, as aquery showed in M02), and our run stopped with HOME: unbound variable. That is hermeticity at work. Pass what the command needs as declared inputs, not through the environment.

The sandbox below has three broken genrules. Run the build and read each error. Fix stamp by declaring its input, split by replacing $@, and loop by escaping the shell variable.

The simulator checks $(location) prerequisites, $@, $<, and unknown $(NAME) variables with Bazel's wording. It does not flag a bare shell $f or $HOME (real Bazel does, as shown above), and it never runs the command.

Remember: let Bazel write paths with $(location)/$(execpath); every label you expand must be declared; $@ and $< need exactly one file; write $$ for the shell.

tools: running your own generator

Your build.py runs with whichever Python is active. On CI that might be a different version than on your laptop, and on a cross-compiling build it might not even be the platform you are building for.

Most generators are programs you wrote: a py_binary that reads a CSV and writes Python. A genrule runs such a program through tools:

genrule(
    name = "shout_tools",
    srcs = ["words.txt"],
    outs = ["shout.txt"],
    tools = ["//tools:upper"],          # a py_binary: upper.py IN OUT
    cmd = "$(location //tools:upper) $< $@",
)

Why not just put the binary in srcs? Because Bazel builds the two lists in different configurations. A configuration is the set of settings a target is built with: compilation mode, CPU, platform, flags (M06).

  • The target configuration is for things you are building to ship or test: srcs, deps, data.
  • The exec configuration is for things that run during the build, on the machine that executes actions: compilers, generators, everything in tools. It is optimized by default (-opt-exec).

cquery shows the configuration next to each dependency. The genrule and its input use the target configuration; the tool gets a different hash, the exec one:

$ bazel cquery 'deps(//gen:shout_tools, 1)' --noimplicit_deps
//gen:shout_tools (a7a71fd)
//gen:words.txt (null)
//tools:upper (04bf134)
$ bazel config
Available configurations:
04bf134dfa57115b01daa56bd3a30421a6e74b1819e002496a26c94ed0087067 k8-opt-exec (exec)
...
e722a217ced723dfeb49874b2007895ae0dc9a9d49d004d95320b88c609c409a k8-fastbuild

Source files have no configuration (null). On a laptop the two configurations target the same CPU, so the difference looks academic. It stops being academic when you cross-compile (building Linux ARM binaries on a Mac): the generator must run on the Mac, while the product runs on ARM. tools gets that right automatically.

There is also a practical reason. A py_binary is several files (a launcher, its .py sources, its runfiles). In tools, $(location) means "the executable". In srcs, it means "all of its files", and Bazel refuses:

ERROR: lt/BUILD.bazel:1:8: in cmd attribute of genrule rule //lt:shout: label '//tools:upper' in $(location) expression expands to more than one file, please use $(locations //tools:upper) instead.  Files (at most 5 shown) are: [bazel-out/k8-fastbuild/bin/tools/upper, tools/upper.py]
ERROR: lt/BUILD.bazel:1:8: Analysis of target '//lt:shout' failed; build aborted

The suggestion ($(locations ...)) is a trap: it would paste two paths into your command. The real fix is to move the binary from srcs to tools. Note that the listed files live in k8-fastbuild, the target configuration, which confirms the binary was built for the wrong purpose.

With the tool in tools, aquery shows the whole picture: the tool's launcher and runfiles are action inputs (so editing the tool re-runs the generator), and the command calls it from the exec output directory:

$ bazel aquery 'mnemonic(Genrule, //gen:shout_tools)'
action 'Executing genrule //gen:shout_tools'
  Mnemonic: Genrule
  Inputs: [bazel-out/k8-opt-exec/bin/tools/upper, bazel-out/k8-opt-exec/bin/tools/upper.runfiles, external/bazel_tools/tools/genrule/genrule-setup.sh, gen/words.txt, tools/upper.py]
  Outputs: [bazel-out/k8-fastbuild/bin/gen/shout.txt]
  Command Line: (exec /bin/bash \
    -c \
    'source external/bazel_tools/tools/genrule/genrule-setup.sh; bazel-out/k8-opt-exec/bin/tools/upper gen/words.txt bazel-out/k8-fastbuild/bin/gen/shout.txt')

The simulator does not model configurations or a binary's multiple files, so it accepts a py_binary in srcs with $(location). The exercises check where you put the binary; the lab shows the real error.

Remember: anything the command runs goes in tools (exec configuration); anything it reads goes in srcs (target configuration).

Sandboxes, missing outputs, and other honesty checks

M02 showed that a genrule reading a file it never declared fails in the sandbox. The same discipline applies to the output side, and it catches Makefile habits early.

Reading an undeclared file fails at execution, because the file is not in the sandbox:

ERROR: un/BUILD.bazel:1:8: Executing genrule //un:count failed: (Exit 1): bash failed: error executing Genrule command (from genrule rule target //un:count) /bin/bash -c 'source external/bazel_tools/tools/genrule/genrule-setup.sh; wc -l < un/words.txt > bazel-out/k8-fastbuild/bin/un/count.txt'
Use --sandbox_debug to see verbose messages from the sandbox and retain the sandbox build root for debugging
/bin/bash: line 1: un/words.txt: No such file or directory

Forgetting to create a declared output also fails at execution. Here outs lists left.txt and right.txt, but the command only touches the first:

ERROR: e/BUILD.bazel:14:8: declared output 'e/right.txt' was not created by genrule. This is probably because the genrule actually didn't create this output, or because the output was a directory and the genrule was run remotely (note that only the contents of declared file outputs are copied from genrules run remotely)
ERROR: e/BUILD.bazel:14:8: Executing genrule //e:pair failed: not all outputs were created or valid

Writing an undeclared file is silently thrown away. A command that also writes $(RULEDIR)/undeclared.txt builds fine, but only the declared file appears in bazel-bin: the sandbox is discarded after the action. If something "disappears", it was never declared.

Generated files are not globbed. glob() runs at loading time over the source tree, so glob(["*.txt"]) never matches a generated .txt. Name generated files explicitly by label.

A generator whose output is a directory of unknown files (protoc emitting one file per message, a docs tool emitting a site) does not fit outs. Real rules use "tree artifacts" for that, which need a custom rule (Level 3). In Level 1, either list the files you know will be produced, or make the tool write a single archive.

Remember: undeclared inputs fail, undeclared outputs vanish, declared-but-missing outputs fail, and globs never see generated files.

bazel_skylib: write_file, copy_file, run_binary

genrule is flexible, but it means Bash, which is fragile (quoting, set -u, Windows). For the common cases bazel_skylib, Bazel's standard library module, has purpose-built rules. Add it once to MODULE.bazel:

bazel_dep(name = "bazel_skylib", version = "1.9.2")

write_file

Writes fixed lines of text to out. No shell at all.

copy_file

Copies src (a file or generated file) to a new name out.

run_binary

Runs one tool with args, directly, without Bash. Takes srcs, outs, and env.

diff_test

A test that passes when two files are identical. Next section.

load("@bazel_skylib//rules:copy_file.bzl", "copy_file")
load("@bazel_skylib//rules:run_binary.bzl", "run_binary")
load("@bazel_skylib//rules:write_file.bzl", "write_file")

write_file(
    name = "greeting",
    out = "greeting.txt",
    content = ["hello", "world", ""],    # lines; the empty last line adds a final newline
)

copy_file(
    name = "greeting_copy",
    src = ":greeting.txt",
    out = "copy.txt",
)

run_binary(
    name = "shout",
    srcs = ["words.txt"],
    outs = ["shout.txt"],
    args = [
        "$(location words.txt)",
        "$(location shout.txt)",
    ],
    tool = "//tools:upper",
)

Two details we checked. write_file joins content with newlines and adds none at the end: ["hello", "world"] produced hello\nworld, so add "" for a trailing newline. And run_binary's tool is built in the exec configuration, exactly like genrule's tools (cquery showed //tools:upper (04bf134)).

Prefer run_binary over genrule when all you do is run one binary. There is no shell to quote, no $$, no set -u surprises, and it works on Windows. Each args entry reaches the tool as one argument, after $(location) expansion. The same prerequisite rule applies, with the same wording:

ERROR: rb/BUILD.bazel:3:11: in run_binary rule //rb:r: label '//rb:words.txt' in $(location) expression is not a declared prerequisite of this rule

Reach for genrule when you genuinely need a shell: a pipeline, a loop, several commands.

In bazel query --output=label_kind, real Bazel lists write_file targets as _write_file rule and copy_file as _copy_file rule: those two public names are macros wrapping private rules. run_binary and diff_test appear under their own names. (The simulator prints the public names.)

Remember: write_file for fixed text, copy_file to rename, run_binary to run one tool without a shell; genrule only when you need Bash.

Golden files and diff_test

pytest users know snapshot testing (syrupy, pytest-regressions): the expected output is stored in a file, the test compares, and a flag like --snapshot-update rewrites the file when the change is intended.

The Bazel version is the golden-file pattern. You check in the expected output (the golden), and a test compares it with what the generator produces now. Reviewers then see generated changes in code review as a diff of the golden, instead of trusting a tool blindly.

load("@bazel_skylib//rules:diff_test.bzl", "diff_test")

diff_test(
    name = "shout_golden_test",
    file1 = ":shout.txt",          # generated
    file2 = "shout.golden.txt",    # checked in
)

When they differ, the test fails with a diff in its log (< is file1, > is file2). We misspelled one line of the golden:

$ bazel test //golden:shout_golden_test --test_output=errors
FAIL: //golden:shout_golden_test (Exit 1) (see .../testlogs/golden/shout_golden_test/test.log)
INFO: From Testing //golden:shout_golden_test:
==================== Test output for //golden:shout_golden_test:
3c3
< CHERRY
---
> CHERY
FAIL: files "golden/shout.txt" and "golden/shout.golden.txt" differ.

Blessing a golden with bazel run

When the change is intended, you "bless" the new output: copy it over the golden. Doing that by hand from bazel-bin works, but teams make it a target. A small py_binary receives both files' rootpaths and writes into the source tree, which bazel run exposes as BUILD_WORKSPACE_DIRECTORY (M03):

py_binary(
    name = "update_golden",
    srcs = ["update_golden.py"],
    args = [
        "$(rootpath :shout.txt)",
        "$(rootpath shout.golden.txt)",
    ],
    data = [
        ":shout.txt",
        "shout.golden.txt",
    ],
)
import os
import shutil
import sys

generated, golden = sys.argv[1], sys.argv[2]
# `bazel run` starts in the runfiles tree; BUILD_WORKSPACE_DIRECTORY is your source tree.
target = os.path.join(os.environ["BUILD_WORKSPACE_DIRECTORY"], golden)
shutil.copyfile(generated, target)
print(f"Updated {golden}")
$ bazel run //golden:update_golden
INFO: Running command line: bazel-bin/golden/update_golden golden/shout.txt golden/shout.golden.txt
Updated golden/shout.golden.txt
$ bazel test //golden:shout_golden_test
//golden:shout_golden_test                                               PASSED in 0.0s
Executed 1 out of 1 test: 1 test passes.

Notice the rootpaths: golden/shout.txt, not bazel-out/.... The binary runs from its runfiles tree, where data files sit at their rootpath.

Why check generated files in at all, if Bazel can generate them? Two reasons: reviewers see the effect of a generator change, and tools outside Bazel (an IDE, pip install -e .) can still find the file. Keep the golden next to the BUILD file, name it *.golden.*, and add a comment telling people which target blesses it.

Remember: diff_test(file1 = generated, file2 = golden) fails with a diff; bless intended changes with a bazel run target that copies into BUILD_WORKSPACE_DIRECTORY.

Legacy macros: functions that write targets

When you copy-paste the same ten lines three times in Python, you write a function. BUILD files have no def (M01), so where does the function go?

Into a .bzl file: a Starlark file that may define functions, which BUILD files load(). A function there that declares targets is a macro. Since Bazel 8 this original kind is called a legacy macro, to distinguish it from symbolic macros (next section). A legacy macro runs during loading; when it returns, the package simply contains the targets it declared, as if you had written them by hand.

"""A legacy macro: upper-case a file and bundle the result."""

def _out_name(src):
    return src.replace(".txt", ".upper.txt")

def shouted_files(name, src, visibility = None):
    """Creates <name>_gen (a genrule) and <name> (a filegroup of its output)."""
    out = _out_name(src)
    native.genrule(
        name = name + "_gen",
        srcs = [src],
        outs = [out],
        tools = ["//tools:upper"],
        cmd = "$(location //tools:upper) $< $@",
        visibility = ["//visibility:private"],
    )
    native.filegroup(
        name = name,
        srcs = [":" + out],
        visibility = visibility,
    )
load("//tools/macros:shout.bzl", "shouted_files")

shouted_files(
    name = "a",
    src = "a.txt",
)

shouted_files(
    name = "b",
    src = "b.txt",
    visibility = ["//visibility:public"],
)
$ bazel query '//notes:*' --output=label_kind
source file //notes:BUILD.bazel
filegroup rule //notes:a
source file //notes:a.txt
generated file //notes:a.upper.txt
genrule rule //notes:a_gen
filegroup rule //notes:b
source file //notes:b.txt
generated file //notes:b.upper.txt
genrule rule //notes:b_gen

The conventions in that file are the ones every good macro follows:

  • native.genrule, not genrule. Inside a .bzl file, native rules live under native.. Forget it and loading fails: shout.bzl:10:5: name 'genrule' is not defined (did you mean 'subrule'?). Rules from rule sets (py_library, run_binary) are load()ed at the top of the .bzl and called directly.
  • A name parameter, and every target derived from it. The "main" target gets exactly name; helpers get name plus a suffix (_gen). Then two calls never clash, and users can guess labels. A clash is a loading error: Error in genrule: genrule rule 'a_gen' conflicts with existing genrule rule.
  • visibility passed through to the main target only. Callers control who uses the result; helpers stay private. With visibility = None, the package default applies.
  • Private helpers start with _. A BUILD file cannot load them.
  • A docstring saying which targets the macro creates.
ERROR: notes/BUILD.bazel:1:52: symbol '_out_name' is private and cannot be imported
ERROR: package contains errors: notes: symbol '_out_name' is private and cannot be imported

A .bzl file needs a package to live in: tools/macros/ must have a BUILD.bazel (an empty one is fine), or the load() label is invalid.

Seeing through a macro

Because a legacy macro just declares targets, bazel query --output=build shows what it expanded to, plus where each target came from:

$ bazel query //notes:a_gen --output=build
genrule(
  name = "a_gen",
  visibility = ["//visibility:private"],
  generator_name = "a",
  generator_function = "shouted_files",
  ...
  outs = ["//notes:a.upper.txt"],
  cmd = "$(location //tools:upper) $< $@",
)
# Rule a_gen instantiated at (most recent call last):
#   notes/BUILD.bazel:3:14           in <toplevel>
#   tools/macros/shout.bzl:10:19     in shouted_files

generator_function is queryable: bazel query 'attr(generator_function, shouted_files, //...)' lists every target any call of the macro created. The second lab grades with it.

print() debugging

print() works in .bzl files and shows up as a DEBUG line while the package loads:

DEBUG: tools/macros/shout.bzl:9:10: shouted_files: a.txt -> a.upper.txt
DEBUG: tools/macros/shout.bzl:9:10: shouted_files: b.txt -> b.upper.txt

Use it while writing a macro, then delete it. It prints for every call, for every user, in every build that loads the package; in a big repository that is noise in everyone's terminal. It also only prints when the package is actually re-loaded: our next build printed nothing, because Bazel had cached the loaded package. So a missing DEBUG line does not mean the code did not run earlier.

Run the commands below. Then add a third call, shouted_files(name = "c", src = "c.txt"), and predict which new targets //notes:* lists. Finally rename the call for b to name = "a" and read the error.

The simulator evaluates local .bzl files, native.*, and private-symbol rules like Bazel. It does not show print() output in the command box, does not support --output=build, and does not record generator_function; those are real-Bazel only.

Remember: a legacy macro is a .bzl function that calls native.* and loaded rules; derive every name from name; pass visibility to the main target; keep helpers _private; delete your print()s.

Symbolic macros: macro() in Bazel 8+

Legacy macros are just functions, so nothing stops a caller passing a list where a string belongs, or a macro naming a target gen that collides with the caller's. Bazel 8 added symbolic macros, declared with macro(). They look like rules from the outside, with typed attributes, and Bazel enforces the conventions you just learned.

def _shouted_impl(name, visibility, src):
    native.genrule(
        name = name + "_gen",
        srcs = [src],
        outs = [name + ".upper.txt"],
        tools = ["//tools:upper"],
        cmd = "$(location //tools:upper) $< $@",
    )
    native.filegroup(
        name = name,
        srcs = [name + ".upper.txt"],
        visibility = visibility,
    )

shouted = macro(
    doc = "Upper-cases src into <name>.upper.txt and wraps it in a filegroup.",
    implementation = _shouted_impl,
    attrs = {
        "src": attr.label(mandatory = True, allow_single_file = True, configurable = False),
    },
)
load("//tools/macros:shout_sym.bzl", "shouted")

shouted(
    name = "c",
    src = "c.txt",
)

That builds in Bazel 9.3.2 and creates //memo:c, //memo:c_gen, and //memo:c.upper.txt. The implementation receives name and visibility automatically, plus each declared attribute. What you get for the extra ceremony, each verified:

Typed attributes. Passing src = ["c.txt"] fails at the call site, naming the attribute:

Error: expected value of type 'string' for attribute 'src' of 'shouted', but got ["c.txt"] (list)

An unknown attribute is refused too: no such attribute 'out' in 'shouted' macro.

Naming enforced. Every target must be name or start with name plus _, -, or .. Our implementation renamed to name = "gen":

ERROR: memo/BUILD.bazel:3:8: in genrule rule //memo:gen: Target //memo:gen declared in symbolic macro 'c' violates macro naming rules and cannot be built. Name must be the same as the macro's name, or the macro's name followed by '_' (recommended), '-', or '.', and a non-empty string.

Visibility enforced. Targets inside a symbolic macro are private to the macro unless it passes visibility through. Even a target in the same package cannot reach the internal output :c.upper.txt; it must go through :c:

ERROR: memo/BUILD.bazel:8:10: in filegroup rule //memo:peek: Visibility error:
target '//memo:c.upper.txt' is not visible from
target '//memo:peek'

Two gotchas we hit. Attributes are configurable by default, meaning they arrive as a select(); passing one straight into native.genrule(srcs = [src]) failed with expected value of type 'string' for element 0 of attribute 'srcs' of 'genrule', but got select(...). Set configurable = False (as above) or pass the value through whole. And a label attribute arrives as a Label object, not a string.

The simulator does not implement macro() (it reports name 'macro' is not defined). Everything in this section is real Bazel 9.3.2 output; the exercises and labs use legacy macros, which you will meet in nearly every existing repository.

Which to write? For new macros shared across a big repository, symbolic macros are the recommended choice: their errors point at the caller, and their encapsulation keeps internals internal. Legacy macros are simpler, still fully supported, and what you will find in most existing repositories.

Remember: macro(implementation, attrs) gives typed attributes, enforced name-prefixed naming, and private internals; set configurable = False for attributes you pass to non-configurable places.

When a macro is the wrong tool

A macro, legacy or symbolic, only arranges existing rules. It runs at loading time, so it cannot see anything decided later:

  • It cannot read a file's contents or a dependency's outputs: those exist only at execution.
  • It cannot see providers (PyInfo) or transitive dependencies: those come from analysis.
  • It cannot resolve a select(): configuration is not known yet.
  • It cannot declare outputs it learns about at run time (a directory of unknown files).

If you need any of those, you need a custom rule (rule() with an implementation function, providers, and ctx.actions). That is Level 3 of this course; see the roadmap. Two signals you have outgrown a macro: you are writing ever more elaborate Bash inside a genrule cmd, or you wish the macro could look at what its dependencies contain.

The opposite mistake is common too. A macro that wraps exactly one rule and renames an attribute adds a layer people must read through, and buys nothing. Write a macro when it removes real repetition (several targets that always travel together) or encodes a team convention.

Remember: macros compose rules at loading time; anything that needs file contents, providers, or configuration needs a custom rule (Level 3).

//build_info:version_py writes a Python module from the VERSION file in the same package, but analysis fails with "is not a declared prerequisite of this rule". Make it build. Keep using $(location ...): do not hard-code a path.

Hint

$(location X) only expands labels in srcs, tools, or outs. Which attribute is for files the command reads?

Show solution 
genrule(
    name = "version_py",
    srcs = ["VERSION"],
    outs = ["_version.py"],
    cmd = "echo \"__version__ = '$$(cat $(location VERSION))'\" > $@",
)

With exactly one input, $< also works. Note $$(cat ...): the doubled $ passes a shell command substitution through Bazel untouched.

//data:split should write the CSV header to header.csv and the rows to rows.csv, but it uses $@, which fails with "variable '$@' : more than one output file". Rewrite cmd so it builds, writing each output through its own $(location ...). Keep both outputs.

Hint

Outputs are prerequisites too, so $(location header.csv) is allowed. $< is fine: there is one input.

Show solution 
genrule(
    name = "split",
    srcs = ["prices.csv"],
    outs = [
        "header.csv",
        "rows.csv",
    ],
    cmd = "head -n 1 $< > $(location header.csv) && tail -n +2 $< > $(location rows.csv)",
)

Users can now depend on //data:rows.csv alone, or on //data:split for both.

def _toc_name(name):
    """The output file for markdown_toc(name = ...). Private: BUILD files cannot load it."""
    return name + ".toc.md"

def markdown_toc(name, src, visibility = None):
    """Generates a table of contents for one Markdown file. (Docstring as in the starter.)"""

    native.genrule(
        name = name + "_gen",
        srcs = [src],
        outs = [out],
        tools = ["//tools:toc"],
        cmd = "$(location //tools:toc) $< $@",
        visibility = ["//visibility:private"],
    )
    native.filegroup(
        name = name,
        srcs = [":" + out],
        visibility = visibility,
    )

Quiz

Recap

  • A generator is an action. Bazel needs its outputs declared in advance so it can plan, cache, and re-run it exactly when inputs change.
  • genrule: srcs (read), outs (names written), tools (programs run), cmd (Bash). Outputs land in bazel-bin/<package>/.
  • Every out is a generated file target; use it by label like a source file, and name the rule differently from its outputs.
  • Make variables write paths for you: $(location)/$(execpath) in commands, $(rootpath) for runfiles, $@/$< only with exactly one file, $$ for the shell.
  • Programs go in tools (exec configuration); a binary in srcs fails with "expands to more than one file".
  • Undeclared inputs fail in the sandbox, undeclared outputs vanish, missing declared outputs fail, and globs never see generated files.
  • Prefer skylib's write_file, copy_file, and run_binary; keep genrule for real shell work.
  • diff_test plus a checked-in golden makes generated changes reviewable; bless with a bazel run target writing into BUILD_WORKSPACE_DIRECTORY.
  • Legacy macros are .bzl functions using native.*; derive names from name, pass visibility to the main target, keep helpers _private, and remove print()s.
  • Symbolic macros add typed attributes, naming rules, and encapsulation; anything needing file contents or providers needs a custom rule.
