Python with rules_python

You already know how Python finds modules, where your data files live, and which interpreter runs your code. Bazel changes all three answers. This module shows what rules_python does with your .py files, why your imports and file paths behave differently, and how to write BUILD files that work on every machine.

⏱ ~2.5 hoursPrerequisites: M02
  • Write py_library, py_binary, and py_test targets with the right srcs, deps, data, and main
  • Predict how an import resolves under Bazel, and use imports for a src/-layout package
  • Explain runfiles, ship a data file with data, and find it at run time with the rules_python runfiles library
  • Describe the hermetic Python toolchain from MODULE.bazel and pin a target to another version with python_version
  • Write unittest tests that Bazel runs, and read a failing test's log
  • Choose between bazel run and running bazel-bin/... directly, and know what changes

Three rules for Python code

In a normal project, a "library" is a directory with an __init__.py, an "application" is a module you run with python -m or a [project.scripts] entry, and a "test" is any file pytest discovers by name. None of that is declared anywhere; it is convention.

Bazel makes each of those a declared target. rules_python, the Python rule set, gives you three rules:

py_library

Python code other targets import. It does not run by itself. It hands its files and import paths to whoever depends on it.

py_binary

A program. Bazel builds an executable launcher you start with bazel run.

py_test

A py_binary that bazel test runs. Exit code 0 means PASSED; anything else is FAILED.

All three share the same core attributes. An attribute is a named argument of a rule, like a keyword argument of a function:

AttributeOnWhat it means
srcsall threeThe .py files that belong to this target. Only files in the same package, written as relative paths.
depsall threeOther Python targets this code imports: py_library labels, later PyPI packages (M04).
dataall threeFiles needed at run time but not imported: JSON, templates, fixtures. See Runfiles.
importsall threeExtra directories, relative to the package, to put on sys.path. See src layout.
mainbinary, testWhich file in srcs is the entry point. Defaults to <name>.py.
python_versionbinary, testRun with a specific registered Python, such as "3.12".
args, envbinary, testCommand-line arguments and environment variables added by bazel run and bazel test.

Here is a small workspace with all three. Run the commands, then try changing kind(py_test, //...) to kind(py_library, //...).

srcs takes files of this package. A common first attempt is srcs = ["hello.py", "//lib:greeting.py"], borrowing another package's file. Real Bazel rejects it: no such target '//lib:greeting.py' if lib/BUILD.bazel never mentions the file, or a visibility error if a rule there uses it. Even when allowed, the file would belong to two targets. Depend on the py_library that owns the file instead.

Remember: srcs is what you own, deps is what you import, data is what you open. Every Python file lives in exactly one target's srcs.

How imports work under Bazel

When you run python hello/hello.py, Python puts hello/ on sys.path, so from greeting import greeting works. With pip install -e ., your package's parent directory is on the path instead. Either way, the answer depends on how you started Python.

Under Bazel, the answer is fixed: the workspace root is on sys.path, and every import is written as a path from there. A file at hello/greeting.py is the module hello.greeting:

from hello.greeting import greeting

print(greeting("Bazel"))

The "it worked when I ran it directly" import, from greeting import greeting, fails under bazel run, because hello/ itself is not on the path:

  File "/root/.cache/bazel/_bazel_root/c29f10e04db78a29c46b057dc668bb52/execroot/_main/bazel-out/k8-fastbuild/bin/hello/hello.runfiles/_main/hello/hello.py", line 3, in <module>
    from greeting import greeting
ModuleNotFoundError: No module named 'greeting'

Why make every import absolute from the root? Because in a monorepo, two packages can each have a utils.py. import utils would be ambiguous; from billing.utils import ... and from search.utils import ... never are.

There is a second rule: an import only works if the file is in your target's transitive deps. Bazel builds each program a private tree containing only the files it declared (the runfiles, below). A module that exists in your repository but is not a dependency is simply not there.

Predict what deps(//app:report) returns, then run it. Remember that deps includes the target itself and its source files.

report.py can import money.fmt and money.rounding (it gets the transitive closure), but import money.currency would fail at run time: nothing in the graph pulls it in. Leaning on a transitive dependency is legal but fragile; if report.py imports money.rounding directly, list //money:rounding in its own deps.

Teams usually enforce "declare what you import" with a tool such as Gazelle's Python extension, which generates deps from your import statements. Until then, the rule of thumb: every import of first-party code maps to one label in deps.

Remember: imports start at the workspace root (from hello.greeting import ...), and only declared dependencies are importable.

py_binary's main file

A py_binary needs to know which file to run. Without a main attribute it looks for a file named after the target: name = "server" means server.py must be in srcs. Python developers often call the entry point main.py or __main__.py, which trips this immediately.

Do not be scared by the traceback. It is a Starlark stack trace through rules_python's own code; the line that matters is Error in fail:, the message the rule author wrote for you. This is an analysis error (M02): the BUILD file loaded fine, but the rule rejected its attributes.

Two fixes. Rename the target or file so they match, or say which file is the entry point:

    srcs = ["main.py"],
    main = "main.py",
)

main must name a file that is also in srcs; otherwise the error is could not find 'main.py' as specified by 'main' attribute. The same rule applies to py_test: a test named routes_test whose file is tests/test_routes.py needs main = "tests/test_routes.py".

Try it: the build fails. Add main = "main.py", and build again.

Remember: no main means <name>.py. When the names differ, set main to a file that is in srcs.

Runfiles: how data files travel with a program

Your code probably opens files with open("data/prices.json") (relative to wherever you started Python) or Path(__file__).parent / "prices.json". Both assume the source tree is right there at run time. Packaging tools then need package_data or MANIFEST.in to ship those files.

A Bazel program does not run from your source tree. When Bazel builds //app:prices, it also builds its runfiles: a directory of everything the program needs at run time, laid out by workspace path. It holds the program's own .py files, every transitive dependency's files, the Python interpreter, and any file listed in data. In this sandbox it is a tree of symlinks next to the launcher.

py_binary(
    name = "prices",
    srcs = ["prices.py"],
    data = ["//data:prices.json"],
    deps = ["@rules_python//python/runfiles"],
)
exports_files(["prices.json"])

The file lives in another package, so data/BUILD.bazel must let other packages refer to it. exports_files does that (M02). Without it, real Bazel says:

ERROR: /home/claude/bazel-practicum/build/scratch-m03/demo/app/BUILD.bazel:15:10: no such target '//data:prices.json': target 'prices.json' not declared in package 'data' defined by /home/claude/bazel-practicum/build/scratch-m03/demo/data/BUILD.bazel; however, a source file of this name exists.  (Perhaps add 'exports_files(["prices.json"])' to data/BUILD.bazel?) and referenced by '//app:prices'
ERROR: Analysis of target '//app:prices' failed; build aborted: Analysis failed

After a build, the runfiles tree for //app:prices looks like this (abridged: the interpreter and the virtual environment rules_python creates are left out):

MANIFEST
_main/                       # your workspace, the "main repository"
    app/prices                 # the launcher
    app/prices.py
    data/prices.json           # because of data = [...]
_repo_mapping
rules_python+/               # the runfiles library, because of deps
rules_python++python+python_3_13_x86_64-unknown-linux-gnu/   # the interpreter

_main is the canonical name of your own workspace in Bzlmod. Other modules get names like rules_python+.

The current-directory trap

Here is the naive version of the program:

import json

with open("data/prices.json") as f:
    prices = json.load(f)
print("total:", sum(prices.values()))

bazel run //app:prices_naive prints total: 7, because bazel run starts the program inside its runfiles tree, at _main/. Run the same launcher from another directory and it breaks:

cd /tmp && ~/practicum/bazel-bin/app/prices_naive
  File "/home/claude/bazel-practicum/build/scratch-m03/demo/bazel-bin/app/prices_naive.runfiles/_main/app/prices_naive.py", line 3, in <module>
    with open("data/prices.json") as f:
         ~~~~^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'data/prices.json'

Tools that call your binary (a genrule, another program, a test harness, a deploy script) will not start it in the right directory. The program needs to find its runfiles on its own.

The rules_python runfiles library

rules_python ships a small library for exactly that. Add @rules_python//python/runfiles to deps and ask it where a runfile is:

import json

from python.runfiles import runfiles

r = runfiles.Create()
path = r.Rlocation("_main/data/prices.json")
with open(path) as f:
    prices = json.load(f)
print("total:", sum(prices.values()))

runfiles.Create() reads environment variables the launcher sets (such as RUNFILES_MANIFEST_FILE) to locate the tree. Rlocation() turns a runfiles path, the repository name plus the path inside it, into a real path on disk. It works from any directory, under bazel run, bazel test, or started directly:

INFO: Running command line: bazel-bin/app/prices
total: 7
  • from python.runfiles import runfiles and from python.runfiles import Runfiles (then Runfiles.Create()) both work; the package is named python.runfiles because it lives at python/runfiles/ in the rules_python repository.
  • The path starts with the repository: _main/data/prices.json. Your module name works too (practicum/data/prices.json), because the library translates it through _repo_mapping. Without the prefix, "data/prices.json" returns None.
  • Rlocation returns None rather than raising when the path is not a runfile, so open(None) fails with TypeError: expected str, bytes or os.PathLike object, not NoneType. That message means "wrong runfiles path, or missing from data".
  • Forgetting the deps entry gives ModuleNotFoundError: No module named 'python'.

Why not Path(__file__).parent? It happens to work for a file in the same directory, because __file__ is inside the runfiles tree. It breaks for files from other repositories, for files Bazel generates, and on Windows, where runfiles are often a manifest rather than a directory of symlinks. The library handles all of those.

Predict the output of the first command, then run both.

A data file is a real edge in the graph. Change prices.json and Bazel knows //app:prices, and every test that runs it, is affected. Click prices.json below.

Remember: list run-time files in data, export them from their package, and open them with runfiles.Create().Rlocation("_main/..."), never with a path relative to the current directory.

The imports attribute and src layout

Many modern packages use a src layout: pyproject.toml at the top, code in src/textstats/, tests in tests/. pip install -e . puts src/ on sys.path, so tests write import textstats.

Bring that package into a Bazel workspace at libs/textstats/. By the workspace-root rule, its module name would be libs.textstats.src.textstats. The test's import textstats fails:

  File "/root/.cache/bazel/_bazel_root/e111c9b5178f1131837654c4f3af2bf6/sandbox/linux-sandbox/1/execroot/_main/bazel-out/k8-fastbuild/bin/libs/textstats/counting_test.runfiles/_main/libs/textstats/tests/counting_test.py", line 3, in <module>
    from textstats import word_count
ModuleNotFoundError: No module named 'textstats'

The imports attribute adds directories to sys.path, relative to the package, for this target and everything that depends on it:

load("@rules_python//python:defs.bzl", "py_library", "py_test")

py_library(
    name = "textstats",
    srcs = [
        "src/textstats/__init__.py",
        "src/textstats/counting.py",
    ],
    imports = ["src"],   # puts libs/textstats/src on sys.path
    visibility = ["//visibility:public"],
)

py_test(
    name = "counting_test",
    srcs = ["tests/counting_test.py"],
    deps = [":textstats"],
)
//libs/textstats:counting_test                                           PASSED in 0.3s
Executed 1 out of 1 test: 1 test passes.

Notice the test's srcs reaches into a subdirectory, tests/. That is fine: a package owns every directory below it that has no BUILD file of its own.

Use imports for code with an established import name (a src-layout package, vendored code). Do not sprinkle imports = ["."] to make from greeting import ... work: it puts every such package on the path, and two utils.py files will shadow each other.

Query which targets change the import path:

//libs/textstats is short for //libs/textstats:textstats: when the target is named after its package, you can drop the :name.

Remember: imports = ["src"] is Bazel's pip install -e . for a src layout. It is relative to the package and inherited by dependents.

The hermetic Python toolchain

With Pixi, your environment pins Python, and everyone who runs pixi install gets the same one. Without it, python3 means whatever is first on PATH.

Bazel takes the Pixi idea further. These two lines in MODULE.bazel register a toolchain, Bazel's word for a tool a rule needs, chosen by Bazel rather than found on PATH:

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(python_version = "3.13", is_default = True)

rules_python downloads a standalone CPython 3.13 build into Bazel's cache and puts it in every Python target's runfiles. Your system Python is never used to run your code. The build is hermetic: its result depends only on declared inputs, so a laptop and CI produce the same thing.

You can see it from inside a program. This one prints sys.version and the sys.path entries that hold the standard library (paths shortened to the part after whereami.runfiles/):

version: 3.13.18
path: rules_python++python+python_3_13_x86_64-unknown-linux-gnu/lib/python313.zip
path: rules_python++python+python_3_13_x86_64-unknown-linux-gnu/lib/python3.13
path: rules_python++python+python_3_13_x86_64-unknown-linux-gnu/lib/python3.13/lib-dynload

More than one version

python_version on a binary or test picks another registered toolchain. It must be registered first; asking for "3.12" when only 3.13 exists fails toolchain resolution:

ERROR: /home/claude/bazel-practicum/build/scratch-m03/demo/hello/BUILD.bazel:20:10: While resolving toolchains for target //hello:hello312 (ffe5c97): No matching toolchains found for types:
  @@bazel_tools//tools/python:toolchain_type
To debug, rerun with --toolchain_resolution_debug='@@bazel_tools//tools/python:toolchain_type'
For more information on platforms or toolchains see https://bazel.build/concepts/platforms-intro.
ERROR: Analysis of target '//hello:hello312' failed; build aborted

Register it next to the default, and both versions live in one workspace:

python.toolchain(python_version = "3.13", is_default = True)
python.toolchain(python_version = "3.12")
py_binary(
    name = "hello312",
    srcs = ["hello.py"],
    main = "hello.py",
    python_version = "3.12",
    deps = [":greeting"],
)
INFO: Running command line: bazel-bin/hello/hello312
Hello, Python 3.12.16!

The same hello.py run as //hello:hello prints Hello, Python 3.13.18!. The library :greeting is built for whichever version the binary uses.

Pixi pins your development tools here (Bazelisk). Bazel pins the Python that builds and tests your code. Why might a team want those to be separate?

Remember: python.toolchain(...) in MODULE.bazel decides which Python runs your code; the system Python does not matter. python_version picks among registered versions.

Tests with py_test and unittest

pytest discovers test_*.py files, imports them, and runs every test_* function. You never write a __main__ block.

py_test does no discovery. It runs the main file as a script, exactly like a py_binary, and reads one thing: the exit code. pytest needs a PyPI dependency, which arrives in M04. Until then, use the standard library's unittest, and end every test file with the block that runs it:

import unittest

from calc.calc import add


class AddTest(unittest.TestCase):
    def test_add(self) -> None:
        self.assertEqual(add(2, 2), 4)


if __name__ == "__main__":
    unittest.main()

Forget the last two lines and the script defines a class, exits 0, and Bazel reports PASSED, even when the test would fail. This is real output for a calc.add that subtracts, without unittest.main():

//calc:calc_test                                                         PASSED in 0.5s
Executed 1 out of 1 test: 1 test passes.

Because bazel run changes directory, a CLI tool that takes file arguments should resolve them against os.environ["BUILD_WORKING_DIRECTORY"]. BUILD_WORKSPACE_DIRECTORY holds the workspace root, handy for formatters and code generators that write into your source tree.

Use bazel run while developing. Run bazel-bin/... directly when you want to start the program many times without Bazel in the loop, or from another tool. Thanks to runfiles, both find their data.

Remember: bazel run = build + args + env + start in the runfiles tree. The bazel-bin launcher works anywhere but adds nothing from the BUILD file.

The __init__.py warning

Your first build with rules_python 2.4.6 prints a big block like this once per target, labeled DEBUG:

DEBUG: /root/.cache/bazel/_bazel_root/dfba37e78417d24b06edbffb8257816f/external/rules_python+/python/private/py_executable.bzl:1582:14:
======================================================================
WARNING: Target @@//hello:hello is using implicit __init__.py creation.
  This diabolic behavior is deprecated and will be disabled by default in a
  future release.
  See https://github.com/bazel-contrib/rules_python/issues/2945

  Ensure all __init__.py files are explicitly created and
  added to the srcs or deps of your targets.

  Disable implicit creation for your module in MODULE.bazel:

    rules_python_config = use_extension("@rules_python//python/extensions:config.bzl", "config")
    rules_python_config.explicit_init_py(default = True)

  Or for a specific target by setting:

    legacy_create_init = 0

  Or globally with the following Bazel flag:

    --incompatible_default_to_explicit_init_py
======================================================================

What it means: by default, rules_python writes an empty __init__.py into every directory of the runfiles tree that lacks one. That is why from hello.greeting import greeting worked even though hello/ has no __init__.py: Bazel quietly made hello a regular package.

The behavior is deprecated because it surprises people. It turns every directory into a package, which breaks namespace packages (PEP 420: packages split across directories, with no __init__.py), and the files exist only under Bazel, so code behaves differently outside it.

It is a warning, not an error. Bazel only prints it when it re-analyzes the target, so it disappears on the next build and comes back when you edit the BUILD file. To opt in to the future behavior now, add the config lines it suggests to MODULE.bazel. The warning goes away, and no __init__.py files are generated:

rules_python_config = use_extension("@rules_python//python/extensions:config.bzl", "config")
rules_python_config.explicit_init_py(default = True)

With that set, the examples in this module still work. Python 3 treats a directory without __init__.py as a namespace package, so hello.greeting still imports. Real __init__.py files you list in srcs, like src/textstats/__init__.py, are always kept.

For new workspaces, set explicit_init_py(default = True) from day one and commit real __init__.py files where your code needs them. Labs in this course leave it unset so you recognize the warning when you meet it in existing repositories.

Remember: the DEBUG block is a deprecation notice about generated __init__.py files. It is safe to ignore while learning, and one MODULE.bazel setting turns it off.

Practice

Exercises run in the simulator, which checks the BUILD graph: targets, labels, visibility, attributes. It cannot run Python, so the labs that follow prove the programs actually work.

//app:hello tries to use greeting.py from the lib package by listing it in its own srcs. That fails analysis (run bazel build //... under "Try commands"), and it is the wrong shape anyway.

Make lib/greeting.py a py_library named //lib:greeting, visible only to the app package (not public), and have //app:hello depend on it. The binary's srcs should list only its own file.

Hint

In lib/BUILD.bazel: load py_library, set srcs = ["greeting.py"] and visibility = ["//app:__pkg__"]. In app/BUILD.bazel, move the label from srcs to deps, pointing at the target rather than the file.

Show solution

Quiz

Recap

  • py_library is importable code, py_binary a program, py_test a program whose exit code is the verdict.
  • srcs lists your own files, deps what you import, data what you open at run time.
  • Imports start at the workspace root, and only declared (transitive) dependencies are importable. imports = ["src"] adapts a src-layout package.
  • Without main, a binary or test needs <name>.py in srcs.
  • Runfiles are a program's private run-time tree. Find files in it with runfiles.Create().Rlocation("_main/...") from @rules_python//python/runfiles.
  • python.toolchain in MODULE.bazel gives a hermetic interpreter; python_version selects another registered one.
  • unittest files need unittest.main(); failing output is in test.log or shown with --test_output=errors.
  • bazel run adds a build, args, env, and the runfiles working directory; bazel-bin/... adds nothing.
  • The implicit __init__.py DEBUG block is a deprecation notice; explicit_init_py(default = True) opts out.
