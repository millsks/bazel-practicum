How This Practicum Works

Bazel is a build and test tool that knows every file and every dependency in your repository, so it can rebuild and retest only what changed, the same way on every machine. This module explains what that buys you, how the course lets you practice it in the page and on your own machine, and gets you to your first real build.

Why Bazel?

In a Python project you probably run pip install -e . once, then pytest whenever you change something. pytest has no idea what you changed, so it runs everything (or whatever you point it at). If a test quietly depends on a file it never declared, it still works on your laptop, until it doesn't on CI.

That works well for one package. It strains when a repository holds dozens of services and libraries, in several languages, with code generators in between. Three questions get hard to answer:

  1. What do I need to rebuild and retest after this change? Usually "everything", because nothing knows.
  2. Is this build the same as CI's? Only if every tool, version, and environment variable matches.
  3. Why is the build slow? Because every machine redoes work another machine already did.

Bazel answers them by making you declare the build. Each directory that holds code gets a BUILD.bazel file listing targets: a library, a binary, a test. Each target lists its source files and the other targets it depends on. From those declarations Bazel builds a graph of the whole repository. Then:

Correct

Actions run in a sandbox that only contains their declared inputs. A forgotten dependency fails loudly instead of working by accident.

Incremental

Every action is keyed by a hash of its inputs. Change one file and only the actions downstream of it run again.

Cached and shared

Because keys are content hashes, results can come from a cache, including a remote one CI and your teammates share.

Polyglot

Python, Go, Java, C++, protobuf, and shell all live in one graph, so a Python test can depend on a Go binary.

Try the visualizer below. Click fmt.py, then main.py. Which targets re-run each time, and which tests can Bazel skip? This one picture is most of why teams adopt Bazel.

A single Python package with a few dozen tests does not need Bazel: pixi plus pytest is simpler and faster to set up. Bazel pays off with many packages, several languages, generated code, slow CI, or a need for reproducible builds. It costs you BUILD files to maintain and a new tool for the team to learn. This course teaches it so you can judge that trade with experience instead of hype.

The words you will see everywhere

You will meet these in the first ten minutes of any Bazel project. Each gets a full module later; for now, a sketch:

Workspace (or repository)
The directory tree Bazel builds. Its root holds a MODULE.bazel file.
Module
A versioned unit of Bazel code you depend on, such as rules_python, fetched from the Bazel Central Registry. Your workspace is a module too.
Package
A directory with a BUILD.bazel (or BUILD) file, plus everything below it that is not another package.
Target
Something in a package that Bazel can build: a rule (like py_binary) or a file.
Label
A target's name: //hello:greeting means "the target greeting in the package hello".
Rule
A kind of target, such as py_library, go_test, or genrule. Rules come from rule sets you load.
Starlark
The language of BUILD and .bzl files: a small, deterministic dialect of Python.

Three files every workspace starts with

Here is the smallest useful Python workspace, the one you will build for real at the end of this module:

first_build/
├── .bazelversion          # which Bazel to run
├── MODULE.bazel           # this workspace's name and its dependencies
└── hello/
    ├── BUILD.bazel        # the targets in package //hello
    ├── greeting.py
    ├── greeting_test.py
    └── hello.py
9.3.2

.bazelversion pins the Bazel release. You do not install Bazel itself: you install Bazelisk, a small launcher that reads this file, downloads that exact Bazel once, and runs it. Every developer and every CI machine then runs the same Bazel.

module(name = "first_build")

bazel_dep(name = "rules_python", version = "2.4.6")

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(python_version = "3.13", is_default = True)

MODULE.bazel names your module and declares what it depends on. Here: the Python rules, and a Python 3.13 interpreter that Bazel downloads itself, so builds never depend on whichever Python happens to be on your machine. Module 04 covers this file in depth.

load("@rules_python//python:defs.bzl", "py_binary", "py_library", "py_test")

py_library(
    name = "greeting",
    srcs = ["greeting.py"],
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":greeting"],
)

py_test(
    name = "greeting_test",
    srcs = ["greeting_test.py"],
    deps = [":greeting"],
)

BUILD.bazel declares targets. Read it top to bottom: load three rules from rules_python; a library made of greeting.py; a binary made of hello.py that uses the library; a test that uses it too. ":greeting" is a label relative to this package, short for //hello:greeting.

Bazel 9 removed the old WORKSPACE file (Bzlmod and MODULE.bazel replaced it) and no longer loads rule sets automatically. Older tutorials skip the load() line and use WORKSPACE; with Bazel 9 both fail. If a guide you find online has a WORKSPACE file, it predates Bazel 8.

The simulator in this page

Real Bazel needs a JVM, downloads, and a file system, so it cannot run in a browser. Instead, each lesson includes sandboxes backed by minibazel, the course's model of Bazel written in Python and run in your browser. It reads the files in the sandbox and answers the way Bazel 9.3 would during its first two phases: which targets exist, whether they are valid, and what depends on what.

This sandbox holds the workspace from the previous section. Run the first command, then try the others. The first run takes a few seconds while Python loads in your browser.

Now break it. Delete the load(...) line in hello/BUILD.bazel and run bazel build //hello:hello again. You get the most common Bazel 9 error there is.

The simulator models loading (evaluating BUILD files) and analysis (checking the graph: labels, visibility, dependency types, select()), plus bazel query and cquery. It never runs a program, a test, or a compiler. So bazel test here tells you which tests would run, not whether they pass. Anything that needs execution (test results, caching, generated files, real timings) is in a lab, which runs real Bazel on your machine.

Sandboxes reset with the Reset button. Exercises save your edits in this browser.

Labs: real Bazel on your machine

Each module ends with one or two labs. A lab is a small workspace in the bazel-practicum repository, with a starter you edit and a grader that runs real Bazel commands against it. Set up once:

git clone https://github.com/millsks/bazel-practicum.git
cd bazel-practicum
pixi install            # Python tooling and Bazelisk, from conda-forge
pixi run bazel version  # Bazelisk downloads Bazel 9.3.2 on first use

Then, for any lab:

pixi run labs                 # list labs and which you have started
pixi run start m00-lab1       # copy the starter to work/m00-lab1/
cd work/m00-lab1
pixi run bazel build //...    # work on it with real Bazel
cd ../..
pixi run grade m00-lab1       # run the lab's checks

Pixi installs Bazelisk, and this repository puts a small bazel wrapper for it on PATH, so pixi run bazel ... works from any directory inside the clone (or run pixi shell once and type bazel ...). For a workspace outside the repository, pixi add bazelisk and run pixi run bazelisk .... Nothing else to install: no Homebrew, no system Python, no Java. Bazel ships its own JDK.

The grader copies your workspace to build/labs/, adds any grading files, runs each check, and prints what passed. Your copy in work/ is never modified, so grade as often as you like.

The first lab downloads Bazel (about 60 MB), a Python toolchain, and rule sets. Later labs reuse Bazel's repository cache, so they start in seconds.

Reading Bazel's output

A successful real build is quiet. This is bazel run //hello:hello from the lab's solution:

INFO: Found 1 target...
Target //hello:hello up-to-date:
  bazel-bin/hello/hello
INFO: Elapsed time: 0.229s, Critical Path: 0.00s
INFO: 1 process: 1 internal.
INFO: Build completed successfully, 1 total action
INFO: Running command line: bazel-bin/hello/hello
Hello, Bazel!

Everything Bazel builds lands under bazel-bin/, a symlink Bazel creates in your workspace (with bazel-out, bazel-testlogs, and bazel-<name>). Never edit or commit them; add bazel-* to .gitignore.

An error names a file, line, and column, then says what is wrong. This is the untouched lab starter:

ERROR: hello/BUILD.bazel:3:1: name 'py_library' is not defined (did you mean 'cc_library'?)
ERROR: hello/BUILD.bazel:8:1: name 'py_binary' is not defined (did you mean 'cc_binary'?)
ERROR: package contains errors: hello: name 'py_library' is not defined (did you mean 'cc_library'?)

Three habits make Bazel errors easy:

  1. Read the first ERROR line first. Later lines are usually consequences ("package contains errors", "Build did NOT complete").
  2. Go to the location. hello/BUILD.bazel:3:1 is line 3, column 1.
  3. Ignore the guess when it is wrong. Bazel suggests cc_library because it is the closest built-in name; the real fix is loading py_library from rules_python.

Practice

Exercises are checked in the page by the simulator. Edit the files, press Check, and read each check's message. You can also open "Try commands" to run bazel against your edits.

This BUILD file uses py_library and py_binary but Bazel 9 cannot find them. Add the load() statement that makes both available, so bazel build //hello:hello succeeds.

Hint

The rules live in the file @rules_python//python:defs.bzl. load() takes the file's label first, then the names you want from it.

Show solution 
load("@rules_python//python:defs.bzl", "py_binary", "py_library")

py_library(
    name = "greeting",
    srcs = ["greeting.py"],
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":greeting"],
)

Order inside load() does not matter; alphabetical is the convention (Buildifier, Bazel's formatter, sorts them for you).

The package has a test file, greeting_test.py, but no target for it, so bazel test //... finds nothing to run. Add a py_test named greeting_test that tests the greeting library. Then bazel test //... should select exactly //hello:greeting_test.

Hint

A py_test looks like a py_binary: name, srcs, and deps. Do not forget to load it.

Show solution 
load("@rules_python//python:defs.bzl", "py_binary", "py_library", "py_test")

py_library(
    name = "greeting",
    srcs = ["greeting.py"],
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":greeting"],
)

py_test(
    name = "greeting_test",
    srcs = ["greeting_test.py"],
    deps = [":greeting"],
)

Someone renamed the library to greeter but forgot a reference. Run bazel build //... under "Try commands" to see the error, then fix the BUILD file so everything builds. Keep the library's new name.

Hint

The error says no such target '//hello:greeting', "referenced by '//hello:hello'". Which attribute of hello mentions :greeting?

Show solution 
load("@rules_python//python:defs.bzl", "py_binary", "py_library")

py_library(
    name = "greeter",
    srcs = ["greeting.py"],
)

py_binary(
    name = "hello",
    srcs = ["hello.py"],
    deps = [":greeter"],
)

The file is still greeting.py: target names and file names are independent. That is why renaming a target needs updating every label that points at it, which bazel query 'rdeps(//..., //hello:greeter)' (Module 09) finds for you.

Quiz

Recap

  • Bazel builds from a declared graph of targets, so it rebuilds and retests only what a change affects, and can share results through caches.
  • A workspace starts with .bazelversion (which Bazel), MODULE.bazel (which dependencies), and BUILD files (which targets).
  • Bazel 9 has no WORKSPACE and no autoloads: every rule set is declared in MODULE.bazel and loaded in BUILD files.
  • Labels like //hello:greeting name targets; :greeting is relative to the current package.
  • Sandboxes and exercises use an in-page simulator of loading, analysis, and query; labs use real Bazel through pixi run start and pixi run grade.
  • Read the first ERROR line, go to its file:line:col, and treat later lines as consequences.
