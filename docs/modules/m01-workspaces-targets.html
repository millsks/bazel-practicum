Stage 1 · Foundations · Module 01

Workspaces, Packages & Targets

Every Bazel command names things: //app:cli, //..., @rules_python//python:defs.bzl. This module teaches the addressing system behind those names: where a workspace starts, how directories become packages, how a label points at exactly one target, and how patterns select many. Get this right and most "no such target" errors stop being mysterious.

⏱ ~2 hoursPrerequisites: M00
  • Say what makes a directory a workspace root, and what module(name = ...) is for
  • Explain packages and the subpackage boundary, including why glob() stops at a subpackage
  • Read and write labels in every form: absolute, relative, external, and the //pkg shorthand
  • Tell rule targets, source file targets, and generated file targets apart
  • Select targets with patterns: //..., //pkg/..., :all, :*, and exclusions after --
  • Use bazel build, run, test, and query, and find outputs through the convenience symlinks

The workspace root: MODULE.bazel

A Python project's root is wherever pyproject.toml (or pixi.toml) lives. Tools find it by walking up from your current directory until they see that file. pytest does the same to find its rootdir.

Bazel works the same way. The workspace is the directory tree Bazel builds, and its root is the nearest directory, at or above where you run bazel, that contains a file named MODULE.bazel. Everything below it is "the main repository".

Run Bazel anywhere without one and it refuses before doing anything:

ERROR: Bazel 'build' must be invoked from within a workspace (below a directory having a MODULE.bazel file).
See documentation at https://bazel.build/concepts/build-ref#workspace

Because Bazel searches upward, you can run commands from any subdirectory. bazel info workspace prints the root it found:

pixi run bazel info workspace
/work/handbook

Real output on this page comes from runs of Bazel 9.3.2. Absolute paths are shortened to /work/<workspace>; on your machine you will see your own directory there.

What goes in MODULE.bazel

The file can even be empty: an empty MODULE.bazel still marks the root. In practice it starts with one call that names your module:

module(name = "greeter")

bazel_dep(name = "rules_python", version = "2.4.6")

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(python_version = "3.13", is_default = True)

A module is Bazel's unit of versioned code, like a distribution on PyPI. Your workspace is the root module; rules_python is a module you depend on. module(name = "greeter") gives yours a name, which matters when someone else depends on it or when a label names your repository explicitly. Leave it out and Bazel uses an empty name:

# MODULE.bazel is empty
<root> (@_)

# MODULE.bazel says module(name = "handbook")
<root> (handbook@_)

bazel_dep and use_extension declare dependencies; Module 04 covers them. For this module, remember one thing: the name on the left of a bazel_dep becomes the @rules_python you type in labels.

Older tutorials mark the root with a WORKSPACE or WORKSPACE.bazel file. Bazel 9 removed that system. If you clone a project with only a WORKSPACE file, Bazel 9 will not treat it as a workspace at all; it needs a MODULE.bazel.

Your repository has MODULE.bazel at the top and you run bazel build //... from services/api/. Which directory does // refer to? (The workspace root, not your current directory. // always means the root.)

BUILD files and packages

In Python a directory becomes an importable package when it has an __init__.py (or by namespace-package rules). Bazel ignores __init__.py entirely when it decides what a package is.

A package is a directory that contains a BUILD file, together with every file below it, except files in deeper directories that have their own BUILD file. The package's name is its path from the workspace root: app/BUILD.bazel defines package app, written //app. A BUILD file at the root defines the root package, written //.

The file may be called BUILD.bazel or BUILD. They mean the same thing. If a directory has both, Bazel reads BUILD.bazel and ignores BUILD. Prefer BUILD.bazel: it cannot collide with a directory named build/ on case-insensitive file systems (macOS, Windows), and editors recognize it.

greeter/
├── MODULE.bazel
├── app/
│   ├── BUILD.bazel        # package //app
│   └── cli.py
└── lib/
    ├── BUILD.bazel        # package //lib
    ├── greet.py
    ├── greet_test.py
    └── testdata/
        ├── BUILD.bazel    # package //lib/testdata: a subpackage of nothing, just another package
        └── words.txt

There are three packages here: //app, //lib, and //lib/testdata. words.txt belongs to //lib/testdata, not to //lib, because its nearest ancestor with a BUILD file is lib/testdata/. A directory without a BUILD file (say lib/util/) would simply be part of //lib.

"Subpackage" only describes where a directory sits. //lib/testdata is a package in its own right, with nothing inherited from //lib: not its targets, not its loads, not its visibility. Each BUILD file starts from a blank page.

Try it: this sandbox has both a BUILD and a BUILD.bazel in docs/. Query the package and see which file won.

Only //docs:pages exists. legacy_pages is never loaded, and nothing warns you. When a target you "definitely declared" does not exist, check for a second BUILD file.

Remember: a BUILD file makes a package; the package owns every file below it down to the next BUILD file; BUILD.bazel wins over BUILD.

The subpackage boundary

The boundary has two consequences that surprise Python developers. Both come from one rule: a file belongs to exactly one package, so only that package's BUILD file may refer to it by a relative path.

1. A glob stops at a subpackage

glob() is a BUILD-file function that lists files in the current package matching a pattern, like Python's pathlib.Path.glob. ** matches any number of directories. But a glob never descends into a directory that has its own BUILD file, because those files are not in this package.

# no BUILD file in docs/guides
//docs:guides/setup.md
//docs:intro.md

# after adding docs/guides/BUILD
//docs:intro.md

This is how files vanish from a build. Someone adds a BUILD file to a subdirectory for an unrelated reason, and a glob(["**/*.md"]) one level up quietly loses those files. No error, just a smaller output. When you add a package, check the globs above it.

2. A label cannot reach into a subpackage

Inside lib/BUILD.bazel, writing "testdata/words.txt" means "the file testdata/words.txt in package //lib", that is, //lib:testdata/words.txt. If lib/testdata/ has its own BUILD file, that label is invalid: the file belongs to //lib/testdata. Run the build in this sandbox:

The simulator reports the same mistake later, during analysis, as no such target '//lib:testdata/words.txt' with the hint (perhaps you meant //lib/testdata:words.txt). Same cause, same fix; real Bazel's wording is the one above.

Move the colon: "//lib/testdata:words.txt". The colon separates the package from the target name, so it must sit exactly at the package boundary. The exports_files() call in lib/testdata/BUILD.bazel is what lets another package use that file; without it you get a visibility error (Module 02).

The fix in the other direction, deleting lib/testdata/BUILD.bazel so the file belongs to //lib again, also works. Choose by intent: does testdata/ need its own targets?

Remember: globs stop at subpackages silently; labels that cross a subpackage fail loudly. The colon always sits on the package boundary.

Anatomy of a label

A Python import path like lib.greet names a module by its dotted location. A Bazel label names a target, not a file or module, and it always has two halves: which package, and which name inside it.

The full form has three parts:

@rules_python//python/private:py_library.bzl
└─────┬─────┘└──────┬──────┘ └──────┬──────┘
  repository     package        target name
 (optional)    (path from     (after the colon)
               repo root)
Repository (@name)
Which repository the package lives in. Leave it out for your own workspace (the main repository). External repositories come from bazel_deps: @rules_python exists because MODULE.bazel says bazel_dep(name = "rules_python", ...).
Package (after //)
The path from that repository's root to the directory with the BUILD file. Never a trailing slash, never ...
Target name (after :)
The name of a rule in that BUILD file, or a file path relative to the package directory (greet.py, data/words.txt if data/ has no BUILD file).

The shorthands

//lib

Means //lib:lib: the target named after the last directory of the package. Name a package's main target after its directory and you get this short form.

:helpers

Relative: the target helpers in this package. Only valid inside a BUILD file (or on the command line, relative to your current directory).

helpers

Also relative, with no colon. Works, but :helpers is the convention for rules; the bare form is used for files: srcs = ["cli.py"].

@rules_python//python:defs.bzl

A file in an external repository. You have been writing one of these in every load().

Inside app/BUILD.bazel, these four all name the same target: ":cli", "cli", "//app:cli", and "@greeter//app:cli" (the module's own name works as a repository name in the root module). You will also see @@//app:cli in Bazel's own messages: @@ is the canonical, unambiguous spelling Bazel uses internally, and @@ with nothing after it is the main repository.

Use the shortest form that is unambiguous: ":name" inside a package, "//pkg" or "//pkg:name" across packages. Never "//app:cli" from inside //app; reviewers read a full label as "this crosses packages".

The mistakes Python developers make

Each of these went into deps of //app:cli, which needs the library //lib:lib. All real Bazel 9.3.2 messages, first ERROR line only:

A relative label: it looks for lib in this package, //app.

ERROR: /work/greeter/app/BUILD.bazel:3:10: in deps attribute of py_binary rule //app:cli: rule '//app:lib' does not exist. Since this rule was created by the macro 'py_binary', the error might have been caused by the macro implementation

Fix: "//lib". Ignore the remark about the macro; py_binary is a macro around the real rule, and Bazel always adds that sentence.

A file path written like a package. Bazel reads lib/greet.py as a package name.

ERROR: no such package 'lib/greet.py': BUILD file not found in any of the following directories. Add a BUILD file to a directory to mark it as a package.
 - lib/greet.py

Fix: depend on the library target, "//lib", not on its source file.

A valid label for the source file, but deps wants libraries, and the file is private to //lib.

ERROR: /work/greeter/app/BUILD.bazel:3:10: in deps attribute of py_binary rule //app:cli: source file '//lib:greet.py' is misplaced here (expected no files). Since this rule was created by the macro 'py_binary', the error might have been caused by the macro implementation

The module is greet.py, but the target is named lib. Target names and file names are independent.

ERROR: /work/greeter/lib/BUILD.bazel: no such target '//lib:greet': target 'greet' not declared in package 'lib' defined by /work/greeter/lib/BUILD.bazel

Relative paths upward do not exist in labels. This fails while loading //app itself.

ERROR: /work/greeter/app/BUILD.bazel:3:10: //app:cli: invalid label '../lib' in element 0 of attribute 'deps' of 'py_binary': invalid target name '../lib': target names may not contain up-level references '..'

A trailing slash, as you would type for a directory in a shell.

ERROR: /work/greeter/app/BUILD.bazel:3:10: //app:cli: invalid label '//lib/' in element 0 of attribute 'deps' of 'py_binary': invalid package name 'lib/': package names may not end with '/' (perhaps you meant ":"?)

One more you will hit as soon as you split code into two packages. A target is private to its package by default, so even the correct label fails until the library opts in:

ERROR: /work/greeter/app/BUILD.bazel:8:10: in py_binary rule //app:cli: Visibility error:
target '//lib:lib' is not visible from
target '//app:cli'
Recommendation: modify the visibility declaration if you think the dependency is legitimate. For more info see https://bazel.build/concepts/visibility

Add visibility = ["//visibility:public"] (or the narrower ["//app:__pkg__"]) to the library. Module 02 treats visibility properly; for now, know the error.

Remember: @repo//package:name; //pkg is //pkg:pkg; :name is relative; the colon sits on the package boundary; you depend on targets, not files.

Three kinds of target

A target is anything a label can name. There are three kinds:

Rule targets
Declared by calling a rule in a BUILD file: py_library(name = "lib", ...) creates //lib:lib. They describe how to produce outputs from inputs.
Source file targets
Files checked into the package, like //lib:greet.py. You never declare them; a file in a package is a target automatically. The BUILD file itself is one too.
Generated file targets
Files a rule promises to produce, named in an output attribute such as outs of a genrule. //docs:toc.txt is generated by //docs:toc; building either builds the file. Module 08 covers generating files.

--output=label_kind makes bazel query print each target's kind. //docs:* means "every target in //docs", files included (more in the next section). Predict the output, then run it:

Real Bazel on a slightly bigger //docs package (one more filegroup, missing, whose srcs name a file nope.md that does not exist):

source file //docs:BUILD.bazel
filegroup rule //docs:docs
source file //docs:intro.md
filegroup rule //docs:missing
source file //docs:nope.md
genrule rule //docs:toc
generated file //docs:toc.txt

A missing file is not a loading error

Look again: //docs:nope.md is listed as a source file, though no such file exists. When a rule mentions a same-package file label, Bazel creates the target on trust. Query, loading, and analysis all succeed. The build only fails at execution, when an action needs the file's bytes:

INFO: Analyzed target //docs:missing (0 packages loaded, 2 targets configured).
ERROR: /work/handbook/docs/BUILD.bazel:6:10: //docs:missing: missing input file '//docs:nope.md'
ERROR: /work/handbook/docs/BUILD.bazel:6:10: 1 input file(s) do not exist
Target //docs:missing failed to build
Use --verbose_failures to see the command lines of failed build steps.
INFO: Elapsed time: 0.210s, Critical Path: 0.00s
INFO: 1 process: 1 internal.
ERROR: Build did NOT complete successfully

This matters for Python developers because the usual cause is a typo or a case mismatch (Readme.md vs README.md), and bazel query will not catch it. If a build says missing input file, compare the label with ls.

Why can't Bazel just check the disk while loading? Because loading must be fast and cacheable across thousands of packages, and a source file can legitimately appear later (a generated file with the same name in another configuration, a file a script writes before the build). Checking at execution keeps loading purely about BUILD files.

Remember: rules are declared, source files exist (or are assumed to), generated files are promised by a rule. A missing same-package file fails at execution with missing input file.

Target patterns: naming many targets at once

pytest tests/ collects every test below a directory. Bazel's equivalent is a target pattern: a label-like expression that expands to a set of targets. You pass patterns to build, test, and query.

PatternSelects
//...Every rule target in every package of the main repository
//tools/...Every rule target in //tools and all packages below it
//app:allEvery rule target in //app only (not subpackages)
//app:* or //app:all-targetsEvery target in //app: rules and files
//app:cliExactly one target
-//tools/exp/...Removes those targets from what earlier patterns selected

Three details trip people up:

  • //... does not include files. A package with only exports_files() and no rules contributes nothing to //....
  • Wildcards skip targets tagged manual. That is how a team keeps a slow or broken target out of bazel test //... while still building it by name (Module 05).
  • :all is a pattern, not a target. In deps you cannot write "//lib:all"; patterns only work on the command line and in query.

Exclusions need --

A pattern starting with - subtracts. But to Bazel's option parser, a leading - looks like a flag:

pixi run bazel build //... -//tools/exp/...
ERROR: Invalid options syntax: -//tools/exp/...
Note: Negative target patterns can only appear after the end of options marker ('--'). Flags corresponding to Starlark-defined build settings always start with '--', not '-'.

Put -- (the "end of options" marker, as in many Unix tools) before the patterns. Patterns are applied left to right, so the negative one goes after what it subtracts from:

pixi run bazel build -- //... -//tools/exp/...

Order matters. bazel build -- -//tools/... //... subtracts from nothing, then adds everything back: in a real run it analyzed all 5 targets, while -- //... -//tools/... analyzed 3. Put exclusions last.

Inside bazel query, which has its own expression language, subtraction is an operator and needs no --: bazel query '//... - //tools/...' (or except instead of -). Quote the whole expression so your shell passes it as one argument.

Predict what this query prints, then run the other buttons and compare.

Relative patterns

Patterns without // are relative to your current directory, like file paths. From the workspace root, bazel build app:cli is //app:cli. From inside app/, bazel build :cli works too. Scripts and CI should always use absolute patterns so they do not depend on where they run.

Long pattern lists belong in a file. bazel build --target_pattern_file=ci/targets.txt reads one pattern per line (negative patterns allowed, # comments allowed) and is easier to review than a shell one-liner. It works with build and test; bazel query rejects it (use --query_file there).

Remember: //... and :all select rules; :* adds files; exclusions go last, after --.

The four everyday commands

Every command has the shape bazel <command> [flags] <targets>. Here is each one on the two-package greeter workspace from this module (//app:cli depends on //lib).

bazel build

Builds targets and everything they depend on. Nothing runs; outputs land under bazel-bin/.

INFO: Analyzed target //app:cli (95 packages loaded, 2868 targets configured).
INFO: Found 1 target...
Target //app:cli up-to-date:
  bazel-bin/app/cli
INFO: Elapsed time: 10.020s, Critical Path: 0.20s
INFO: 12 processes: 12 internal.
INFO: Build completed successfully, 12 total actions

"95 packages loaded" is the first build in a fresh workspace: most of those packages are inside rules_python and the Python toolchain. The next build loads almost nothing and takes well under a second.

The first time you build a py_binary or py_test, rules_python 2.4.6 prints a long WARNING: Target @@//app:cli is using implicit __init__.py creation. It is harmless here; Module 03 explains it and how to silence it.

bazel run

Builds one executable target, then runs it. Arguments for your program go after --; everything before it is for Bazel:

pixi run bazel run //app:cli -- --name Ada
INFO: Analyzed target //app:cli (0 packages loaded, 0 targets configured).
INFO: Found 1 target...
Target //app:cli up-to-date:
  bazel-bin/app/cli
INFO: Elapsed time: 0.869s, Critical Path: 0.00s
INFO: 1 process: 1 internal.
INFO: Build completed successfully, 1 total action
INFO: Running command line: bazel-bin/app/cli <args omitted>
Hello, Ada! Built by Bazel.

Forget the -- and Bazel tries to parse --name as one of its own flags:

ERROR: --name :: Unrecognized option: --name

And run needs something executable: a py_binary or py_test, not a library.

ERROR: Cannot run target //lib:lib: Not executable
INFO: Elapsed time: 0.133s
INFO: 0 processes.
ERROR: Build did NOT complete successfully
ERROR: Build failed. Not running target

bazel run //app:cli -- --name Ada is the Bazel spelling of python -m app.cli --name Ada. The program runs from a prepared directory of its files and dependencies (its runfiles), with Bazel's Python 3.13, not your Pixi environment's Python. Module 03 covers runfiles.

bazel test

Builds the targets, then runs every test target among them. bazel test //... is the "run the whole suite" command:

INFO: Analyzed 3 targets (2 packages loaded, 32 targets configured).
INFO: Found 2 targets and 1 test target...
INFO: Elapsed time: 2.718s, Critical Path: 1.76s
INFO: 13 processes: 12 internal, 2 linux-sandbox.
INFO: Build completed successfully, 13 total actions
//lib:greet_test                                                         PASSED in 1.0s
Executed 1 out of 1 test: 1 test passes.
There were tests whose specified size is too big. Use the --test_verbose_timeout_warnings command line option to see which ones these are.

(rules_python's __init__.py warning is trimmed from this and the other outputs; see the note above. The last line is a hint that the test finished far inside its time budget; Module 05 covers test sizes.)

If the patterns match no tests at all, bazel test builds what it found and then fails with ERROR: No test targets were found, yet testing was requested. That usually means a typo in the pattern, or tests tagged manual.

bazel query

Answers questions about the graph without building anything. Module 09 goes deep; for now, three uses:

pixi run bazel query //...                       # list every rule target
pixi run bazel query //... --output=label_kind   # ...with each target's kind
pixi run bazel query //... --output=package      # list the packages that have rules
py_binary rule //app:cli
py_test rule //lib:greet_test
py_library rule //lib:lib

Output is sorted, one label per line, which makes it ideal for scripts and for graders like the ones in this course's labs.

Try all four here. The simulator never executes anything, so run stops at "simulated: not executed" and test tells you which tests would run.

Where the outputs go: convenience symlinks

After the first build, your workspace root has four new symlinks. Bazel's real output tree lives in a cache directory outside your workspace; these are shortcuts into it:

bazel-bin -> ~/.cache/bazel/_bazel_root/3812.../execroot/_main/bazel-out/k8-fastbuild/bin
bazel-greeter -> ~/.cache/bazel/_bazel_root/3812.../execroot/_main
bazel-out -> ~/.cache/bazel/_bazel_root/3812.../execroot/_main/bazel-out
bazel-testlogs -> ~/.cache/bazel/_bazel_root/3812.../execroot/_main/bazel-out/k8-fastbuild/testlogs
bazel-bin
Built outputs for the current configuration. bazel-bin/app/cli is the launcher; you can run it directly: ./bazel-bin/app/cli --name Grace printed Hello, Grace! Built by Bazel.
bazel-testlogs
Each test's test.log and XML results.
bazel-out
The parent of every configuration's outputs (k8-fastbuild is "Linux x86-64, default compilation mode").
bazel-<dir>
The execution root, the directory actions run in. Named after your workspace directory (here greeter/), not the module name.

Add bazel-* to .gitignore on day one, and tell your editor and linters to skip those directories. Otherwise ruff, mypy, and IDE indexers will crawl Bazel's entire output tree.

Remember: build builds, run builds one executable and runs it (program arguments after --), test builds and runs tests, query inspects without building. Outputs live under bazel-bin.

Hint

Each BUILD file needs its own load(). The library must be visible to //app: add visibility = ["//visibility:public"]. From app/BUILD.bazel the library is "//lib", short for "//lib:lib".

Show solution 
load("@rules_python//python:defs.bzl", "py_library")

py_library(
    name = "lib",
    srcs = ["greet.py"],
    visibility = ["//visibility:public"],
)
load("@rules_python//python:defs.bzl", "py_binary")

py_binary(
    name = "cli",
    srcs = ["cli.py"],
    deps = ["//lib"],
)

Naming the library after its directory is what makes the short label //lib possible. visibility = ["//app:__pkg__"] would also pass and is stricter: only //app may use it.

//lib:lib ships lib/testdata/words.txt as a data file, but lib/testdata/ is its own package, so the label in data is invalid. Fix the label. Keep lib/testdata/BUILD.bazel: the package boundary should stay where it is.

Hint

The colon separates package from target name. The package is lib/testdata, so the colon goes right after it.

Show solution 
load("@rules_python//python:defs.bzl", "py_library")

    name = "lib",
    srcs = ["greet.py"],
    data = ["//lib/testdata:words.txt"],
    visibility = ["//visibility:public"],
)

This works only because lib/testdata/BUILD.bazel calls exports_files(["words.txt"]). Without it, the file is private to its package and you would get a visibility error instead.

Show solution 
# One target pattern per line, applied in order.
//...
-//tools/experimental/...
-//app:cli_legacy

In a file, negative patterns need no --: there is no option parser to confuse. On the command line the same thing is bazel build -- //... -//tools/experimental/... -//app:cli_legacy. Excluding //tools/... instead would also drop //tools:gen.

//docs:all_pages is supposed to hold every Markdown page, but someone made docs/guides/ its own package and guides/setup.md and guides/deploy.md silently dropped out of the glob. Keep docs/guides a package. Give it a filegroup named pages holding its Markdown files, and make //docs:all_pages include that filegroup alongside its own glob, so deps(//docs:all_pages) reaches all four pages.

Hint

In docs/guides/BUILD.bazel, filegroup(name = "pages", srcs = glob(["*.md"]), ...). It is private by default, so //docs cannot use it until you add visibility. In docs/BUILD.bazel, a list plus a list is a list: glob([...]) + ["//docs/guides:pages"].

Show solution 
filegroup(
    name = "pages",
    srcs = glob(["*.md"]),
    visibility = ["//docs:__pkg__"],
)
filegroup(
    name = "all_pages",
    srcs = glob(["**/*.md"]) + ["//docs/guides:pages"],
)

Each package owns its files and exposes them through a target. That is the general pattern: when a subdirectory becomes a package, the parent stops globbing its files and depends on a target there instead.

Quiz

Recap

  • The workspace root is the nearest directory with MODULE.bazel; // always means that root. module(name = ...) names your module.
  • A package is a directory with BUILD.bazel (or BUILD; BUILD.bazel wins), owning every file down to the next BUILD file. Packages do not inherit anything from parent directories.
  • Globs stop at subpackages silently. Labels that reach into a subpackage fail while loading, with a suggestion to move the colon.
  • A label is @repo//package:name. //pkg means //pkg:pkg; :name and name are relative to the current package; @rules_python//... comes from a bazel_dep.
  • Targets are rules (declared), source files (exist, or are assumed to), or generated files (promised by a rule). A missing same-package file fails at execution: missing input file.
  • //... and :all select rule targets; :* adds files; exclusions come last, after --.
  • build, run (program arguments after --), test, and query cover daily work. Outputs live under bazel-bin, test logs under bazel-testlogs.
