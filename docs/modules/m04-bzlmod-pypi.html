Third-Party Dependencies with Bzlmod

Every real project stands on other people's code: rule sets from the Bazel Central Registry and packages from PyPI. This module takes MODULE.bazel apart line by line, shows how Bazel picks versions (and why it is not pip), and wires PyPI into the build with a hashed lock file, so import requests works under Bazel exactly as it does in your Pixi environment, on every machine.

MODULE.bazel, line by line

In a Python project, pyproject.toml names your project and lists what it needs: dependencies = ["requests>=2.31"]. Pixi's pixi.toml does the same for conda packages. Then a resolver turns those wishes into exact versions and writes a lock file.

MODULE.bazel is Bazel's pyproject.toml. You met it in M00: it marks the workspace root. Here is a complete one, the kind you will write for the rest of the course:

module(name = "weather", version = "0.1.0")

bazel_dep(name = "rules_python", version = "2.4.6")
bazel_dep(name = "bazel_skylib", version = "1.9.2")

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(python_version = "3.13", is_default = True)
module(name, version)
Names this module, the root module. It must be the first call in the file. The version only matters if someone else depends on you; leave it out in an application.
bazel_dep(name, version)
Depends on another module: a versioned bundle of Bazel code (rules, toolchains, libraries) with its own MODULE.bazel. The name is the module's registry name; the version is the minimum you accept (more on that soon).
use_extension and its tags
Run a module extension: Starlark code from a module that creates more repositories, such as a Python interpreter or a hub of PyPI packages. Covered below.

Every bazel_dep makes an external repository visible under the same name. That is why bazel_dep(name = "bazel_skylib", ...) lets a BUILD file say load("@bazel_skylib//rules:write_file.bzl", "write_file"). No bazel_dep, no @bazel_skylib.

Try it. This BUILD file uses bazel_skylib's write_file rule, but the module does not declare it. Run the build, read the error, then add the missing line to MODULE.bazel and run again.

Real Bazel fails while loading the package, because the load() names a repository the main repository cannot see:

ERROR: error loading package 'docs': Unable to find package for @@[unknown repo 'bazel_skylib' requested from @@]//rules:write_file.bzl: The repository '@@[unknown repo 'bazel_skylib' requested from @@]' could not be resolved: No repository visible as '@bazel_skylib' from main repository.

Read it as "who asked, for what, and from where": requested from @@ means the main repository (your workspace) asked, and nothing named @bazel_skylib is visible from it.

Mistakes in the bazel_dep line itself

A typo in the name or a version that does not exist fails before any BUILD file is read, while Bazel resolves the module graph:

ERROR: Error computing the main repository mapping: in module dependency chain <root> -> bazel_skylib@1.99.0: module bazel_skylib@1.99.0 not found in registries:
* https://bcr.bazel.build/modules/bazel_skylib/1.99.0/MODULE.bazel: not found

Declaring the same module twice is a Starlark error with a traceback pointing at the second line:

Error in bazel_dep: The repo name 'bazel_skylib' cannot be defined by a bazel_dep at /work/handbook/MODULE.bazel:4:10 as it is already defined by a bazel_dep at /work/handbook/MODULE.bazel:3:10

Real output on this page comes from runs of Bazel 9.3.2 with rules_python 2.4.6. Workspace paths are shortened to /work/<workspace> and Bazel's cache to ~/.cache/bazel/…; progress lines are dropped.

Remember: module() first; one bazel_dep per module; the dependency's name becomes the @name you type in labels and loads.

Versions: the registry and Minimal Version Selection

Where does bazel_skylib@1.9.2 come from? From the Bazel Central Registry (BCR) at registry.bazel.build, Bazel's PyPI. For each module and version it stores a copy of the module's MODULE.bazel and a source.json saying where to download the source archive and its checksum. Browse it to find a module's versions and its README.

Each module in the graph declares its own bazel_deps, so dependencies have dependencies. rules_python alone pulls in many more, from bazel_features to protobuf. When two modules ask for different versions of the same module, Bazel has to pick one.

pip picks the newest; Bazel picks the oldest that satisfies everyone

pip

You write ranges (requests>=2.31,<3). The resolver searches for the newest versions that satisfy every range, backtracking when they conflict. Run it next month and you may get different versions, which is why you need a lock file.

Bazel (MVS)

Every bazel_dep version is a minimum. For each module, Bazel picks the highest of the minimums anyone in the graph asked for. Never newer than someone asked for, so the same MODULE.bazel files always give the same answer.

This is Minimal Version Selection (MVS), the algorithm Go modules also use. It needs no search and no backtracking, and a new release on the registry cannot change your build until someone raises a version in a MODULE.bazel. The price: only one version of each module ends up in the graph, and it can be newer than the one you wrote.

Here is what that looks like. This workspace asks for skylib 1.7.1, but rules_shell 0.8.0 (through its own dependencies) needs at least 1.8.2:

module(name = "handbook", version = "1.0.0")

bazel_dep(name = "bazel_skylib", version = "1.7.1")
bazel_dep(name = "rules_shell", version = "0.8.0")
WARNING: For repository 'bazel_skylib', the root module requires module version bazel_skylib@1.7.1, but got bazel_skylib@1.8.2 in the resolved dependency graph. Please update the version in your MODULE.bazel or set --check_direct_dependencies=off

The build still works, with 1.8.2. Bazel warns because your file no longer tells the truth about what you run. Fix it by writing the version Bazel actually picked. Teams usually make it an error in CI with --check_direct_dependencies=error:

ERROR: For repository 'bazel_skylib', the root module requires module version bazel_skylib@1.7.1, but got bazel_skylib@1.8.2 in the resolved dependency graph. Please update the version in your MODULE.bazel or set --check_direct_dependencies=off
ERROR: Error computing the main repository mapping: Direct dependency check failed.

Going the other way works as you would expect: ask for skylib 1.9.2 and every module in the graph gets 1.9.2, even those that only asked for 1.6. "Highest minimum" means the root module can always pull a dependency up.

Your module asks for platforms 1.0.0, rules_go asks for 0.0.10, and bazel_skylib asks for 1.1.0. Which version does MVS select, and why can it never select 1.2.0 even if the registry has it? (1.1.0: the highest minimum. Nobody asked for 1.2.0.)

MVS only applies to Bazel modules (rule sets and tools from the registry). PyPI packages are resolved by pip, exactly as you are used to, then pinned in a lock file. The two systems sit side by side, and the rest of this module covers both.

Remember: a bazel_dep version is a minimum; MVS picks the highest minimum; keep your root versions equal to what is resolved.

Apparent and canonical repository names

A label like @bazel_skylib//rules:write_file.bzl starts with an apparent repository name: the name your module uses for a repository. Each module sees the world through its own names. Behind them, every repository has one canonical name, unique in the whole build, which Bazel writes with two at-signs. For a module from the registry it is the module name plus a +:

pixi run bazel query @bazel_skylib//rules:write_file.bzl --consistent_labels
@@bazel_skylib+//rules:write_file.bzl

The table that turns one into the other is the repository mapping. Bazel prints the main repository's mapping with bazel mod dump_repo_mapping '':

{"":"","handbook":"","bazel_skylib":"bazel_skylib+","bazel_tools":"bazel_tools"}

Read each pair as "apparent: canonical". "" and handbook (your module's name) both mean the main repository, whose canonical name is empty: that is the @@ you see in errors such as requested from @@. Repositories made by extensions get longer canonical names, such as @@rules_python++pip+weather_pypi: module, extension, repository.

Never type a canonical name in a BUILD file. The + format is an implementation detail that has already changed once (Bazel 7 used ~). Use apparent names; read canonical ones in error messages.

repo_name: choose the apparent name

repo_name on a bazel_dep changes the apparent name. It is mostly used to keep old BUILD files working when a module was renamed, or to shorten a long name:

bazel_dep(name = "bazel_skylib", version = "1.9.2", repo_name = "skylib")

Now @skylib works, and @bazel_skylib no longer does: the module is the same, only its name in your module changed. Run both commands, then edit the load():

Real Bazel gives the same No repository visible as '@bazel_skylib' error until the load() says @skylib. Bazel itself still calls the module bazel_skylib@1.9.2 in bazel mod graph; repo_name never changes the module's identity.

Remember: @name is apparent and per-module; @@name+ is canonical and global; repo_name only renames the apparent one.

dev_dependency and overrides

dev_dependency: dependencies only you need

In pyproject.toml, pytest goes in a dev group or an optional extra, not in dependencies, so people who install your package do not get it. Pixi has the same idea with features.

dev_dependency = True marks a bazel_dep (or a use_extension) as needed only when your module is the root: for your tests, linters, and tools. When another module depends on yours, Bazel ignores your dev dependencies entirely, so they never enter its graph or its version selection.

module(name = "textkit", version = "1.0.0")

bazel_dep(name = "bazel_skylib", version = "1.8.2")
bazel_dep(name = "rules_shell", version = "0.8.0", dev_dependency = True)  # only our sh_tests use it

As the root module, textkit sees both. You can preview what a consumer sees with --ignore_dev_dependency. Both runs below are real, on the handbook workspace with rules_shell marked dev:

<root> (handbook@1.0.0)
├───bazel_skylib@1.8.2
└───rules_shell@0.8.0 
<root> (handbook@1.0.0)
└───bazel_skylib@1.8.2

Mark something dev when your library code does not load from it. Test rule sets, formatters, a pip hub with only pytest in it: dev. The rule set your BUILD files use to build the library itself: not dev. In an application nobody will depend on, it changes nothing, but it documents intent.

Overrides: when the registry is not the answer

Sometimes you need a module from somewhere other than the registry, or a version MVS would not pick. Four override functions do this. Each takes the module_name of a module in the graph, and each only works in the root module: overrides in your dependencies' MODULE.bazel files are ignored, so a library cannot force choices on you.

single_version_override

Pin a registry module to an exact version, even below what MVS would pick. Also takes patches. Use it to hold back a broken release or to patch a module.

local_path_override

Use a module from a directory on disk (path). For a module you are developing next to your project, or one vendored into your repository.

git_override

Use a module from a Git remote at a commit. For an unreleased fix or a fork. Pin a commit hash, never a branch.

archive_override

Use a module from a source archive at urls with an integrity hash. For releases on a server that is not a registry.

bazel_dep(name = "textkit", version = "0.3.0")
local_path_override(
    module_name = "textkit",
    path = "vendor/textkit",
)

bazel_dep(name = "bazel_skylib", version = "1.9.2")
git_override(
    module_name = "bazel_skylib",
    remote = "https://github.com/bazelbuild/bazel-skylib.git",
    commit = "564ef5d5407bd9f91a046c7ceed2c259b884ac49",
)

The bazel_dep line is still required; the override only changes where the module comes from. Overridden modules show @_ instead of a version in the graph, because the version no longer comes from the registry:

<root> (handbook@0.1.0)
└───bazel_skylib@_

bazel mod show_repo shows the repository rule behind a module, which is the quickest way to confirm an override took effect:

## bazel_skylib@_:
load("@@bazel_tools//tools/build_defs/repo:git.bzl", "git_repository")
git_repository(
  name = "bazel_skylib+",
  remote = "https://github.com/bazelbuild/bazel-skylib.git",
  commit = "564ef5d5407bd9f91a046c7ceed2c259b884ac49",
)

An override for a module nobody depends on is an error, which catches typos in module_name:

ERROR: Error computing the main repository mapping: the root module specifies overrides on nonexistent module(s): nope

Every override is a decision the registry no longer makes for you, so leave a comment saying why and when to remove it. A git_override to a fork tends to outlive the bug it fixed.

Remember: dev dependencies vanish for consumers; overrides change where a module comes from and only count in the root module.

Module extensions and use_repo

A bazel_dep gives you exactly one repository: the module's own source. Many things you depend on do not fit that shape. A Python interpreter differs per operating system. A set of PyPI packages depends on your lock file. Something has to read your configuration and create repositories on demand.

That something is a module extension: Starlark code shipped by a module, which reads tags (calls such as pip.parse(...)) from every module in the graph and then defines any number of repositories. Three steps, always the same:

# 1. Get a proxy for the extension: the .bzl file that defines it, and its name.
pip = use_extension("@rules_python//python/extensions:pip.bzl", "pip")

# 2. Call tags on it to configure it. Nothing runs yet.
pip.parse(
    hub_name = "weather_pypi",
    python_version = "3.13",
    requirements_lock = "//:requirements_lock.txt",
)

# 3. Import the repositories you want to use, by name.
use_repo(pip, pypi = "weather_pypi")

Step three is the one people forget. An extension may create hundreds of repositories (one per wheel, for pip), but your module only sees the ones you import with use_repo. Like a bazel_dep, it makes an apparent name. use_repo(pip, "weather_pypi") imports it under its own name; use_repo(pip, pypi = "weather_pypi") imports it as @pypi.

Bazel runs an extension lazily, the first time something needs one of its repositories. That has a surprising consequence: a use_repo that names a repository the extension never creates is only reported when the extension runs. Here the hub is called weather_pypi but use_repo asks for pip:

ERROR: module extension @@rules_python+//python/extensions:pip.bzl%pip does not generate repository "pip", yet it is imported as "pip" in the usage at /work/weather/MODULE.bazel:11:20

The sandbox below defines a hub but never imports it. Run the build, then add the use_repo line.

Without the use_repo, real Bazel reports exactly what it reports for a missing bazel_dep, because from your module's point of view it is the same problem. From the weather workspace used later in this module, where a library depends on @pypi//python_dateutil:

ERROR: /work/weather/forecast/BUILD.bazel:3:11: no such package '@@[unknown repo 'pypi' requested from @@]//python_dateutil': The repository '@@[unknown repo 'pypi' requested from @@]' could not be resolved: No repository visible as '@pypi' from main repository and referenced by '//forecast:forecast'

bazel mod tidy rewrites MODULE.bazel so every use_repo lists exactly what the extensions report you need, and formats the file. Run it after editing extension usages.

Remember: use_extension, then tags, then use_repo. If a repository is "not visible", check the use_repo before anything else.

PyPI packages: pip.parse and the hub

With pip-tools you keep loose wishes in requirements.in, run pip-compile to get a fully pinned requirements.txt, and pip install -r it into a virtual environment. Bazel uses the same two files. It just never installs into an environment you can see.

rules_python's pip extension reads a lock file, a requirements.txt where every package, including transitive ones, is pinned with == and carries hashes. From it, the extension creates one repository per wheel and a hub repository that gives each package a friendly label. The pip.parse tag takes three attributes you always set:

hub_name
The hub repository's name. Make it unique: the convention is your module name plus _pypi.
python_version
Which registered toolchain (M03) evaluates markers and picks wheels. It must match a python.toolchain(...) call, or the extension fails.
requirements_lock
The label of the lock file, usually "//:requirements_lock.txt".

Why not hub_name = "pypi"?

Most older examples write hub_name = "pypi". With rules_python 2.4.6 that still works, but every build prints:

DEBUG: ~/.cache/bazel/…/external/rules_python+/python/private/pypi/extension.bzl:397:26: WARNING: The PyPI hub name 'pypi' is reserved (module 'weather'). Please rename your hub, otherwise a future release will rename it to 'weather_pypi'.

Since rules_python 2.2, the name pypi is reserved for a "unified" hub the extension generates on its own. So name your hub after your module and import it as @pypi with use_repo's keyword form. Your BUILD files keep the short, conventional labels:

pip = use_extension("@rules_python//python/extensions:pip.bzl", "pip")
pip.parse(
    hub_name = "weather_pypi",
    python_version = "3.13",
    requirements_lock = "//:requirements_lock.txt",
)
use_repo(pip, pypi = "weather_pypi")

Labels for PyPI packages

Each locked package becomes a package in the hub, named after its distribution name (the name on PyPI, in the lock file) normalized: lowercase, with every run of -, _, and . replaced by one underscore. @pypi//requests is short for @pypi//requests:requests, which is the target you put in deps.

In the lock fileYou importLabel
requestsimport requests@pypi//requests
python-dateutilimport dateutil@pypi//python_dateutil
PyYAMLimport yaml@pypi//pyyaml
typing-extensionsimport typing_extensions@pypi//typing_extensions
zope.interfaceimport zope.interface@pypi//zope_interface

The label follows the distribution, never the import name. This is the single most common PyPI mistake under Bazel. All three of these are wrong for python-dateutil, and real Bazel rejects each with the same message. (These runs used a hub named pypi; with weather_pypi the canonical name in the message reads @@rules_python++pip+weather_pypi.)

The import name. There is no distribution called dateutil.

ERROR: no such package '@@rules_python++pip+pypi//dateutil': BUILD file not found in directory 'dateutil' of external repository @@rules_python++pip+pypi. Add a BUILD file to a directory to mark it as a package.

The distribution name, but not normalized. Labels are matched exactly.

ERROR: no such package '@@rules_python++pip+pypi//python-dateutil': BUILD file not found in directory 'python-dateutil' of external repository @@rules_python++pip+pypi. Add a BUILD file to a directory to mark it as a package.

Normalized, except for case.

ERROR: no such package '@@rules_python++pip+pypi//Python_Dateutil': BUILD file not found in directory 'Python_Dateutil' of external repository @@rules_python++pip+pypi. Add a BUILD file to a directory to mark it as a package.

The same message also means "not in the lock file". Adding requests to requirements.in is not enough: the hub is built from the lock. Predict what this build prints, then run it.

The simulator adds a hint in parentheses, ('requests' is not in //:requirements_lock.txt …), which real Bazel does not print. It also accepts un-normalized labels such as @pypi//python-dateutil that real Bazel rejects (see the tabs above), so trust the table, not the sandbox, on spelling.

What is in the hub

Each package in the hub has a few targets. You will almost always use the default one:

@pypi//pytest:_no_matching_repository
@pypi//pytest:data
@pypi//pytest:dist_info
@pypi//pytest:extracted_whl_files
@pypi//pytest:pkg
@pypi//pytest:pytest
@pypi//pytest:srcs
@pypi//pytest:whl
@pypi//pytest:whl_file

:pytest is an alias for :pkg, a py_library with the unpacked wheel and deps on pytest's own dependencies (pluggy, iniconfig, packaging…). You list only what your code imports; the transitive packages come along.

Undeclared imports fail, even if the package is locked

The lock decides what can be used; deps decide what is on each target's import path. If dates.py adds import attrs without "@pypi//attrs" in deps, the test fails at run time even though attrs is in the lock:

    from forecast.dates import weekday
forecast/dates.py:1: in <module>
    import attrs
E   ModuleNotFoundError: No module named 'attrs'

This is Bazel's sandboxing working for you: in a virtual environment, an undeclared import works by accident because everything is installed in one place.

Remember: hub named <module>_pypi, imported as @pypi; labels use the normalized distribution name; only locked packages exist; every import needs a deps entry.

Generating the lock: compile_pip_requirements

You could run pip-tools yourself, but then the lock depends on whichever Python you ran it with. rules_python ships a macro that runs pip-compile with the hermetic interpreter from your toolchain:

load("@rules_python//python:pip.bzl", "compile_pip_requirements")

compile_pip_requirements(
    name = "requirements",
    src = "requirements.in",
    requirements_txt = "requirements_lock.txt",
)

A macro is a function that declares several targets at once. This one makes four:

filegroup rule //:requirements
py_test rule //:requirements.test
py_binary rule //:requirements.update
alias rule //:requirements_test
bazel run //:requirements.update
Re-solves requirements.in and rewrites requirements_lock.txt in your source tree. Run it after every change to requirements.in, and to upgrade.
bazel test //:requirements.test
Re-solves into a temporary file and fails if the result differs from the committed lock. It needs the network (it is tagged requires-network and no-sandbox). //:requirements_test is a deprecated alias for it.

The lock file must exist before the first run; an empty file is fine. Then:

touch requirements_lock.txt
pixi run bazel run //:requirements.update

# by the following command:
#
#    bazel run //:requirements.update
#

    --hash=sha256:9121e2c1fdb355232495be3194c8dfe87ccc2d5dee45947b78e68f499790d7a7
    # via pytest

Why the hashes matter

Each --hash is the SHA-256 of one file PyPI serves for that version (here a wheel and an sdist). When Bazel downloads the wheel, pip checks it against the hashes. A file that was replaced on the index, or a corrupted mirror, fails the build instead of quietly entering it. Change one hash by hand and you see:

ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE. If you have updated the package versions, please update the hashes. Otherwise, examine the package contents carefully; someone may have tampered with them.
        Expected sha256 a5e246f79eb80475e691bf93862cead98decd8a498cf53ba0516fcdc0f50dc1d
             Got        a5e246f79eb80475e691bf93862cead98decd8a498cf53ba0516fcdc0f50dc1c

Unpinned lock files

A Python developer's instinct is to point requirements_lock at the loose requirements.in. Don't. rules_python 2.4.6 warns that the file has no hashes, and a line with a range instead of == is not a pin at all: it is dropped. With a "lock" of pytest and python-dateutil>=2.9, the hub's package list was just ["pytest"], and the dateutil label failed as if the package did not exist:

rules_python:weather:pypi:hub:weather_pypi WARNING: requirement file has been generated without hashes, will use all hashes for the given version  that could find on the index:
ERROR: no such package '@@rules_python++pip+weather_pypi//python_dateutil': BUILD file not found in directory 'python_dateutil' of external repository @@rules_python++pip+weather_pypi. Add a BUILD file to a directory to mark it as a package.

The fix is always the same: lock with bazel run //:requirements.update and commit both files.

Keeping the lock honest

Add a package to requirements.in without updating, and the test catches it:

+requests==2.34.2 \
+    --hash=sha256:2a0d60c172f83ac6ab31e4554906c0f3b3588d37b5cb939b1c061f4907e278e0 \
+    --hash=sha256:f288924cae4e29463698d6d60bc6a4da69c89185ad1e0bcc4104f584e960b9ed
     # via -r requirements.in
…
Lock file out of date. Run 'bazel run //:requirements.update' to update.

The lock test re-resolves against the live index, so it is slow, needs the network, and starts failing on its own when a new release appears. Many teams add tags = ["manual"] to the macro so bazel test //... skips it, and run bazel test //:requirements.test in a separate CI job when requirements.in changes. The labs in this module do that.

Remember: edit requirements.in, run //:requirements.update, commit both; the lock has == pins and hashes; //:requirements.test checks they agree.

pytest under Bazel

You type pytest and it finds test_*.py files, collects test_* functions, and reports. Plain assert, fixtures, parametrize.

A py_test does not know pytest exists. It runs one file, its main, as a script, and passes if the process exits with 0. Run a pytest-style file directly and Python defines your test functions, calls none of them, and exits 0. The test "passes" with an assertion that is plainly false:

py_test(
    name = "dates_test",
    srcs = ["dates_test.py"],          # def test_weekday(): assert ... == "Tuesday"  (wrong on purpose)
    deps = [":forecast", "@pypi//pytest"],
)
INFO: From Testing //forecast:dates_test:
…
//forecast:dates_test                                                    PASSED in 0.5s
Executed 1 out of 1 test: 1 test passes.

Nothing was collected and nothing was printed. This is the most dangerous mistake in this module, because it looks like success.

A small pytest entry point

The fix is a three-line main that hands the test files to pytest and exits with pytest's status. Put it next to your tests (or in a shared //tools package) and reuse it:

import sys

import pytest

if __name__ == "__main__":
    sys.exit(pytest.main(sys.argv[1:]))
py_test(
    name = "dates_test",
    srcs = [
        "dates_test.py",
        "pytest_main.py",
    ],
    args = ["$(rootpath dates_test.py)"],
    main = "pytest_main.py",
    deps = [
        ":forecast",
        "@pypi//pytest",
    ],
)
  • main names the file Bazel runs; it must also be in srcs.

MODULE.bazel.lock

The first time you build, Bazel writes MODULE.bazel.lock next to MODULE.bazel. It is not a list of chosen versions (MVS recomputes those from the MODULE.bazel files, deterministically). It records what Bazel fetched to compute them, so the next run can skip the network and detect changes. Its top-level keys, from a real lock file:

{
  "lockFileVersion": 28,
  "registryFileHashes": { "https://bcr.bazel.build/modules/bazel_skylib/1.9.2/MODULE.bazel": "…", … },
  "selectedYankedVersions": {},
  "moduleExtensions": { "@@rules_python+//python/uv:uv.bzl%uv": { … }, … },
  "facts": { "@@rules_python+//python/extensions:pip.bzl%pip": { "dist_hashes": { … } } },
  "factsVersions": {}
}
registryFileHashes
A SHA-256 for every registry file read, such as each module's MODULE.bazel. If the registry ever serves different bytes for a published version, the build fails instead of changing.
moduleExtensions
Recorded results of module extensions, with digests of their inputs, so Bazel can skip re-running them while nothing they read has changed.
facts
Data extensions looked up, such as the wheel URLs and hashes the pip extension found on PyPI.

Commit it. It is to MODULE.bazel what pixi.lock is to pixi.toml: it makes a fresh clone and CI see exactly the inputs you saw. (This course's repository ignores it inside lab copies only so that labs start clean.)

--lockfile_mode

By default (update), Bazel adds missing entries as it goes. In CI you want the opposite: fail if the committed lock is incomplete, so nobody forgets to commit it. Add a bazel_dep without building locally first, then:

pixi run bazel build //... --lockfile_mode=error
ERROR: Error computing the main repository mapping: Missing checksum for registry file https://bcr.bazel.build/modules/platforms/1.1.0/MODULE.bazel not permitted with --lockfile_mode=error. Please run `bazel mod deps --lockfile_mode=update` to update your lockfile.

The other modes are refresh (re-fetch things that may change, such as yanked-version info) and off.

Two lock files, two jobs. requirements_lock.txt pins PyPI packages and is written by //:requirements.update. MODULE.bazel.lock records module and extension inputs and is written by Bazel itself. You edit neither by hand, and you commit both.

Remember: commit MODULE.bazel.lock; use --lockfile_mode=error in CI.

Quiz

Recap

  • MODULE.bazel starts with module(); each bazel_dep brings in one module from the Bazel Central Registry and makes @name visible.
  • Versions in bazel_dep are minimums. Minimal Version Selection picks the highest minimum, so builds do not change when the registry does. Keep root versions equal to what is resolved.
  • Apparent names (@skylib) are per module and set by repo_name; canonical names (@@bazel_skylib+) are global and only for reading errors.
  • dev_dependency = True hides a dependency from consumers. Overrides (single version, local path, git, archive) change where a module comes from and only work in the root module.
  • Module extensions create repositories from tags; use_repo imports the ones you use.
  • pip.parse(hub_name = "<module>_pypi", python_version, requirements_lock) plus use_repo(pip, pypi = "<module>_pypi") gives @pypi//<normalized distribution name>.
  • Lock with bazel run //:requirements.update; the lock has == pins and hashes; //:requirements.test keeps it in sync with requirements.in.
  • pytest needs an entry point: main = "pytest_main.py", args = ["$(rootpath ...)"], and @pypi//pytest. Without it, tests silently pass.
  • Commit MODULE.bazel.lock; CI runs with --lockfile_mode=error. bazel mod graph, deps, explain, and show_repo inspect the graph.
